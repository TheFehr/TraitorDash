# RFC 23: The Bridge's Own Settings in the Dashboard

> **Status: built (2026-11-04), not yet tried on the real server.** The bridge (`settings.lua`), the backend (`services/bridgeSettings.ts`, `POST /api/v1/settings`, `POST /api/bridge-settings/:serverId`, migration v27) and the page (`/servers/:serverId/bridge`) work and are tested, the page also in a browser. The open questions are answered in section 9. Differences from the proposal are in section 10. Follows RFC 6 (the signed command channel), RFC 8 (the bridge's configuration file) and RFC 12 (position tracking); the role settings page (RFC 4) is the model for the page.

## 1. Abstract
The dashboard changes a server's TTT2 settings (the `ttt_*` ConVars of the roles) from a page. The settings of the bridge itself (`traitordash_stats`, `traitordash_track`, the sampling interval and budget, and the like) can only be changed on the game server's console or in `server.cfg`, and the dashboard cannot even see what they are. This RFC adds a settings page for them, with the same staging, the same signed delivery and the same look as the role settings, admin only, for the settings that are safe to change from the dashboard. The connection settings (the dashboard's address, the token, the public address) are left out on purpose.

## 2. Motivation
*   An operator who wants a faster position sampling for smoother replays has to know that a ConVar exists, what it is called, what range it takes and where to put it, and has no way to see what the server runs with now. This came up in practice (2026-11-04, "any way to increase sample time on the server?").
*   The dashboard shows the live value of every role ConVar and lets an admin change it. The bridge's own settings are the odd ones out, which makes the bridge look configured when it may not be (tracking is off by default and nothing says so).
*   Nothing was decided against this. The dashboard grew up around the role settings; the bridge's own ConVars were added later for operators, and RFC 8 only moved the connection settings into a file.

## 3. What is there
*   **The bridge's ConVars:** `traitordash_stats`, `traitordash_stats_debug`, `traitordash_stats_bots` (stats.lua); `traitordash_track`, `traitordash_track_interval_min`, `traitordash_track_interval_max`, `traitordash_track_budget_ms` (track.lua); `traitordash_url`, `traitordash_token`, `traitordash_public_url` (bridge.lua, read through `config.lua`, RFC 8). The sampling ones are read again at every tick, so a change takes effect at once.
*   **The command channel (RFC 6).** The backend stages commands (`commands` table); the bridge asks (`POST /api/v1/poll`), gets the staged commands in a signed answer, applies them and sends their ids back (`acked`); an unacknowledged command stays for an hour. The bridge **re-validates everything itself**: `commands.lua` accepts a `convar` command only for a name that matches `^ttt2?_[%w_]+$` and a value from a strict character set, and applies it with `RunConsoleCommand` (one command, never chained). That is deliberate: "the backend is trusted to carry admin changes, not to be a remote console". The `traitordash_` names are therefore not settable through it today.
*   **The role settings.** `POST /api/save/:serverId/:role` checks every name against the role's schema and the ConVars the server reported, every value against a strict pattern, stages one command each, and writes an audit entry. The page (RFC 4, 17) shows each setting's live value, default and range as the bridge reported them (`POST /api/v1/values`, `convar_values`), a save bar when something differs, and a toast for the result.
*   **The configuration file (RFC 8).** `data/traitordash/config.json` holds `url`, `token` and `public_url` (and `version`); the bridge writes it only after pairing.

## 4. Proposal

### 4.1 A registry of settings, in both places
One list says which settings the dashboard may change, each with its name, type, range and the words shown beside it. It exists twice, in the bridge (`settings.lua`) and in the backend (`services/bridgeSettings.ts`), as the signature code does, with a test that compares the two (names, types, ranges), so they cannot drift apart. The bridge's copy decides what it accepts; the backend's decides what the page offers.

First list (all with a default, a range and a plain description):

| Setting | Type | Range | Applies |
|---|---|---|---|
| `traitordash_stats` | on/off | | at once |
| `traitordash_stats_debug` | on/off | | at once |
| `traitordash_stats_bots` | on/off | | next round |
| `traitordash_track` | on/off | | next round |
| `traitordash_track_interval_min` | seconds | 0.05 to 2 (0.1 to 2 in the first version) | at once |
| `traitordash_track_interval_max` | seconds | 0.2 to 5, not under the minimum | at once |
| `traitordash_track_budget_ms` | milliseconds | 0.05 to 5 | at once |

A new setting is added to both lists, with its explanation; nothing else is needed.

### 4.2 Not on the list, on purpose
`traitordash_url` and `traitordash_token` are how the bridge finds and trusts the dashboard: if the dashboard could change them, a dashboard that was taken over could point every bridge at another server and take over the game server's command channel. `traitordash_public_url` is the address players are sent to by the in-game menu, so changing it from the dashboard would be a way to send players anywhere. They stay in `config.json` and `server.cfg` (and the pairing command). Anything that is a setting of the *backend* (`GAME_CONTENT`, `MAP_GEOMETRY` and the other environment variables) is not a game server setting and is not touched. The debug commands (`traitordash_role_trace`, `traitordash_frametime`) are tools for a person at the console, not settings.

### 4.3 The bridge reports what it runs with
On every sync and every 10 minutes the bridge sends `POST /api/v1/settings` (the server's token): its version and the value of every setting on the list (and nothing else), which the backend keeps (a table `bridge_settings`: server, name, value, reported at; the version with the server). Without this the page could only show what was *asked for*, not what runs. An older bridge never reports; the page then says so and offers nothing to change.

### 4.4 Changing a setting
*   The page stages one `setting` command for each changed setting through a new route (`POST /api/bridge-settings/:serverId`, admin, CSRF-checked like the role save), after the backend's own check of name, type and range against the registry. The values are written into the commands in the one strict format the bridge parses.
*   The bridge accepts a `setting` command only for a name on **its** list and a value inside **its** range, applies it (`RunConsoleCommand`), saves it (4.5), answers with the next report so the page sees the new value, and acknowledges the command like any other. A refused one is acknowledged too and logged on the console with the reason (so a bad command does not return for an hour).
*   Every save is an audit entry (`SAVE_BRIDGE_SETTINGS`, the names and values), as the role save is.
*   Delivery, expiry and rate limits are those of the existing channel (RFC 6).

### 4.5 Which wins: the dashboard or `server.cfg`
`server.cfg` is run at every start, so a ConVar changed from the dashboard would be undone at the next restart. The bridge therefore keeps what the dashboard set in `data/traitordash/config.json` under `settings` (as `{ "traitordash_track": "1", ... }`, an additive key: the file stays version 1 and an older bridge ignores it), and applies it when it starts, after `server.cfg`, as it already prefers the file over the ConVars for `url` and `token`. This extends RFC 8's rule "the bridge never writes the file except as the result of an explicit pairing" to "and when it applies a setting from the dashboard"; the write is atomic and holds only the settings of the list. A setting changed on the console afterwards lasts until the next start; the page then shows the value that runs, and a note when the file holds another one.

### 4.6 The page
Admin only (`admin` tier). `/servers/:serverId/bridge`, linked from the server's page next to the role settings. It looks like the role settings page: the same panels and fields, a switch for each on/off setting and a number with its range for the others, the live value and its source (reported by the bridge, default, not reported), the description in plain words ("a faster sampling gives a smoother replay and a bigger track"), a save bar when something differs and a toast for the result. Settings are grouped (Round stats, Position tracking). Each carries its explanation in words (what it does and what it costs where that is known: a track grows with the sampling rate), and a button that puts it back to its default; one that is not at its default is marked. Above them: the bridge's version, when it last reported, and whether the server is connected. After a save the page waits for the next report and says "applied" when the reported value is the new one, or "waiting for the game server" while it is not, and "not applied" after the hour a command lives.

## 5. What we do not do
*   Change the connection settings or run console commands from the dashboard (4.2).
*   Settings of the TTT2 gamemode or its roles: those are the role settings.
*   Per-user permissions: the page is for admins, as the role settings are.
*   Read `server.cfg` or any file of the game server.

## 6. Security Considerations
*   A dashboard that is taken over can, with this, only set the settings on the list to values inside their ranges: switch tracking or stats off, or sample faster or slower within limits that cannot harm the game (the sampling already slows itself down when it costs too much, RFC 12). It cannot reach the connection settings, a console command or any other ConVar. That is the same trust the dashboard has already (it can change every role setting).
*   Both ends validate; the bridge validates last and never trusts the registry it was sent (it does not receive one).
*   Values pass one strict pattern (numbers and `0`/`1`), as the role settings' values do; a name with anything else is refused whole.
*   The report carries the list's values and nothing else, so it cannot leak anything.

## 7. Testing
*   The two registries are equal (a test reads both). The bridge's list and ranges: a value outside is refused and acknowledged, a name off the list (`traitordash_token`, `traitordash_url`, `rcon_password`, a `ttt_` name sent as a `setting`) is refused, a minimum above the maximum is refused.
*   The bridge harness: a `setting` command applies, is saved to the file (and the file keeps its other keys), is applied again at start after the ConVar default, is reported, and a failed write is logged without changing the running value's report.
*   The backend: the route's gate (admin only, CSRF), validation, staging one command each, the audit entry; the report endpoint stores exactly the listed names and refuses others; an older bridge's page offers nothing to change.
*   The page: fields from the registry, live values, the save bar, the pending and applied states.

## 8. Stages
1.  **The bridge:** `settings.lua` (the list, the report, the `setting` command, the file), with its tests.
2.  **The backend:** the registry, `POST /api/v1/settings`, the table and migration, the save route, with tests.
3.  **The page** and its link.
4.  **Documentation:** what the dashboard can and cannot change; how it relates to `server.cfg` (4.5); RFC 8 and RFC 12 point here.

## 9. Decisions of the maintainer (2026-11-04)
*   **Scope:** all the bridge's settings that are not too risky. The connection settings (`traitordash_url`, `traitordash_token`) and **`traitordash_public_url`** stay out, for the reasons in 4.2.
*   **Staging and delivery:** the same as the role settings (a save bar, staged commands, the signed channel, an audit entry).
*   **Who:** admins only.
*   **Dashboard and `server.cfg`:** the dashboard wins after a restart (4.5): what it set is kept in the configuration file and applied after `server.cfg`.
*   **Reset to default:** each setting has a button that puts it back to its default (it stages the default like any other change), and a setting that is not at its default is marked.
*   **Explanations, not warnings:** each setting carries a clear explanation of what it does and what it costs (a faster sampling makes a smoother replay and a bigger track and costs the game server a little more at each tick). There is no warning or confirmation when a value is changed.
*   **Process:** an RFC first; this is it.

## 10. As built
*   **The bridge's version is not reported** (4.3): the bridge has no version string yet; the page shows when the game server last reported. The report carries a `format` number for later.
*   **The longest sampling time against the shortest** (4.1) is checked by the backend only, counting the value the server reports for the one that was not sent. The bridge checks each setting's own range and does not compare the two.
*   **A report is sent** two seconds after any of the seven ConVars changes (also from the console), eight seconds after the start, and every ten minutes; not on every sync. A backend that answers 404 is left alone for five minutes (the ten-minute timer then asks again), see the last point.
*   **The page waits** by asking `GET /api/bridge-settings/:serverId` every four seconds after a save: "waiting for the game server" until the reported value is the new one, then the note goes; "not applied" after the hour a command lives.
*   **At start** the saved settings are applied twice, at once and five seconds later, because `server.cfg` of the map can run after the bridge starts.
*   **A console command** `traitordash_settings` lists each setting with its value, marks a default, and says what the dashboard set.
*   **A dashboard that is older than the bridge (found 2026-11-05).** The first version gave up on a 404 until the next map change and said nothing, so a dashboard that was updated after the game server started never heard from the bridge, and the page said "not reported" with nothing in the console to say why (the log of the game server was read to find out: no error, the role sync fine). Now a 404 is left alone for five minutes, the ten-minute timer asks again on the same map, and the console says it once ("the dashboard does not know the settings report yet ... it is asked again every ten minutes"). A failure to send and any other refusal are told once too, and again only after a report has got through. Tests in `settings_bridge.test.ts`.
*   **A setting that is a whole number, and the limit of ticks (2026-11-05).** The settings list gained a kind `int` (a whole number; written as it is, never in the `%.4g` form that would turn 40000 into `4e+04`) and `traitordash_track_max_ticks` (default 40,000, 1,000 to 100,000): the most ticks a round records, which was a constant of the bridge (RFC 12, 3.2). The backend's own limit is the ceiling, 100,000. At 0.2 s between samples 40,000 ticks are about two and a half hours, at 0.05 s 33 minutes.

### 11. One page for the settings of a server (2026-11-05)
The settings were on two places: the bridge's on `/servers/<id>/bridge` and the retention of the replays (how many tracks, how many MB, RFC 12, 3.4) in a card on the Rounds tab of the statistics; and the list of servers had no button to either (the maintainer: "this should move into a shared config UI" and "why is there no config button here?"). Now:
*   **One page, `/servers/<id>/settings`**, with the groups Round stats and Position tracking (the bridge's, staged to the game server as before) and **Replay storage** (the dashboard's own, saved at once): the usage line, the two limits as fields in the same look (with a "dashboard" badge instead of the live one, "reset to default", the ceiling of the instance as the range) and the button that deletes the rounds only test bots played in. One save bar for all: the bridge's changes go through `POST /api/bridge-settings/<id>` as before, the limits through `POST /api/track-limits/<id>` (the same rules and the same audit entry as the form of the stats page, answered as JSON), and the message says what was done. The old address `/bridge` goes to the new page (301).
*   **A Settings button** in the list of servers, beside Connect, and the link on the server's page is "Settings".
*   **The Rounds tab** keeps one line for an admin: "Replays: 62 tracks, 2.6 MB used of 200 tracks / 200 MB. Change the limits in Settings", where the card was.
Tests in `bridge_settings_page.test.ts` and `tracks_admin.test.ts`.
*   **A ninth setting, `traitordash_track_parts` (2026-11-05).** Records doors, lifts and traps with the track (RFC 20, stage 2); a bool in the group "Position tracking", applied from the next round, off by default.
