# RFC 22: The Players' Real Models in the Replay

> **Status: stages 0 and 1 built (2026-11-04): the replay draws the posed stock model in the team's colour; stages 2 (each player's model) and 3 (the crouch in the replay) are not built. Not yet seen on a real server's replay of a real round. Decisions of the maintainer are in section 9.** Follows RFC 12 (the replay), RFC 14 (events in the track) and RFC 18 (reading the game's own models). It turns the idea noted in RFC 12, 7.2, into a plan. Stage 1 needs no change in the game server. Crouching must look right, so posing the model (stage 3) is wanted, not optional.

## 1. Abstract
The replay draws every player as the same small figure made of boxes. The game's own player models are in the content the backend can already read (RFC 18, `GAME_CONTENT=1`): the Counter-Strike: Source models TTT hands out by default are in the free Counter-Strike: Source server files, the others of the base game in the Garry's Mod ones. This RFC draws a real model for a player: first one stock model for everyone, then the model each player actually had in that round.

## 2. Motivation
*   The figure says "a person stands here" and nothing more; a real model also shows size and heading, and it is what the players remember seeing.
*   The code to read a model exists and is tested (RFC 18, 4.3, `maps/model.ts`), and so does the cache of the game's files (`services/gameContent.ts`). What is missing is the choice of which model and a way to serve it to the viewer.
*   Only the WebGL replay needs it. The canvas replay of RFC 19 draws pins and does not change.

## 3. What is there, and its limits
*   `readModel` reads one model's **first body part, first model, first level of detail**, as triangles in the model's own space (Source's axes, the feet at the origin, facing +x). It reads no materials (except "is this foliage"), no skeleton and no animation. A player model read this way is its **reference pose**: usually standing with the arms out or down, the same for every frame.
*   The track (RFC 12) records, for each player, positions and the view yaw, and nothing about the body: not the model, not the pose, not whether the player ducks.
*   Workshop player models are not in the game's content. A server that uses them gets the box figure for those players.
*   The backend has no route that serves a single model, and the map's GLB writer (`meshGlb.ts`) writes a map, not a model.

## 3b. The probe (2026-11-04)
A throw-away script (not in the repository) read the real files of six stock player models (`phoenix`, `arctic`, `guerilla`, `leet`, `police` and `kleiner`, from the free Garry's Mod and Counter-Strike: Source server files) and the animation set they use, and posed them. What it found:
*   **Where the animations are.** Not in the player model: each has two sequences of its own (`idle`, `ragdoll`) and includes `models/m_anm.mdl`, Garry's Mod's shared set of 464 sequences. m_anm keeps the data of the frames in an external file, `models/m_anm.ani` (7.1 MB). Both are in the same package archive as many of the models (`garrysmod_001.vpk`), so the existing fetching code can get them; the female models include `f_anm.mdl` and `f_anm.ani` (7.3 MB) in the same way, which the probe did not read.
*   **The skeleton matches.** `phoenix`, `arctic`, `guerilla` and `leet` have the 56 bones of m_anm, with the same names (matched by name), and all matched. `police` has one bone m_anm lacks (`baton_parent`) and `kleiner` has 69 bones, 13 of them not in m_anm; those keep their own bind position.
*   **The sequences exist.** `idle_all_01` is the standing idle and `cidle_all` the crouching idle; there are also one for each weapon (`idle_pistol`, `cidle_pistol`, `idle_ar2` and so on), which a later step could use to have the player hold what they hold.
*   **The data can be decoded.** In frame 0 of the standing and the crouching idle (103 bone entries) the rotation and position were stored in three ways: raw 64-bit quaternions (64), run-length coded Euler angles (37) and the same with a run-length position (2), the position of one bone being raw half-floats. The 48-bit quaternion form did not appear and was not tested. For a sequence longer than a section (30 frames) the first frame is in the first section. The vertices carry up to three bone weights each (they sum to 1 everywhere); linear blend skinning with them gives the posed mesh.
*   **The result looks right.** Standing, the model is 71 to 74 units tall (the hull is 72) with the arms hanging; crouching, it is about 46 units tall (the crouch hull is 36, plus the head, which is above it) and squats with the knees forward and the hands up. The reference pose, by contrast, is the T-pose with arms out that was feared, so it must not be drawn. Reading, decoding and posing a model took about 45 ms in all.
*   **A pitfall found on the way.** The first version of the decoder read the second and third angle of each run-length value pointer from the wrong base (the three offsets of a pointer are all counted from the start of the pointer, not each from its own place), which left the standing pose looking right (it is mostly raw quaternions) and bent the crouch legs and spine wrongly: one leg went backwards with the heel in the air. The stage 3 tests must check bone positions of a known pose (feet on the floor, knees in front of the hips when crouching), not only that the numbers decode.
*   **Rough edges.** The decoded poses put the lowest point of the mesh a few units below the floor (standing 1 to 3, crouching about 7), so the pose is moved so that the feet stand on the floor (the lowest foot bone decides). The frame is the first of an animation that loops; for a crouch that is the start of the loop, which is fine for a still.
*   **Sizes.** A posed model is about 6 000 vertices and 5 000 triangles, about 110 KB as a binary glTF file; one file for each pose and model.

## 4. Proposal

### 4.1 Stage 1: one stock model for everyone
*   One stock model is chosen by the operator's setting `PLAYER_MODEL` (default a Counter-Strike: Source terrorist model, which every Garry's Mod server has the content for) and is read through `readModel` and the game-content cache, exactly like a prop.
*   The model is turned into a small glTF file and served by a new route, `GET /servers/:serverId/models/:name.glb`, behind the same gate as the map's mesh (a signed-in visitor, RFC 13). `:name` must be a model name that the stored tracks or the setting name; any other is a 404, so the route cannot be used to read the game's files at will.
*   In `replay.ts` the figure of RFC 12 (3.5) is replaced by the model's mesh, a matte material in the team colour (no textures are read), `dim` for a body that lies where its player died, placed at the pose and turned by the yaw like the figure. The name, the pin and the ring stay.
*   If the model cannot be loaded (no game content, a failed read), the box figure stays. Nothing else changes in the page.
*   No new data, no migration, no change in the bridge.

### 4.2 Stage 2: each player's own model
*   The bridge adds `model` to each player of the track: `ply:GetModel()` at the start of the round, as one lowercase path like `models/player/phoenix.mdl`. At most 128 characters; a bot or a missing model sends nothing.
*   The backend accepts the field only as `^models/[a-z0-9_./-]{1,120}\.mdl$` without `..`, and stores it inside the track JSON, so no migration is needed. A track without it (every track recorded before) uses the stock model of stage 1.
*   The viewer asks for each distinct model once (a handful for 16 players) and shares one geometry between the players that have it.
*   A model the content does not have (a Workshop model) is remembered as missing (the cache keeps a negative entry, so the backend does not look again) and its players get the stock model or the box figure, as the setting says.

### 4.3 Limits and cost
*   `readModel` already caps a model at 50 000 triangles; this view takes 20 000 for a player model and leaves out a larger one. At 16 players sharing a handful of models the drawing cost is far below the map's.
*   A served model is a few hundred kilobytes at most and is cached by name for good, like the props.
*   The new route is rate limited like the mesh route.

## 4b. Stage 1 as built
*   `maps/posedmodel.ts` reads the model and the animation set and returns the posed mesh (`readPosedModel(files, animations, pose)`); `maps/modelGlb.ts` writes it as a GLB; `services/playermodel.ts` chooses the model (`PLAYER_MODEL`, a model path, else `models/player/phoenix.mdl`), fetches the files through the game-content cache (which now also fetches an animation set: a model file and a `.ani` file, no vertices) and keeps each built pose in memory. A failure (a download, a model that cannot be read) is not remembered, so a later request tries again.
*   Route `GET /servers/:serverId/playermodel.glb?pose=stand|crouch`, for signed-in visitors under the mesh's rate limit, `private, max-age=86400`; 404 when the switches are off, the server or pose is unknown, or the model cannot be built. Both poses are served; the replay asks for the standing one only.
*   The replay's payload carries `playerModel` (the route's address) when `MAP_GEOMETRY=1` and `GAME_CONTENT=1`, and the ETag includes whether it does. `replay.ts` loads the model before it builds the markers and draws one mesh per player: a matte material in the role's colour (dimmed for a body that lies where its player died, and recoloured at a conversion like the box figure was), the pin and name above its real height, the body lying on its back on the floor. If the request or the file fails, the box figure is drawn, as before.
*   The feet are put on the floor by the lowest vertex (not the lowest foot bone, as the plan said: it is simpler and the soles are what touch the floor). The triangles are turned from Source's clockwise winding to glTF's counter-clockwise; the file holds Source's coordinates under a root node that turns Z-up into Y-up, like the map's.
*   Tested (`posedmodel.test.ts`, `playermodel.test.ts`, `gamecontent.test.ts`): a model made by eye (three bones, three vertices) is posed with a quaternion and with run-length angles, the third axis of which was the pitfall of 3b; blended weights; the feet on the floor; faces outward; the bad files of 7 give null; the route's gate, caching, failure and setting; the payload; the file passes the Khronos reference validator with no warnings. On the real files of six player models the poses take 1 to 12 ms and give 4 500 to 6 400 triangles and a GLB of 144 to 202 KB; the replay was rendered in Chromium with WebGL on and showed the models standing in the Airbus map in the colours of the teams.
*   **Found on the first real round (2026-11-04, a video of the Lego replay on a phone):** the lying bodies hung in the air, about 64 units up (an eye's height). The bridge reports a death's position from `TTT2PostPlayerDeath`, which runs after the victim has become a spectator, whose view sits at the height of their eyes (the cause is deduced from the numbers, not yet checked against a stored track). The replay now puts a body at the height of the victim's last sample (their feet) when that is within 100 units of the reported height (`deathPosition` in `replaylogic.ts`, tested), draws the kill line at chest height between the two, and puts the death cross over the middle of the lying body instead of over its feet. The reported height is still wrong in the stored data, in the killzones (RFC 21) too; the proper fix is to take the position in `DoPlayerDeath`, before the victim is a spectator.
*   Known: the crouch of `leet` is 69 units tall where the others are 49 to 52 (some bone is not what the others are); stage 3 must look at it.

## 5. What we do not do
*   **Moving animation.** Walking and running legs, swimming strokes and the like need a frame for each moment (the player's sequence and cycle recorded in the track). Not planned. What is planned (stage 3) is **still poses**: standing, crouching and lying, each one frame of a sequence of the model.
*   **Textures.** The model's materials are not read; the team colour is the look. A skin or a bodygroup the player had (a different head, a hat) is not shown: the first body part's first model is the whole body.
*   **Workshop player models.** Fetching them would need the player's addon list and a download of each; not planned.
*   **The canvas replay and the map page.** They draw pins and shapes; no model.

## 6. Security Considerations
*   The path comes from the game server's bridge, which is trusted only as far as its token goes. It is checked against a strict pattern, never used as a file path on the backend (the content cache looks it up by name in the game's index files) and never echoed into a page without escaping.
*   The route serves only names that a stored track or the setting contains, and only to signed-in visitors, so it adds no way to enumerate the game's content or to read a file outside it.
*   The model files themselves are untrusted: `readModel` already turns any read past the end into `null` and caps every count (RFC 18, 4.3).

## 7. Testing
*   Path validation (accepted and refused names, length, `..`, upper case).
*   The route: gate (anonymous refused, signed-in served), a name no track has is 404, a missing model is 404 with the negative entry kept, the glTF passes the Khronos reference validator like the map's files do.
*   The bridge test of the track includes the model for a player and omits it for a bot.
*   A track without the field replays with the stock model.
*   In a browser (Chromium with WebGL on): the model appears at the pose, turned to the yaw, in the team colour; a player whose model is missing is drawn with the box figure. A screenshot is compared with the figure's.

## 8. Alternatives Considered
*   **Read the model in the browser** from the game's files directly: the files are not served to browsers and are large; the backend already reads and caches them.
*   **One generic mannequin** drawn by the viewer: cheaper, but it is not "the game's model", which was the point.
*   **Record the full pose** (a sequence and a cycle for each sample) so the replay could animate the model: the track would grow by about a third and the animation would have to be decoded for every frame. Stage 3 records only whether the player ducks (one number for each sample) and uses one frame of a standing and of a crouching sequence.

## 9. Decisions and what is still open
Decided by the maintainer (2026-11-04):
*   **The stock model is one neutral model** for everyone (the stage 1 setting `PLAYER_MODEL`), not one per team; the team shows in the colour.
*   **Crouching has to look correct.** So the model is posed (stage 3): the reference pose is not enough, and a squashed or sunk figure is not acceptable for a crouch. This also answers the T-pose worry: a standing pose taken from the model's own idle sequence replaces the reference pose.
*   **Size:** the model is drawn at its own size, not stretched to the 32 by 72 box of the old figure. The position of a player is where the feet are, which the model's origin also is, so it stands in the right place either way. The ring and the pin are placed from the model's real height.

Still open:
1.  ~~Where are the animations?~~ In `models/m_anm.mdl` and `models/m_anm.ani` (section 3b), which are fetched like a model.
2.  **Lying.** A body lying where a player died is a rotation of the standing pose (as the figure does) until a death sequence is wanted.

## 10. Stages
0.  **Probe: done** (section 3b). Stage 3 is feasible and smaller than feared.
1.  **One stock model, served and drawn** (4.1). **Built** (4b), in the standing pose, with the box figure for a model that cannot be read. No bridge change. Still to do: look at a real round on the real server.
2.  **Each player's model** (4.2).
3.  **Posed stills, so crouching looks right.** The bridge records whether the player ducks (`ply:Crouching()`), one number for each sample next to `x`, `y`, `z` and `a` (about a sixth more per sample; the byte cap of RFC 12 still holds and is rechecked). The backend reads the model's bones and vertex weights and one frame of the standing and of the crouching idle sequence, and serves the model once for each pose. The viewer swaps by the recorded state. A track without the number is drawn standing.
