# RFC 31: Joining Voice Without a Steam Sign-In (a Code from the Game)

> **Status: built (2026-11-13).** Asked for by the maintainer: friends who play on the server should not each have to sign in to Steam in their browser to use the voice page. Builds on RFC 13 (who is signed in), RFC 16 (the game vouches for a player) and RFC 27 (the voice page).

## 1. Abstract
The voice page needs a real browser (a microphone, WebRTC), so it cannot run in the game's own browser window, and the Steam overlay browser has no microphone (tested by the maintainer). The in-game pages (RFC 16) get their sign-in from the game server: the bridge vouches for each player with a signed key, and the client puts it into a link. That cannot be used here, because **a GMod client cannot open a link in the player's own browser**: `gui.OpenURL` opens the Steam overlay browser, asks the player to confirm, and takes only `http://` or `https://` addresses (Facepunch wiki; a `steam://openurl_external/` address is not documented to work and was not found in any addon). So the link has to be carried by the player.

This RFC does that with a short code: the player types `!voice` in the game chat, the game shows a code such as `K7F-3QX`, and the player types it on the voice page in their own browser. The browser is then remembered for 30 days, **for the voice page only**, so a friend pairs once per device, bookmarks the voice page and does not need the game again for a month.

## 2. Rules
1.  **Only a player in the game can get a code.** The code is made by the game server's bridge for a player who is connected (the server's token, RFC 13, 4.4). A friend who is not in the game uses the Steam sign-in as today.
2.  **A code is single-use and short-lived**: 6 characters, 5 minutes, used up by the first successful entry. A new `!voice` replaces the player's earlier code.
3.  **What it gives is small.** A cookie that is accepted by the voice page and its three data routes (`GET /servers/:id/voice`, `POST …/voice/token`, `GET …/voice/people`) and **nowhere else**; it is a plain user, **never an admin, not even for an admin's account**; it follows the same switches as a sign-in (`OPEN_SIGNIN`, the block list) and is checked on every request, so blocking a player ends it at once.
4.  **The Steam sign-in stays** and is tried first: someone with a real session or a game session does not need the code.

## 3. Design
*   **Chat.** The bridge answers `!voice` in `PlayerSay` (the same hook and the same "hide the line when it was ours" as `!role`, `rolemenu.lua`), only when `traitordash_voice` is on. It asks the backend for a code for the player's SteamID64 and prints, to that player only (`ChatPrint`), for example: `Voice code K7F-3QX (5 minutes). Open <address>/voice in your browser and type it there.` (the short address, section 10; first built with the server's own voice page address, which wrapped over three chat lines). The address is the bridge's configured base URL, as for the role guide. The player can say `!voice` again for a new code. The line is hidden so that other players do not see the command; the code is never broadcast.
*   **Backend route** `POST /api/v1/voice-codes` (tier `bridge`; the server's token): body `{ steam_id }` (a SteamID64, validated), answer `{ success, code, ttl, path }`. A limiter per server (a few a minute, as `ingame-keys`) and one per player (one new code every 10 seconds). Codes are kept **in memory** (a map from code to `{ steamId, serverId, expires }`, at most a few hundred, swept on every call); a restart of the backend loses them, which only means "ask for a new one".
*   **The alphabet.** 28 characters: the digits 2 to 9 and the consonants without `L` (no `0 O 1 I`, and no vowels, so a code never spells a word); the code is shown as two groups of three. Typed input is upper-cased and stripped of spaces and dashes. 28^6 is 481 million; with at most about ten live codes, a guess hits with probability 10 in 481 million; the entry route is limited per address (10 attempts a minute) and, as a whole, to 60 failed attempts a minute, after which entry waits (the rate limiter of RFC 13).
*   **Entry.** When the voice page is opened without a session, it no longer only sends the visitor to Steam: it shows a small page with the code field and "Sign in with Steam instead". The field posts to `POST /auth/voice-code` (a form, same site; the `Origin` is checked; the answer is a redirect to the voice page, `no-store`, `no-referrer`). A wrong, used or expired code redirects back with a short message ("That code did not work. Say !voice in the game for a new one."); it does not say which.
*   **The cookie** `td_voice` (`__Host-td_voice` over https, like the others): `<SteamID64>.<expiry>.<signature>`, an HMAC under a key derived from the session secret for the purpose `traitordash voice` (a key that is not the game key's and not the session cookie's, so none of the three can be used as another; the code of `gameKey.ts` is the model), HttpOnly, SameSite Lax, 30 days. Nothing in it says "admin" and it carries no server (the code does, section 10; the cookie does not): it is for a player, and each server's voice page still applies its own rules (RFC 27).
*   **Where it is read.** `getSession` is **not** changed, so the cookie opens no other page and no other route. The three voice routes use a small `getVoiceSession` (the real session or the game session first, then this cookie) in place of `getSession`; the page route and the three data routes are in the tiers file as `user` now and stay `user` (the tiers test says so). The 30 days therefore do not extend the 6-hour game session to the whole site.
*   **Forgetting.** A "Forget this browser" button on the voice page (a POST to `/auth/voice-logout`) clears the cookie; `/auth/logout` clears it too.
*   **What it does not need.** No database table, no migration, no new setting (RFC 23: it follows `traitordash_voice`), no change to the media server.

## 4. Risks and what they cost
*   **A stolen code** lets someone speak as that player for the short time it lives and once. Typed by the player, it lives in the chat history and on a screen for 5 minutes; that is the cost of not sending it over a link.
*   **A stolen cookie** gives the voice page as that player for up to 30 days, nothing else; blocking the player, turning off `OPEN_SIGNIN` for non-admins or changing the session secret ends it. There is no per-browser list, so one lost browser cannot be revoked alone (see 6).
*   **Login by force** (someone makes a victim's browser enter the attacker's code): the victim's browser would speak as the attacker's player. It needs the victim to submit a form; the `Origin` check and SameSite Lax close the cross-site way.
*   **The game server can name any SteamID64** (RFC 16, 4 says the same): it can already report anything about its own players, and the cookie it can obtain this way is a voice-only plain user.

## 5. Stages
*   **A (this RFC):** the route, the entry page, the cookie, the three routes, the chat command, tests, the docs.
*   **B (only if wanted):** a list of paired browsers per player with revoke (needs a table); a "pair" button for the Tauri app of RFC 27 stage 2.

## 6. Open
*   **Revoking one browser.** Stateless, so "everyone" (the secret) or "the player" (the block list) only. If that turns out to matter, stage B.
*   **Length of the memory.** 30 days is the maintainer's idea of "pair once and forget"; shorter costs a `!voice` more often, longer widens a stolen cookie. Decide on use.
*   **A code is tied to the player and to the server that issued it** (decided 2026-11-13, section 10). Entering it anywhere gives the player's cookie and leads to that server's voice page; it cannot be used to reach another server's page. The cookie itself is the player's and names no server.
*   **Players who are not on the server but are friends.** They can use the Steam sign-in. If that is too much, the code could be made by an admin from the dashboard for a named SteamID64; not planned.

## 7. Tests (what must fail on a broken build)
*   The code: alphabet, 6 characters, shown in groups, input normalised; single use; expiry at 5 minutes (a fake clock); a new code replaces the old; the cap and the sweep.
*   The bridge route: needs the token; a bad SteamID64 and a missing one are refused; both limiters.
*   The entry route: right code sets the cookie and redirects; wrong, used and expired codes do not and say the same thing; the address limiter and the whole-server limiter; a cross-origin POST is refused; a GET does nothing.
*   The cookie: forged, expired, and a game key or a session cookie presented as a voice cookie are refused; a blocked player and a non-admin player without `OPEN_SIGNIN` are refused; an admin's cookie gives `admin: false`.
*   **Reach:** with only the voice cookie, the voice page and its three routes work, and every other user route (the leaderboard's player page, the replay, the maps page, the admin API) still answer as for an anonymous visitor. The tiers test lists the routes and fails when one is added that takes the cookie.
*   The page: the entry form, its message, the forget button; in the style rules (no layout jump between the form and its message).
*   Lua: `stats_test.lua`-style test of the chat handler: the line is hidden, off when `traitordash_voice` is off, the answer is printed to the one player.

## 8. What cannot be verified here
The chat command and the printed line on a real server (hiding the command, the text's length in the chat); how long a friend's browser keeps the cookie in practice (a browser may clear it); whether a code typed in a phone's browser pastes as expected. The maintainer's test of a real game, a real friend and a real browser is the check.

## 9. As built (2026-11-13)
Built as designed (`services/voiceCode.ts`, `services/voiceSession.ts`, the routes in `routes/api.tsx` and `routes/auth.ts`, `!voice` in `voice.lua`, `VoiceEntryPage` in `components/VoicePage.tsx`). Where it differs or adds:
*   **Failure redirect.** A failed entry goes back to the voice page with `?code=failed`; the page prints only its own fixed message for that flag, never the query's text.
*   **Origin check is strict.** `/auth/voice-code` and `/auth/voice-logout` accept a post only with `Sec-Fetch-Site: same-origin`, or, without that header, an `Origin` of this site. A post with neither is refused (the general check lets a post without an Origin pass).
*   **Limits.** A server may ask for 20 codes a minute (ten players asking at a map change must not be refused); one code per player per 10 s is the store's own rule. The address limit (10 a minute) only applies where `TRUST_PROXY` gives an address; the 60-failures-a-minute limit applies always.
*   **Caching.** The voice page (with or without a session) is sent `no-store`, so the page shown after entering a code is never the cached entry form.
*   **No media server.** Without `LIVEKIT_*` the page keeps its old answer to a visitor without a session (a redirect), and `POST /api/v1/voice-codes` answers 503; in the game's window (`embed=1`) the old answer stays too.
*   **Address in the chat line.** `!voice` prints the public https address (`public_url`, as the role guide) when it is set, else the bridge's own address, which is often not reachable from a player's machine.
*   **Forget button** sits at the foot of the first card (only with the voice cookie as the sole session).
*   **Tiers.** The voice page stays `user`; the sweep test accepts the code form as its answer to a visitor. The new routes are `bridge` and `login`.
*   **Not verified here:** section 8 (a real game, chat line length and hiding, a real friend's browser keeping the cookie, a phone). The pages were checked in Chromium: no layout change between the form with and without its message (0 px at 1100 and 390 px), all text at least 5.3:1, no horizontal overflow at 390 px.

## 10. The short address (2026-11-13)
**Change.** `<address>/voice` is a public page with the code form and nothing else about a server. A code typed there leads to `/servers/<id>/voice` of the server that issued it. `!voice` now prints `Voice code R73-NND (5 minutes). Open <address>/voice in your browser and type it there.`

**Why.** The line with the server's own address (`<address>/servers/<uuid>/voice`) wrapped over three lines in the game chat on the real server and nobody could type it.

**What it does.**
*   The code store keeps `{ steamId, serverId, expires }`; the bridge route passes the server that asked; `redeem` gives back both. A code is therefore tied to the player and to the issuing server. The answer's `path` field stays (the page tests use it) but the chat line no longer prints it; the bridge still checks that the answer's code has the shape of a code and its path the shape of a path.
*   `POST /auth/voice-code` takes the code with or without a `to` field. A right code always leads to the issuing server's voice page, the cookie is set either way. This changes one thing: a code from server A typed on server B's entry page used to land back on B's page and now lands on A's (the page that can use it). A wrong, used or expired code, or a player who may not sign in, still gives one answer: back to the page the form came from with `?code=failed`, or to `/voice?code=failed` when the form had no `to` (or one that is not a voice page of this site). The `Sec-Fetch-Site` and `Origin` rules, both limiters, `no-store` and `no-referrer` are those of the existing route.
*   `GET /voice` (tier `public`) shows the code field, the fixed failure message in the reserved line, and a muted "No code? Say !voice in the game." It has no Steam sign-in link of its own (a sign-in needs a server page to return to; the site header's generic link stays), no section buttons and no server name. It looks the same whatever servers exist. Without a media server on the dashboard, and in the game's window, it redirects home as the per-server page does. A visitor who already has a session sees the form too; there is no server picker.
*   If the issuing server has been deleted, or has no voice, the redirect still goes to its voice page, which answers as it always does for that case; nothing special-cased.

**Not verified here.** The new chat line's length and wrapping on a real server, and a friend typing the short address on a phone.
