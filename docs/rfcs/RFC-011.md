# RFC 11: Exact Map Geometry from the Map File (opt-in, per map)

> **Status: draft.** Nothing is built. The spike in section 3.5 checked the download routes against a real 29-addon collection; what it settled and what it left open is there. It builds on [RFC 10](./RFC-010.md) (map inventory and trace-based floor plans), which stays the default for every map.

## 1. Abstract
RFC 10 measures a map's floors with ray traces: cheap, automatic, coarse. This RFC adds an **optional** second source for the maps where that is not good enough: the geometry stored in the map's own `.bsp` file. An administrator turns it on **per map** in the dashboard. The **backend then fetches the map itself**, the way players' game clients do, reads only the parts of the file that describe surfaces, and stores a compact mesh (floors, walls, ramps, stairs) next to the trace plan. The game server is not involved unless no public copy of the map exists, in which case it can send the needed parts itself. No map file is uploaded by hand, converted by hand or kept.

## 2. Motivation
*   **Traces are coarse.** RFC 10 section 4.4 lists the blind spots: a 64-unit grid misses ledges and thin walls, doors count as open, a crawl void under a floor is ambiguous, and nothing says where a wall *is*, only that a step was blocked.
*   **Some features need real geometry:** a good-looking replay background, a 3D view, line-of-sight or "who could see whom" analysis, wall-accurate heat maps.
*   **It cannot be the default.** Map files are 100-250 MB on the reference server (RFC 10, section 4.1); most of that is embedded content (textures, models, sounds) that is irrelevant here. Doing it for dozens of maps unasked would cost bandwidth and storage for little gain, hence opt-in per map.
*   **The backend does not need the game server to get the file.** Players' clients already download every map from somewhere public. The same source can be used here (section 3.2), which keeps load and new code off the game server.

## 3. Design

### 3.1 Opting in
*   The Maps tab (RFC 10, section 3.3) gets an **Exact geometry** switch per map and a status: *off*, *queued*, *fetching*, *parsed*, *failed (reason)*. Only an admin session with a same-site `Origin` can change it (RFC 7); the audit log records `MAP_GEOMETRY_REQUESTED` with the admin's SteamID.
*   Off is the default and there is no global "all maps" switch.
*   The **backend operator** also has a switch (`MAP_GEOMETRY=1`), off by default, because the feature makes the backend download hundreds of megabytes from the internet. Without it the switch in the dashboard is hidden and nothing is fetched.

### 3.2 Where the file comes from
The bridge's map report (RFC 10, section 3.1) gains a `source` per map, so the backend knows where a public copy lives. Three sources, tried in this order:

1.  **Workshop addon.** A mounted map addon has a Workshop ID, which the game exposes. The report lists the ID of the addon the map came from; the backend downloads that addon from the Workshop itself and extracts the map from it. **Default: a helper program, DepotDownloader, run as a separate process** (3.5, 4.1), which fetched every kind of item tested, anonymously. A download needs the *whole* addon (it is stored compressed as one file), so 100-250 MB once per opted-in map, on the backend, with no game-server load.
2.  **Download URL (FastDL).** If the server sets a download URL for its clients, the bridge reports it once. The backend fetches `maps/<name>.bsp` with HTTP range requests: the 1 KB header first, then only the whitelisted lumps (3.3), a few MB in total. Servers that publish the files compressed (the usual `.bz2`) cannot be range-read and count as "no download URL" here.
3.  **The game server (fallback).** For a map with neither (a private map, a file copied in by hand), the bridge reads the same whitelisted lumps from its own disk and sends the bytes in numbered, signed, size-bounded chunks (RFC 5, RFC 6), one map at a time, spread over ticks with a work budget like the scanner's (RFC 10, section 4.2). Only the header and the whitelisted lumps ever leave the server. This route is the only one that needs a bridge command (`map_geometry <name>`), which carries the map name only: the bridge resolves it against the maps it listed itself and never takes a path from the backend.

**The fingerprint.** Every map in the report carries a `fingerprint`: the SHA-256 of the lowercase hexadecimal text of the file's first **1036 bytes** (the whole header: the `VBSP` identifier, the version, the 64-entry lump directory with every lump's offset and length, and the map's revision number), followed by `:` and the file size in decimal. Hex text, because the raw bytes are not safe to pass around as a Lua string. The backend computes the same value from the file it fetched; the bridge's tests and the backend's share one test vector. The bridge computes it by reading 1 KB per map; the whole file is never read into the game. The backend uses it in three places:
*   **Identity.** A fetched file is accepted only if its own header hashes to the reported fingerprint. A Workshop addon that has since been updated, a download URL serving an older copy, or a different map of the same name is therefore rejected instead of parsed as if it were the server's map.
*   **Matching map to addon.** If the report cannot say which addon a map came from (below), the backend can try the candidate addons and keep the one whose `maps/<name>.bsp` has the right fingerprint. The check needs only the header of each candidate, not a full parse.
*   **Cache key.** Geometry is stored per `(map name, fingerprint)`, so two servers with the same map version share one row and a changed map version triggers a new parse, which the file size alone would not always catch.

Limits: the fingerprint covers the header, not the lumps' content, so an edit that keeps every lump's size and the revision number would go unnoticed. That is accepted: it would be a map re-saved without recompiling, and the cost of hashing the lumps on the game server is not justified. A full-file hash is likewise not asked of the game server; the backend may hash a file it downloaded completely, for its own bookkeeping.

**Checked by the spike (3.5):** both facts below were open when this was first written.

**Originally unverified:**
*   whether the backend can download a Workshop addon for this game without an account, and how (the Workshop's public download interface, or a command-line Steam client run anonymously), and what that adds to a deployment;
*   which Workshop addon a given map came from. The game lists mounted addons and their IDs, and tags them as maps, but does not obviously say which map file belongs to which addon. If it cannot, the backend resolves it by content (open each candidate addon's file list and look for `maps/<name>.bsp`).

### 3.3 Reading and parsing (backend)
A `.bsp` starts with a header holding a directory of 64 *lumps* (offset and length of each part). Only the lumps that describe surfaces are needed: vertices, edges, surface edges, faces, planes, texture info (to leave out sky, triggers and the like), the displacement records and their vertices, and the brush-model table (to tell the world from doors and lifts). The embedded content lump, by far the largest, is never read.

*   A small reader for these lump formats, written for this project: the format is publicly documented and the needed part is a few hundred lines. An existing library may be used instead after its licence is checked and recorded here; no code is copied without that.
*   Output is a **mesh of walkable and blocking surfaces**: faces whose normal points mostly up (floors, ramps, stair treads) and faces that stand upright (walls), as triangles with integer coordinates in map units, grouped per level. It is simplified, not the full render geometry: no textures, no props, no hidden or sky faces. **The stored format is glTF 2.0 in its binary form (GLB), an existing standard, not a format of our own** (3.6).
*   The parse runs off the request path (a worker), with a time and memory ceiling. The downloaded file is deleted as soon as the mesh is stored: only the mesh is kept, as one compressed blob per `(map name, fingerprint)`.
*   The trace plan from RFC 10 is kept. The dashboard prefers exact geometry when present and falls back to the plan, so a failed fetch or parse never leaves a map without a background.
*   Lumps the engine stores compressed are not handled in the first version (section 9).

### 3.6 The format, and what draws it in the browser
**Format: glTF 2.0 (GLB).** It is the open Khronos standard for 3D meshes ("the JPEG of 3D"), it holds indexed triangles, a scene graph with named nodes, materials and free-form metadata (`extras`) in one file, every serious viewer and converter reads it, and it has standard compression extensions if size ever matters. A format of our own would need its own writer, reader, documentation and viewer.
*   **Writing it:** `@gltf-transform/core` (MIT, one small dependency). **Checking it:** the Khronos reference validator `gltf-validator` (Apache-2.0) as a development dependency: the tests require **0 errors and 0 warnings**.
*   **Structure:** one scene; a root node that rotates Source's Z-up into glTF's Y-up and carries the map name, the fingerprint and the units in `extras`; **one node per level** (RFC 10's storeys, found with the same rule, weighted by area) with its height range in `extras`, each with a `floors` and a `walls` primitive (two materials), so a viewer can show or hide a level and tell floors from walls. Coordinates stay whole Source units; no scaling is baked in.
*   **Measured (2026-10-19) on the real `ttt_diescraper`:** a GLB of the cropped playable area is **326 KB, 145 KB gzipped** (17 000 vertices, 19 700 triangles), against 708 KB as a bare float list; it passed the Khronos validator with no errors and no warnings. The only notes were 23 degenerate triangles produced by rounding coordinates to whole units, which the writer drops. Compression extensions (`EXT_meshopt_compression`, MIT) are not needed at this size and are left as an option.
*   **The 3D skybox is removed, and only that.** A map's world model also holds the **3D skybox**: a small scaled copy of the surroundings built far from the map, marked by a `sky_camera` entity inside it. Drawn with the map it was a 15 000-unit slab next to a speck (the first render). **Two ways of cropping were tried on the 28 maps of the reference collection and one was rejected:** cropping to the box around the spawn points plus a margin kept **28 of 54 351 triangles** of `ttt_lttp_kakariko`, 9% of `ttt_minecraft_haven` and 20% of `ttt_waterworld_tropical` (their spawns sit in a corner of the play area; one map has no spawn entities at all), so it is **not used**. What is used: geometry is grouped into **pieces** (cells of 1 024 units, neighbouring cells joined); a piece that holds a `sky_camera` and **no spawn point** is the skybox and is removed. It never guesses: if the skybox is joined to the map there is nothing to separate and nothing is removed, and if the pieces to remove are more than half of the triangles nothing is removed. **Measured:** it removes 0.1% to 18% of the triangles on the 9 maps where the skybox is a separate piece and nothing on the other 19; on `ttt_diescraper` it removes 4.4%, and what is left matches the **independent** crop to the trace plan's bounds almost exactly (19 670 and 19 673 triangles). A crop to a plan's bounds (RFC 10) stays available as an option for a map that has a plan.
*   **The whole collection through the writer (2026-10-19).** Every map of the reference collection was read, cleaned of its skybox and written as a GLB: **28 of 28 are valid by the Khronos validator (0 errors, 0 warnings)**, are **83 to 1 034 KB (35 to 449 KB gzipped)**, have 1 to 7 levels, and take **22 to 185 ms** in all. The real `ttt_diescraper` GLB was loaded and drawn by three.js, and hiding the level nodes above level 3 gave a cutaway of the lower storeys.

**What draws it in the browser.** The project's front end is server-rendered pages with a small bundle (HTMX, Alpine); no React. So:
*   **The round replay (RFC 12) is drawn by the same three.js, on this mesh when it exists.** The replay is a three.js scene: the map's GLB as the background (one node per level, so levels can be hidden or cut away), a marker per player in the same coordinates, and cameras for orbit, top-down (an orthographic camera, which is the 2D replay as a camera mode) and follow. A map without exact geometry gets the same viewer with its RFC 10 floor plan drawn as flat tiles.
*   **The 3D view and the replay use three.js** (MIT) with its `GLTFLoader` and `OrbitControls`: the de-facto web 3D library, loads exactly this GLB, and has everything a viewer needs (orbit, clipping planes to cut away upper levels, instancing for the players, picking). **Measured:** a bundle of just the parts needed (renderer, scene, camera, lights, `GLTFLoader`, `OrbitControls`) is **641 KB minified, 159 KB gzipped**, loaded only on the pages that need it and cached afterwards. **Proven:** the real `ttt_diescraper` GLB was loaded and drawn by it in a headless Chromium (a software WebGL renderer): the building shows with its roof, walls and several storeys.
*   **Considered and not chosen:** Google's `<model-viewer>` web component (easiest to embed, but it is a viewer, not a toolkit: no overlays such as player dots or a timeline, no custom clipping); Babylon.js and PlayCanvas (larger and aimed at games and editors); react-three-fiber (needs React); raw WebGL (reinventing the wheel); map libraries such as MapLibre or deck.gl (made for geographic data).
*   **Who may fetch the mesh.** `GET /servers/<id>/maps/<map>/mesh.glb` needs a **signed-in user** (RFC 13: any Steam account, rate limited per account; admins are a subset), and so does the 3D viewer. The floor-plan pictures of RFC 10 are unchanged.
*   **No renderer of our own.** The code written for display is the replay's markers, timeline and cameras on top of three.js, which is the feature itself.

### 3.4 Data model (proposed, migration v11)
```sql
CREATE TABLE map_geometry (
  map_name   TEXT    NOT NULL,
  fingerprint TEXT   NOT NULL,   -- sha256 of the header + lump directory, plus the size (3.2); a changed map version is a new row
  source     TEXT,               -- workshop | download-url | game-server
  status     TEXT    NOT NULL,   -- queued | fetching | parsed | failed
  detail     TEXT,               -- the failure reason, never file content
  mesh       BLOB,               -- the mesh as a GLB (glTF 2.0 binary), NULL until parsed
  created_at INTEGER NOT NULL,
  PRIMARY KEY (map_name, fingerprint)
);
ALTER TABLE server_maps ADD COLUMN geometry_requested INTEGER NOT NULL DEFAULT 0;
ALTER TABLE server_maps ADD COLUMN source TEXT;   -- the JSON of section 3.2, as reported
```
Geometry is a property of the map file, not of a server, so servers with the same map name and fingerprint share one row; "requested" is per server.

### 3.5 Spike results (2026-10-19)
Run against the 29-addon Workshop collection of the reference server, from an ordinary machine with no Steam account.

*   **Two ways to download, both anonymous.** The public Workshop API (no key) lists each item with its size and, for **18 of 29**, a direct `file_url`. The other **11** (including the largest: 244, 252, 149 and 137 MB) have none and can only be fetched through Steam's content system. The command-line Steam client run anonymously fetched one such item (the 244 MB one) in about 20 s, but it is a 32-bit program (see the hosting constraint). A JavaScript client library (`steam-user`, MIT) and a native helper (DepotDownloader, GPL-2.0) can both do it too; the later bullets compare them, and the decision is at the end of this section.
*   **Two container formats.** A `file_url` download (and the helper, for a legacy item) is an addon archive compressed as a whole with LZMA (no range reads possible; 3.3 MB for a 21 MB map); the Steam client route delivers the plain, uncompressed archive. The backend must handle both (an LZMA decoder, then the addon archive format: a header, a file table, then the file bytes in order). Both were parsed here with a few dozen lines.
*   **The fingerprint works.** The map inside each archive had exactly the size the game server reported (22 095 766 and 243 312 804 bytes), with `VBSP` version 20 and a readable revision number (320 and 904). Matching a map to its addon by header fingerprint is therefore workable. The game server's own computed fingerprint was then compared with these and is **identical** for both maps (verified on the real server once the bridge side existed).
*   **The surface lumps are tiny.** Without the embedded-content lump, the needed parts are **2.7 MB of 21 MB** and **1.1 MB of 232 MB**. The embedded-content lump is 220 MB of the 232 MB (95%), which is why a range-read from a download URL, where available, would be worth it. None of the lumps checked was compressed.
*   **Resource limits.** Pelican limits memory and disk per server. A 250 MB addon must be streamed to disk and deleted, not held in memory; a whole-file LZMA decode (legacy items) has to be checked against the memory limit too. Not yet measured.
*   **The reader, on the real file (2026-10-19, steps 1 and 1b built).** `extractSurfaces` read the 243 MB `ttt_diescraper` through a file-backed byte source in **8 range reads, 1.25 MB, 20 ms**, and refused nothing. The map has 6 666 faces in its world model: 2 536 floors, 3 908 walls, 47 ceilings (dropped), 170 skipped (sky, nodraw, triggers), **5 displacements** and 676 more faces on doors and lifts (other brush models, excluded). Its fingerprint is the one the game server reported. **Against the trace scan of the same map** (section 7's check), before displacements were drawn: of the 1 499 floors the scan found, 89% lay on a parsed floor face within 16 units and 98% within 64.
*   **Displacements (terrain), drawn.** A displacement is the face's four corners plus a grid of (2^power + 1)^2 vertices, each pushed along its own direction; the reader interpolates the grid across the quad from the corner nearest the record's start position, pushes every vertex, splits each cell into two triangles (the diagonal alternating like a chessboard) and classifies each triangle by its own slope, using the face's plane to say which way is out (so the order of the corners and the side of the plane do not matter). On `ttt_diescraper` the 5 displacements make 640 triangles (636 of them floors, all at heights 480-512). **Checked against the scan:** of the scanned floors at that level that lie under one, 58 of 114 agree with the displacement's height **within 2 units** (2 more within 8); the other 54 are all off by almost exactly 32 units, i.e. a second floor layer below the displacement, not a placement error. Power 2 to 4 is read; anything else is refused.

*   **The whole collection (2026-10-19).** The reader was run on **every map of the reference server's Workshop collection**, downloaded with DepotDownloader (28 maps in 29 addons; the 29th is a navigation-mesh addon without a map): **28 of 28 parsed, none refused**. All are version 20. Per map the reader took **0.4 to 3.4 MB (of 9-252 MB) and 1 to 111 ms**. The terrain-heavy map `ttt_alps` has 1 085 displacements (37 600 triangles, 111 ms, the slowest); `ttt_67thway_rework_b1` has the most displacement triangles (46 592 from 94 displacements); eight maps have none. A world model has 1 900 to 20 000 faces.
*   **Not tested:** maps that bundle several `.bsp` files, FastDL, how Steam's anonymous access behaves at volume (rate limits), maps older than version 19 or newer than 21, and compressed lumps (none was compressed in the 28 maps).
*   **Hosting constraint.** The project's only supported hosting today is the [Pelican egg](../../pelican/README.md), which runs inside a container and has **no container runtime and no access to a Docker socket**, and which must not be changed to get one. The command-line Steam client therefore has two strikes against it there: it needs 32-bit system libraries that the backend image does not carry, and the wrapper libraries that make it convenient (for example `steam-workshop-ts`, which spawns the client and parses its output) can sandbox it only through Docker. A pure-JavaScript client (`steam-user`) and a self-contained native binary (DepotDownloader, below) avoid both.
*   **`steam-user` under Bun needs a small patch.** Run unmodified under the backend's runtime (Bun 1.4.3), the same download failed: the manifest's file name came back truncated and the chunks failed with `VZip: Didn't see expected footer`. Cause, found in five experiments: the library's crypto helper (`@doctormckay/steam-crypto`, a dependency) decrypts with the stream idiom `decipher.end(data); decipher.read()`, and Bun returns only the blocks before the last one (32 of 40 bytes in the reduced test) where Node returns all of them. Replacing the two decrypt functions with `update()` + `final()` fixes it: the patched run under Bun was **byte-identical** to the Node run for both the 2.4 MB and the 244 MB item. The patch is about 20 lines applied at start-up by replacing the two exported functions (no change to files in `node_modules`); it should also be reported upstream to Bun.
*   **`steam-user` memory.** The library writes each chunk to disk as it arrives (4 parallel workers, about 1 MB chunks), so the data itself is not held. Measured on the 244 MB item: Bun peaked at about **890 MB** resident, Node at about **685 MB**, but Bun with a garbage collection forced once a second peaked at about **330 MB** (103 s). So most of the peak is garbage that is not collected in time, not live data; the likely source is the library's pure-JavaScript decompression of every chunk into plain number arrays, though the function was not profiled. A periodic forced collection while a download runs is a cheap mitigation; whether about 330 MB fits the egg's memory limit is open.
*   **A native helper is much lighter.** DepotDownloader (a .NET program, published as a self-contained Linux binary of 79 MB, 33 MB zipped) fetched the same 244 MB item anonymously with `-app 4000 -pubfile <id>`: **7 s, about 149 MB peak memory, output byte-identical**. It also fetched a legacy item (one that has a direct link) in 1 s with 84 MB, byte-identical to the direct download, so **one tool covers all 29 addons**. It needs no 32-bit libraries and no container runtime, so it fits the hosting constraint. Costs: it is **GPL-2.0**, which is acceptable here (see 4.1); a 79 MB larger image; it is untested on a minimal base image (system libraries such as a TLS library may be missing); and it is a separate project to track, as `steam-user` is. The other non-JavaScript option found, `steamctl` (Python, MIT, can download Workshop items), has not been updated since December 2023 and was not tested.
*   **Decision: DepotDownloader is the default** for the Workshop source: faster (7 s against 73-103 s), a quarter of the peak memory of `steam-user` with forced collection (150 MB against 330 MB; 890 MB without), no patch, and it works for all 29 addons. `steam-user` stays documented as the alternative for an operator who cannot ship a GPL binary, with the Bun patch and forced collection described above; it is not built unless asked for. The direct HTTPS download that 18 of 29 items offer is **not** used: the helper is as fast for them (1 s for the small item tested), and a second route would add a second fetch path to secure and test, for a gain of nothing; on an install without the helper the feature reports "helper missing" instead of working for only some maps.
*   **Addon container formats.** The helper delivers a plain archive for current items and an LZMA-compressed one for legacy items (the same bytes a direct link gives); the backend decodes both, and an LZMA decoder (a library or the system `xz`, present in the image or not) is an implementation detail to settle.
*   **The cost** of the `steam-user` route is a runtime dependency on a library that follows Steam's undocumented protocol: it can break when Valve changes it, and it is a maintained third-party package of several MB with many dependencies. DepotDownloader follows the same protocol (it is built on the SteamKit library from the same GitHub organisation) and was updated this month, but the same risk applies.

## 4. Security Considerations
*   **The backend fetches addresses a game server told it about.** This is a server-side request forgery risk: a compromised or hostile bridge could name an internal address. Therefore: the Workshop route uses only a numeric ID, which is handed to the helper (the backend itself makes no request for it), never a URL from the bridge; a download URL must be `https` (or `http` only to a public address), is resolved first, and is refused if it points at a private, loopback or link-local address, **including after each redirect** (redirects are limited and re-checked); the request carries no credentials and no cookies; timeouts and byte caps apply to every fetch.
*   **The file is untrusted input.** Workshop maps are third-party content. Every offset, length and count is checked against the file size before use; counts are capped (vertices, faces, displacement grids); parsing is iterative with no recursion driven by file content; a file that fails any check is rejected whole, with a short reason and nothing partial stored.
*   **Bounded resources.** A cap on bytes per download, a limit on concurrent fetches and parses, a time and memory ceiling for the worker, a scratch directory that is cleaned on completion and on startup, and a limit on requests per server. A server cannot use this to fill the disk or the network. Range reads count only the bytes actually received.
*   **Third-party content.** Only the derived mesh is stored; the map file and the addon are deleted after parsing. The Workshop route is the operator's decision (3.1), because it means downloading content under the platform's terms; the RFC does not decide that for them.
*   **Authorization.** Only an admin requests a parse. For the fallback route only the paired server's bridge uploads for itself, with the usual token and signature, and cannot write geometry for another server's request.
*   **Privacy.** The game server's download URL is public by nature (every player is sent to it). Embedded map content is never read, and on the fallback route never leaves the server.

### 4.1 Licensing of a bundled helper
This project is MIT licensed; the helper in 3.5 (DepotDownloader) is GPL-2.0. This section records the reasoning, which is **not legal advice**.

*   **A separate program is an aggregate.** The FSF's GPL FAQ says an aggregate is "a number of separate programs, distributed together on the same CD-ROM or other media", that the GPL permits creating and distributing one "even when the licenses of the other software are nonfree or GPL-incompatible", and that the only condition is not to license the aggregate so as to take away the rights each programme's own licence gives. It says the line between one program and two depends on the mechanism of communication and on its semantics, and that "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs"; communication exchanging "complex internal data structures" could point the other way. It also says that putting the code in containers "does not change the analysis". The FAQ itself says the boundary is "a legal question, which ultimately judges will decide".
*   **How this design stays on the safe side.** The backend starts the helper as a **separate process** with command-line arguments (an application ID, an item ID, an output directory) and reads a file it wrote. It does not link the helper, does not load it into the backend's process and does not exchange internal data structures. The helper is **unmodified**, so no changes need publishing.
*   **MIT is GPL-compatible, but only one way.** MIT code may be combined into a GPL program (the result is GPL); GPL code cannot be relicensed as MIT. Keeping the helper a separate process is what keeps the backend MIT. **Do not embed the helper's code in the backend** (as a library, or by loading it into the same process): that would make the combined backend subject to the GPL.
*   **What stays MIT.** The backend, bridge and docs keep their licence. The container image is the aggregate: the helper keeps its GPL-2.0 and its licence text must travel with it.
*   **What distributing it brings.** Shipping the helper's binary means offering its **corresponding source** under the GPL: the image (or the project) includes the licence text, names the exact upstream version, and points to that version's source (a written offer or a link to the upstream release, which for an unmodified upstream release is how many projects comply). The image documentation lists the helper and its version. Community discussion points out that this is harder for layers inherited from a base image, which this RFC does not change.
*   **A lighter variant.** The image need not contain the binary at all: the backend can download the upstream release at first use, when the operator enables the feature. Then the project distributes no GPL code, though the operator's installation holds it. That needs the egg to fetch a release at first start, which it does not do today (that is a separate design decision), so this RFC assumes the binary ships in the image.
*   **To confirm before building:** the exact licence terms of the release used (the licence text shipped with it is GPL version 2; whether files carry "or any later version" notices was not checked), and the licences of what the self-contained binary bundles (the .NET runtime and libraries are separate licences, mostly MIT).

## 5. Dashboard Changes
*   The per-map switch and status in the Maps tab (3.1), with the failure reason and the source used.
*   Anything that draws a map (RFC 10's later viewer) shows exact geometry when parsed and the trace plan otherwise, and labels which one it is showing.

## 6. Compatibility and Rollout
*   Additive and off by default: with no map opted in, and without the operator's switch, nothing changes and no new traffic appears. A bridge without `source` in its report gives a status of *failed (no known source)*; an old bridge never receives the fallback command (an unknown command type is ignored, RFC 6) and the dashboard says the server must be updated.
*   Delivered in order: (0) the spike (done, section 3.5); (1) the backend reader and its tests on synthetic files, which need no network and no game server; (2) storage and the worker; (3) the Workshop and download-URL sources; (4) the dashboard switches; (5) the game-server fallback, only if the first sources prove insufficient.

## 7. Testing
*   **Backend reader (tests first):** a small test map is built by the tests themselves (a header, a lump directory and a handful of faces), so no copyrighted map is committed. Cases: a flat floor, a ramp, stairs, a wall, a displacement; the same map twice yields the same mesh; the world is told apart from a door's brush model.
*   **Hostile input:** truncated file, lump offset past the end, lump overlapping the header, huge counts, a wrong version, a lump marked compressed, zero faces, NaN-like coordinates. Each is rejected without crashing or storing anything.
*   **Fingerprint:** a file whose header differs by one byte (revision, a lump length) is rejected as a different map; identical headers are accepted; the same map under two names yields the same fingerprint; the bridge's value and the backend's value agree for the same bytes (one shared test vector, in both test suites).
*   **Fetching, against a local fake server:** range reads fetch only the header and the whitelisted lumps; a server that ignores ranges is detected and stopped at the byte cap; a redirect to a private address is refused; a download URL that resolves to a private address is refused; timeouts; a compressed file is reported as unsupported; the downloaded file is deleted on success and on failure.
*   **Limits:** the byte cap, concurrent fetches and parses, the worker's timeout, the scratch directory cleanup.
*   **Bridge (Fengari, fake file API), for the fallback route:** only whitelisted lumps are read, nothing outside the header's lump directory, chunk numbering and size, a refusal for a map the bridge did not list, and the tick budget. For the other routes: the report names the addon ID and the download URL and no more.
*   **Real server:** a parse of the reference map compared with the RFC 10 trace plan: every trace-reachable cell should lie on or near a parsed floor face.

## 8. Alternatives Considered
*   **The game server uploads the map (the first version of this RFC).** Works for any map source but puts file reading and chunking on the game server and needs a transport that does not exist yet. Kept only as the fallback (3.2).
*   **Upload the whole map file.** 100-250 MB per map; rejected.
*   **Parse in Lua on the game server and upload only the mesh.** Smallest transfer, but heavy work on the game thread and a parser that can only be fixed by redeploying every addon.
*   **A manual converter** an admin runs on a PC. Violates the no-manual-action requirement.
*   **Collision brushes instead of render faces.** Closer to what the engine collides with, but turning planes into surfaces needs constructive-solid-geometry work that the render faces already did.
*   **steamcmd or a wrapper around it** for the 11 maps. Needs 32-bit libraries (or Docker, which the hosting rules out); DepotDownloader does the same job without either.
*   **A third-party map-viewer library as a dependency.** Possible for the reader (3.3); a decision after a licence check.

## 9. Open Questions
*   **Minimal image.** DepotDownloader was run on a development machine, not on the minimal image the egg uses. Which system libraries does it need there (TLS, ICU or invariant globalization), and does it start with a read-only or small temp directory?
*   **Fingerprint agreement: settled.** The game server's value and the value computed from the downloaded file are identical for both maps tested (2026-10-19, see RFC 10 section 7). What is left is the shared test vector in both test suites.
*   **Compressed lumps.** Some map builds compress lumps. Decompress them in the backend, or answer "not supported"?
*   **Doors, lifts and other brush entities.** Include them as separate groups, or leave them out as RFC 10 does?
*   **Props.** Static props are not part of the surface lumps; stairs and ramps made of props would be missing. Acceptable, or add their bounding boxes?
*   **Size of the mesh.** Is a per-map cap needed? A GLB of the test map is 326 KB; the largest maps in the collection have about 5 times the triangles. Is mesh compression (`EXT_meshopt_compression`) worth adding, or does gzip over HTTP do?
*   **Skyboxes that are joined to the map.** On 19 of the 28 maps there is no separate skybox piece to remove (no `sky_camera`, or its piece shares the map's), so the mesh keeps whatever the map has there. Is that acceptable, or should those maps also be cropped to a plan's bounds when a plan exists?
*   **Fallback transport.** If the fallback is built, do the existing bridge request limits suffice, or does it need a dedicated endpoint with a higher cap?
