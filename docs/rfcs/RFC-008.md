# RFC 8: Bridge Configuration File

> **Status: implemented in the bridge** (`config.lua`, `bridge.lua`, `stats.lua`). Not yet done: provisioning tools writing the file and the later removal of their `server.cfg` lines (section 6), (the pairing command of [RFC 9](./RFC-009.md) now writes the file). Differences from the first draft are noted in section 4.1.

## 1. Abstract
The TraitorLink Bridge learns where the backend is (`traitordash_url`) and how to authenticate (`traitordash_token`) from two ConVars set in `server.cfg`. This RFC moves both into a dedicated configuration file in the server's data folder, keeps the ConVars as a fallback so no existing installation breaks, and gives the bridge a single place to ask "am I configured, and where from?". [RFC 9](./RFC-009.md) builds on it: pairing is a way to *write* this file without anyone copying a token.

## 2. Motivation
*   **The token sits in the most shared file on a server.** `server.cfg` is the file owners paste into support threads, commit to repositories, copy between servers and include in backups. A server token is a credential: with it anyone can read that server's command queue and report data on its behalf.
*   **Configuration is scattered.** Four places read the ConVars directly (`GetApi`, `IngestRole`, `Poll`, `traitordash_status`), and `stats.lua` reaches them through `TrustedBaseUrl`. Anything that has to change about *how* configuration is found (this RFC, RFC 9, a future Workshop install) has to be changed in each of them.
*   **An unconfigured bridge is silent.** An empty token makes `Poll` return without a message, and the default URL `http://localhost:3000` is quietly polled on a fresh install. A single accessor is the natural place to report what is missing (RFC 9 and the install guide rely on this).
*   **Provisioning tools overwrite lines.** Provisioning tools (configuration management, container images, hosting panels) have to edit two lines inside a file they do not own. A file owned entirely by TraitorDash can be written whole and atomically.

## 3. The File

### 3.1 Location and format
`garrysmod/data/traitordash/config.json`, read with `file.Read("traitordash/config.json", "DATA")`:

```json
{
  "url": "https://traitordash.example.com",
  "token": "…64 hex characters…"
}
```

*   JSON, because the bridge already has `util.JSONToTable` and the backend, provisioning tools and the pairing flow can all produce it without a Lua-specific format.
*   Unknown keys are ignored (room for later settings). `url` and `token` must be strings; anything else is treated as "not set".
*   `data/` is the one directory Lua can read and write at runtime. It is not part of the files a connecting client downloads (it is neither mounted for FastDL nor sent as part of the server's content), and, unlike the `cfg` folder, it is not something owners habitually share.

### 3.2 Precedence
For each setting independently:
1.  the value in `config.json`, if it is a non-empty string;
2.  otherwise the ConVar (`traitordash_url`, `traitordash_token`).

The file wins, because it is the newer mechanism and the one RFC 9 writes: after pairing, a stale `server.cfg` line must not silently take over again. When both are set and differ, the bridge prints one line at init (`config.json overrides traitordash_url from server.cfg`) and never prints the token.

### 3.3 When it is read
*   at init, before the first poll;
*   when the `traitordash_reload` console command runs (superadmin only, like the other commands), which re-reads the file and resets the warn-once flags;
*   after the bridge itself writes the file (RFC 9).

It is not re-read on every poll: a poll every 10 seconds must stay free of disk I/O. Hand-editing the file therefore needs `traitordash_reload` (or a restart).

## 4. The Accessor
One function owns the lookup, so no other code touches the ConVars again:

```lua
-- Returns { url = <trusted, cleaned base URL or nil>, token = <string or ""> , source = "file" | "convar" | "none" }
TraitorDash.GetConfig()
```

*   `url` has already been through `TraitorDash.TrustedBaseUrl` (https or private/loopback only, trailing slashes removed, warn once).
*   Every sender (`bridge.lua` poll, ingest, values, lang; `stats.lua`) calls `GetConfig()` and idles quietly when `url` is nil or `token` is empty, exactly as today.
*   `GetConfig()` caches the parsed file; it does no disk I/O after the load in 3.3.

### 4.1 Reporting what is missing
Because the accessor knows *why* a bridge is idle, init prints one actionable line instead of nothing:

| State | Message (once) |
|---|---|
| no token anywhere | `Not configured: no token. Create a server in the dashboard and put its token in data/traitordash/config.json (or set traitordash_token in server.cfg).` (once RFC 9 exists, this points to `traitordash_connect`) |
| no URL anywhere | `Not configured: no dashboard URL. Set "url" in data/traitordash/config.json (or traitordash_url in server.cfg).` |
| URL refused | the existing transport warning (https or a private address) |
| file unreadable or invalid JSON | `data/traitordash/config.json is not valid JSON; using server.cfg values.` |

`traitordash_status` prints the same information: configured or not, whether each value came from the file or a ConVar (`URL: https://… (from file)`), a refused URL with the reason, the token's length (`Token: set, 64 characters (from file)`, never the token) and the existing "Last Heartbeat" (time of the last successful poll). A file that overrides a ConVar somebody set in `server.cfg` is mentioned once at init, by name only (a ConVar left at its shipped default or empty is not "set").

*As built:* the accessor also returns `rawUrl` (the URL as configured, so status can say what was refused), `urlSource`/`tokenSource` (`file`, `convar` or `none`) and an overall `source`. The status line does not report whether poll answers verified; that stays in the poll's own log lines (RFC 6, section 2.3). `traitordash_reload` re-reads the file only; it does not re-run the startup sync (open question 1 answered: no).

## 5. Writing the File
*   **By hand or by a provisioning tool:** write the whole JSON file in one step, with mode `0600`, owned by the user the game server runs as, and keep the token out of logs and command output. Once the file is in place, the two `server.cfg` lines can be removed.
*   **By the bridge (RFC 9):** `file.CreateDir("traitordash")` and `file.Write("traitordash/config.json", json)`. Lua cannot set permissions, so the file has whatever mode the game process's umask gives it; see 7.
*   The bridge never writes the file except as the result of an explicit pairing.

## 6. Migration
1.  **Release N:** the bridge understands the file; the ConVars keep working; nothing is removed. Provisioning tools may start writing the file and leave `server.cfg` alone.
2.  **Release N+1:** provisioning tools remove the two `server.cfg` lines. The ConVars stay in the bridge as a fallback.
3.  **Later, separately:** deprecate the ConVars with a one-line console notice. This RFC does not remove them.

Nobody has to do anything on upgrade. The only visible change for an existing owner is the init line from 3.2 if they also create a file.

## 7. Security Considerations
*   **Not a stronger secret store than a ConVar against code on the server.** Any Lua addon running on the server can `file.Read` the data folder, just as it can `GetConVar("traitordash_token")` today. The gain is against *accidental disclosure* (pasted or committed configuration, backups of `cfg`), not against a hostile addon. This is stated here so nobody expects more.
*   **File permissions.** Provisioned files are `0600`. A file the bridge writes inherits the process umask (often `0644`); on a shared host that means other local users could read it. The install guide should say so, and the bridge documents how to tighten it. The container model of Pelican (one uid per server) makes this moot there.
*   **Never logged.** The token is never printed, not even partially; status shows only whether it is set and how long it is.
*   **No new network surface.** This RFC adds no endpoint and does not change what is sent or verified (RFC 6 is untouched).
*   **FCVAR_PROTECTED ConVars stay protected.** They still hide their value from `cvarlist` and from clients; the file does not weaken that for installs that keep using them.
*   **Failure mode is closed.** A missing or corrupt file never produces a default token or URL: the bridge falls back to the ConVars, and with none it stays idle.

## 8. Testing
In the existing Fengari harness (a fake `file` library with an in-memory `DATA` store):
*   file only, ConVar only, both (file wins), neither;
*   a file with only one of the two keys falls back per setting;
*   invalid JSON, wrong types, empty strings fall back and warn once;
*   an untrusted URL in the file is refused exactly as one from a ConVar;
*   `traitordash_reload` picks up a changed file and does not spam;
*   no sender reads a ConVar directly any more (a test greps the bridge for `cv_token:GetString`/`cv_url:GetString` outside the accessor);
*   the token never appears in any printed line, whatever the configuration.

## 9. Alternatives Considered
*   **Environment variables.** GMod's Lua has no `os.getenv`; not possible.
*   **Launch parameters** (`+traitordash_token …`, filled from a Pelican egg variable). This would keep the token off disk, but ConVars created by Lua after the engine parsed the command line may ignore the value. Unverified; worth a test on a real server before relying on it, and it would not help non-Pelican installs.
*   **A setup console command only** (`traitordash_setup <url> <token>`). Convenient, but the token ends up in the console history and logs; it would only write the same file, so it can be added later on top of this RFC.
*   **Keep ConVars, document better.** Cheapest, but leaves the token in `server.cfg` and the scattered reads in place.
