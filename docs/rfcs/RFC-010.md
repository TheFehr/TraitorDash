# RFC 10: Map Inventory and Map Floor Plans

> **Status: draft.** Two prototypes exist and were run against a real server (`addon/lua/traitordash/maps.lua`, `mapscan.lua`, `tools/render-mapscan.ts`); this RFC states what is kept, what is proposed and what is left open. Nothing in the backend exists yet.

## 1. Abstract
The dashboard knows a server's players, rounds and roles, but not its **maps**. This RFC adds two things, in this order:

1. **A map inventory:** which maps a server has, and which of them it will actually play ("votable") right now.
2. **Map floor plans:** a coarse, automatically measured plan of each map's walkable floors, so later features (a 2D round replay, heat maps, positions on a map) have a background without anyone drawing or exporting anything.

The inventory is needed first and is small. The floor plan is a separate, optional step with its own cost and limits. The replay viewer itself is **out of scope** and gets its own RFC.

## 2. Motivation
*   **"Which maps exist and are active?" has no single answer in GMod.** Maps live on disk and in mounted addons; the gamemode declares a name pattern; the map cycle file may be empty; a map-vote addon decides in its own way. Any feature that talks about maps (per-map statistics, a replay picker) needs one consistent list.
*   **No manual work.** A background image per map would have to be produced by someone, for every map, and again whenever a map updates. Servers run dozens of Workshop maps. The requirement is: no administrator action beyond running one console command once per map, and ideally none at all.
*   **Evidence from a real server** (a TTT server with 28 Workshop maps and the standard vote addon):
    *   30 maps on disk: 28 matching the gamemode pattern `^ttt_`, plus two built-in ones.
    *   The map cycle file was **empty** (the vote decides), so the cycle cannot be the source of truth.
    *   The vote addon's loaded configuration held only three settings (`MapLimit`, `TimeLimit`, `AllowCurrentMap`); the map prefixes were only in its data file, which was months old. Live ConVars disagreed with `server.cfg` (the vote limit was 12, the config file said 9), so something changes settings at run time.
    *   A floor scan of one map took **0.1 s over 27 server ticks, slowest tick 3.5 ms**, 14 637 traces, and produced about 55 KB.

## 3. Map inventory

### 3.1 What the bridge collects
A new console command, `traitordash_maps` (superadmin or server console), builds the report below and writes it to `data/traitordash/maps.json`. The same function feeds the backend (3.3).

```jsonc
{
  "current": "ttt_example", "next": "ttt_other", "gamemode": "terrortown",
  "pattern": "^ttt_",                    // the gamemode's declared map pattern, if any
  "maps": [
    { "name": "ttt_example", "size": 243000000,
      "fingerprint": "ab12...",           // sha256 of the first 1 KB (header + lump directory) with the size; see RFC 11
      "matchesGamemode": true,           // nil when there is no usable pattern
      "inCycle": false, "onCooldown": false, "isCurrent": true,
      "inVotePool": true, "votable": false }
  ],
  "cycle":   { "file": "cfg/mapcycle.txt", "maps": [], "missing": [] },
  "mapvote": { "present": true, "configSource": "merged",   // merged | global | file | none
               "poolBasis": "prefixes",                      // prefixes | gamemode | absent
               "prefixes": ["ttt_"], "config": {}, "convars": {}, "recent": [] },
  "addons":  { "mounted": 29, "maps": 29 }
}
```

### 3.2 What "active / playable" means
No signal is authoritative on its own, so the report carries all of them and **derives** two flags per map:

*   **`inVotePool`:** the map starts with one of the vote addon's prefixes. If no prefixes are known anywhere, the gamemode's pattern decides instead. `poolBasis` records which rule applied, so a pattern match is never mistaken for a vote setting. With neither, the flag is absent (unknown), not false.
*   **`votable`:** `inVotePool`, and not the current map unless the vote allows it, and not on the cooldown list when the cooldown is enabled.

Rules for reading the vote addon's settings:
*   The addon's loaded configuration and its data file are merged **per key**; the loaded value wins where it has one. (An all-or-nothing choice failed twice on the real server: first an empty global shadowed the file, then a partial one did.)
*   Live ConVars override both for the settings they cover. Defaults when nothing says otherwise: cooldown on, current map excluded.
*   `votable` ignores the vote's **per-vote random subset** (`MapLimit`): it means "can appear in a vote", not "is in this one".

**Known limit:** "active" is *derived*, not read from the addon. The addon exposes no runtime list of its pool, so a stale data file or a custom fork can make the derivation wrong. The report keeps the inputs (`prefixes`, `config`, `convars`, `recent`, `configSource`) so a wrong answer can be diagnosed rather than trusted.

### 3.3 Transport and storage (proposed)
*   The bridge sends the report to a new bridge endpoint, `POST /api/v1/maps`, authenticated and signed like every other bridge request (RFC 5 and RFC 6), on startup and when the map changes. Reports are bounded (a few hundred maps, tens of KB) and rate limited per server.
*   Storage, migration v9: `server_maps(server_id, name, size, matches_gamemode, in_vote_pool, votable, seen_at)` keyed by `(server_id, name)`, replaced as a whole per report in one transaction, plus a small `server_map_state` row (current map, next map, pool basis, reported at). Maps that disappear from a report are deleted.
*   The dashboard shows a **Maps** tab per server: the list with the flags above, and a notice of the form "pool decided by the gamemode pattern" when `poolBasis` is not `prefixes`.
*   Statistics tables keep using the map name as they do today; this RFC adds no foreign key from rounds to maps (a map can be removed while its history stays).

## 4. Floor plans

### 4.1 Why traces; where the map file fits
**Decision:** floor plans are measured with traces. Exact geometry from the map file is a separate, opt-in, per-map variant, specified in [RFC 11](./RFC-011.md); it adds to this RFC and does not replace it.

A map's `.bsp` is the authoritative geometry, and parsers exist (several open-source libraries read the format; their licences must be checked before use). It is not the default because:
*   BSP files are **100-250 MB** on this server. Getting them to the backend means uploading hundreds of megabytes per map, or reading only the needed lumps on the game server, which needs a reader written and shipped in Lua.
*   A parser gives raw geometry, including the 3D skybox, props, clips and voids; deciding what is *walkable* is still left to do.

The game engine already answers "what can be stood on" through ray traces, needs no files and no client, and a scan costs milliseconds per tick. The cost is a coarse result (a grid, not a mesh) and some blind spots (4.4). For a 2D replay background that is enough, so every map gets it by default.

### 4.2 Algorithm
Run by `traitordash_mapscan` (superadmin or console), spread over server ticks with a **3 ms work budget per tick**:

1.  **Seeds:** the map's spawn entities (`info_player_start`, `info_player_deathmatch`, and the teamed variants).
2.  **Per grid cell** (default 64 units): trace straight down against solids only; every standable surface found is a *floor* at that height. Starting inside a solid continues below it. Sky is not a floor.
3.  **Headroom:** one trace upward from each surface. Under 36 units: not a floor. 36-71: a floor flagged **crouch-only** (vents, crawl spaces). 72 or more: a normal floor.
4.  **Flood fill** from the seeds over the four neighbours. A step between neighbouring floors must be at most **48 units** high, and a horizontal trace **20 units above the higher floor** must hit no wall. A node is (cell, height), so a cell with two storeys is visited once per storey.
5.  Only reachable cells are kept. This removes the skybox (the world bounds on the test map were ~15 000 x 13 000 units for a playable ~1 500 x 1 200), ceiling tops and voids, with no map-specific rules.

Output: grid origin and cell size, and per cell a list of floor heights with the crouch-only flag, about 55 KB for the test map.

### 4.3 Operation
*   **Never automatic by default.** The scan runs only when a superadmin runs the command; it refuses a second scan while one is running and a grid above 250 000 cells, and reports its own timing.
*   **Triggering from the dashboard** (a button that makes the server scan the current map) is a later step and goes through the existing command channel; it is listed under open questions, not proposed here.
*   Storage: one blob per `(server_id, map name)`, replaced on upload. A scan is a property of the map, so the same map on two servers is the same plan; deduplicating by map name and file size is an open question.

### 4.4 Known limits (observed or expected)
*   **Measured:** on the test map the scan found five height levels; one (a possible crawl void under a larger floor) is ambiguous and the author could not judge it. A candidate rule, "a floor whose cells are mostly crouch-only and directly under another floor is a low void", is **not** adopted; it needs several maps to validate.
*   **Not yet tested on the real engine:** spawn entity heights, cell centres inside props, steep ramps. The mask ignores doors and props, so doors count as open and props as absent.
*   A 64-unit grid misses narrow ledges and thin walls. A finer grid and wall edges (needed for a good-looking plan, and certainly for 3D) multiply the cost and size; not decided here.

## 5. Security and Privacy
*   Both commands are superadmin/console only. Nothing is written outside `data/traitordash/`.
*   The report contains map names, sizes and vote settings. It contains no player data, no ConVar other than the `mapvote_*` ones read by name, and never a password or token. (The ConVars are read by a fixed list, not by pattern.)
*   `POST /api/v1/maps` enforces the existing bearer token, signature and size limits; a server can only write its own maps.
*   A scan costs server time. The per-tick budget and the single-scan rule bound it; the cell-count cap bounds memory.

## 6. Compatibility and Rollout
*   Additive: new commands, one endpoint, one or two tables. Old bridges send no maps and the Maps tab says so; an old backend answers 404 and the bridge stops trying after one failed attempt.
*   **The prototypes currently ship with the addon** (the bridge includes both files). Until this RFC is accepted, that is the only reason they are loaded; the commands do nothing by themselves. On acceptance the inventory stays in the default build and the scanner may move behind an explicit opt-in file.
*   Delivery order: (1) bridge inventory and its tests, which already exist as prototype tests; (2) backend endpoint, migration and tests; (3) the Maps tab; (4) floor-plan upload and storage; (5) a viewer, under its own RFC. The opt-in BSP variant is RFC 11 and is independent of steps 1-4.

## 7. Testing
*   **Bridge (Fengari, existing):** disk list, current/next/gamemode, a broken pattern, cycle parsing, the vote settings merge (file only, global only, both, empty, foreign keys), ConVar overrides, flags and defaults, pool basis (`prefixes`, `gamemode`, none), the console summary. Scan: floors, sky, stacked floors, the 36/72 headroom boundaries, step and wall rules, spawn selection, trace economy, tick slicing, command guards.
*   **Backend (to write, tests first):** auth and signature, size limit, replace-as-a-whole, disappeared maps removed, a server cannot write another's maps, malformed reports rejected, rate limit.
*   **Real server:** the run described in section 2 is the reference: expected 30 on disk, 28 pool, 25 votable with the then-current map and two cooldown maps.

## 8. Alternatives Considered
*   **Read the map cycle file only.** Simple, but empty on the reference server, and wrong for any vote-driven server.
*   **Ask the admin to list playable maps in the dashboard.** The list goes stale and is manual work; rejected by the no-manual-action requirement.
*   **Parse BSPs as the default** (4.1). Complete geometry but 100-250 MB per map and a parser to write or vendor. Not the default; offered per map as an opt-in in RFC 11.
*   **A bot that looks straight down and records the view.** Needs a running client and a player slot, and sees roofs, not floors. The trace scan needs neither.
*   **Hand-made map images** (the community radar images some maps ship). Not available for most maps and not consistent.

## 9. Open Questions
*   Should the report also be refreshed when the vote addon's settings change, or only on startup and map change?
*   Is "votable" the right granularity, or should the dashboard also show the cooldown's remaining length?
*   Share floor plans between servers by map name and size, or keep them per server?
*   Where should the flood fill stop: grid size, step height and wall height are tuned on one map. Which other maps (multi-storey, outdoor, water) should be run before the thresholds are frozen?
*   Low voids and crawl spaces: a rule that works on more than one map, or keep every storey and let the viewer decide?
*   Does the scan belong in the default addon, or in an optional file the owner enables?
