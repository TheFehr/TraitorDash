# RFC 6: Secure Command Queue (RCON-less)

> **Status: implemented.** This revision describes what the code does today. The first version
> described a GET poll that deleted commands as it handed them out and trusted every answer;
> sections 2.3 to 2.5 and 4 replace that.

## 1. Abstract
This document defines a secure, pull-based method for applying web-based configurations to the Garry's Mod server. By utilizing an HTTP command queue instead of RCON, TraitorDash eliminates the need for exposing sensitive console ports and simplifies deployment in restricted network environments.

## 2. Command Staging & Delivery
TraitorDash operates on an asynchronous "Stage-and-Poll" model.

### 2.1 Web-Side Staging
When an authorized admin submits changes via the dashboard (`POST /api/save/:serverId/:role`):
1.  **Authorization:** The request needs an admin session (RFC 7) and a same-site `Origin`.
2.  **White-listing:** Only ConVars discovered during ingestion (or reported by the bridge for that role) are eligible. An unknown name, such as `rcon_password`, is ignored and logged.
3.  **Validation:** A value may be at most 64 characters from `A-Za-z0-9_.: -` (`on`/`off`/`true`/`false` become `1`/`0`). Anything else, such as a newline or `;` that could start a second console command, refuses the whole request with a 400; nothing is queued.
4.  **Persistence:** Each accepted change is stored as one row in the `commands` table (`type`, `payload`, the server it belongs to) and recorded in the audit log with the admin's SteamID.

### 2.2 Bridge Polling (The "Pull" Model)
Instead of the backend "pushing" to the game server, the GMod Bridge "pulls" its work:
1.  **The Poll:** Every 10 seconds the Bridge sends `POST /api/v1/poll` with a JSON body: `active_admins` (for CAMI, RFC 5), `acked` (see 2.4) and a fresh `nonce`.
2.  **The Handshake:** The `traitordash_token` ConVar is sent as a Bearer token in the `Authorization` header. The token identifies the server; a stolen token only ever reaches that server's queue.
3.  **The Payload:** The Backend answers with the pending commands for that server (see 2.3).

### 2.3 The Signed Answer
A poll is answered as `{"commands":[{id,type,payload},...],"sig":"<hex>"}` where

    sig = SHA-256( token \n nonce \n <the commands array exactly as sent> \n token )

The nonce is new for every poll, so an answer cannot be replayed. The token is a secret both ends hold, and it is both prefix and suffix of the hashed text, so the construction is not extendable. The Bridge recomputes the value, compares it in constant time, and **parses only the bytes it verified**. An answer without a valid signature applies nothing; the Bridge logs the first three refusals with what it received (and then at most every five minutes) and announces when answers verify again. The signature is in the body, not in a header, because GMod's `HTTP` success callback does not expose custom response headers.

A poll without a valid nonce (an older Bridge) is answered unsigned, as `{"commands":[...]}`, and the backend logs a warning once per server. A new Bridge never applies such an answer, so Bridge and backend must be updated together; an old Bridge keeps working against a new backend.

### 2.4 At-Least-Once Delivery
Handing a command out does not delete it. The Bridge remembers the ids it applied and sends them as `acked` in its next poll; only then does the backend delete them (for that server only). Acknowledgements are dropped from the Bridge's memory only after a verified `200`, so a lost response or a lost acknowledgement leads to a re-send, never to a lost change. Consequences:
*   Commands must be idempotent. ConVar sets are; the Bridge applies a re-sent one again without harm.
*   A refused or failed command is acknowledged as well, since re-sending it forever helps nobody.
*   A command that is never acknowledged is dropped after one hour.
*   A Bridge that sends no `acked` field keeps the original delete-on-poll behaviour.

### 2.5 Transport
The Bridge sends the token and receives commands only to an `https://` URL or to a loopback or private-network address (`TraitorDash.TrustedBaseUrl`). Anything else (a public `http://` address) is refused with one warning and the Bridge stays idle. This applies to every sender (poll, ingest, values, language files, stats), not just the poll.

## 3. Execution Logic (GMod-Side)
Upon receiving a verified manifest, the Bridge executes the updates within the game engine:
*   **ConVar Updates (`convar`):** The payload is `<name> <value>`. It is parsed by `TraitorDash.ParseConVarCommand` and applied only if the name is a plain `ttt_*`/`ttt2_*` identifier of a ConVar that exists, with exactly one value (quoted if it has spaces). It is applied with `RunConsoleCommand(name, value)`, never through the raw console string, so a payload can not chain a second command. A payload that fails any rule is refused as a whole.
*   **TTT2 Data Updates (`data`):** Applied via the global setters (`SetGlobalBool/Int/String`) and, where the role keeps the value in `TTT2.DATA`, through TTT2's own API, for keys that are plain identifiers.
*   **Logging:** The Bridge logs every applied or refused command (`[TraitorDash] CONVAR: ttt_x 1`) to the server console for auditability.

## 4. Security & Integrity
*   **RCON-less Design:** No RCON password is ever stored or transmitted, significantly reducing the attack surface.
*   **Network Simplicity:** No TCP port-forwarding (27015) is required on the game server's router; as long as the server has outbound internet access, the system functions.
*   **Token Authentication:** Every Bridge request is authenticated via the unique API token (only a hash of it is stored). A leaked token is replaced in the dashboard (`regenerate-token`).
*   **The Bridge does not trust the backend blindly.** Defence in depth, in order: the transport must be https or private (2.5); the answer must carry a valid signature (2.3); a command must pass the allow-list and the one-command rule (3). A compromised backend or a network attacker can therefore not make the server run an arbitrary console command or set `rcon_password`.
*   **What a token holder can do:** report data for its own server (roles, ConVar values, round statistics) and read that server's queue. That includes inventing players in the statistics; this was weighed and accepted, since a stolen token can already do more than that.
*   **Auditability:** Every command staged on the web is linked to the authenticated SteamID of the admin, providing a complete record of "who changed what."
*   **Resource limits:** the poll body, a role file (256 KB), the language push (8 MB in total) and the round report are size-limited; `/v1/round` is limited to 10 reports per minute per server.

## 5. Performance Considerations
*   **Minimal Latency:** While not "instant" (subject to the polling interval), configuration changes do not require the sub-millisecond response time of administrative commands like "Kick" or "Ban."
*   **Batching:** All pending changes are delivered in a single HTTP response, minimizing the number of network round-trips.
*   **Cost of a poll:** one small POST every 10 seconds per server; nothing else runs per tick.
