# RFC 40: The Server's Workshop Collection as a Content Source (Index, Fetch, Build)

> **Status: built, not run on the real server (2026-11-20).** Sections 3.1 to 3.4, 5 and 6 are in the code and covered by tests on constructed archives and a fake Steam; nothing here has been run against the real Workshop collection, so section 7 (the real run and looking at the models) is still to do. See "As built" at the end. Asked for by the maintainer while discussing RFC 39 (weapon models): "why aren't we pulling, or at least indexing, the same Workshop collection I set on the GMod server? That is one Workshop ID that contains all of the content." Builds on RFC 11 (the Workshop fetch of map addons with the pinned helper), RFC 18 (models, materials and the game's own content), RFC 36 (every material gets its texture; levels of detail only if the numbers call for it) and RFC 39 (weapon models).

## 1. Abstract
The replay can draw a model only if it can read it. Today it reads three sources: the map's own pack, the game's stock content (the free dedicated-server apps, RFC 18 4.5, switched on by `GAME_CONTENT`) and nothing else. Everything the server's **Workshop addons** add (about 650 mounted items on the maintainer's server: weapons, props, player models, role icons, materials) is invisible to it. The symptoms are known: on `ttt_minecraft_b7_summer` "37 models unavailable", props that the map places from an addon draw as nothing, and RFC 39's weapons from addons would get a placeholder.

The server's addons are **one Workshop collection** (possibly with sub-collections), set once on the game server. This RFC makes that collection a content source of the dashboard: the backend learns the list from the collection, **indexes** every addon (what files it holds), and **builds** a model, with its materials, from the addon that holds it **when something needs it**, gradually and in the background. Nothing in it is a quality budget: everything is fetched and indexed; the work is spread over time (the maintainer's rule: levels of detail and gradual loading, not caps).

## 2. What exists (read 2026-11-20)
*   **The fetch.** `workshop.ts` runs the pinned DepotDownloader (RFC 11, 3.2: `-app 4000 -pubfile <id>`, an argument list, an empty environment, a scratch directory on the server's volume, size and time limits, the archive read in place and deleted when the job ends); `gma.ts` reads an addon archive's file table (`readGmaIndex`, `mapEntries`); the LZMA-compressed legacy archives (the oldest items) are handled. This is used today **only for map addons**.
*   **The addon list.** The bridge already sees `engine.GetAddons()` (`roleaddons.lua`) and sends the Workshop IDs of the mounted **map** addons (`mapAddons`, digits only, at most 300, RFC 11). The game does not say which addon holds which file.
*   **The model pipeline.** `.mdl`/`.vvd`/`.vtx` are read and written as GLB (`model.ts`, `modelGlb.ts`, `propset.ts`), the materials and textures through the VMT and VTF readers and the texture book (RFC 18 5, RFC 36), from a **source** (a map pack or the game's content index, `gamecontent.ts`).
*   **What is missing** is a source for the addons of the collection, and the list of what they hold.

## 3. Design
### 3.1 The list: the collection
*   A new backend setting **`WORKSHOP_COLLECTION`** (the Workshop ID of the collection, digits only; the egg's variable list, `pelican/egg-traitordash.json`, gets it; empty means the feature is off and nothing changes). The backend resolves it with Steam's **public** Web API (`ISteamRemoteStorage/GetCollectionDetails`, which needs no key), **recursively through sub-collections** (a child that is itself a collection is expanded; a depth and a count guard against loops and against a hostile collection), into a list of addon IDs with titles and update times (`GetPublishedFileDetails`).
*   **Cross-check with the game:** the bridge's `mapAddons` becomes `addons`: **all** mounted addon IDs (digits, at most 2 000), so that the dashboard can say "the server mounts 3 addons that are not in the collection" (workshop items added by another way) and can index them too. The collection is the primary list (it is the maintainer's definition of "what the server runs"); the bridge's list fills the gaps.

### 3.2 The index: what each addon holds
*   A background **queue** (the pattern of `runGeometryQueue`, RFC 11): one addon at a time, resumable, started at boot and on a schedule (nightly, off-peak; the maintainer's server is small and the work must never slow it: one download at a time, a delay between downloads, a pause while a round report is being processed). Per addon: download with the pinned helper into the scratch directory, read the **file table** (every path, size and CRC; the archive header, not the contents), write the rows, **delete the download**. An addon that cannot be fetched (private, friends-only, removed, too large for the existing limits, a timeout) is recorded with its error and retried on the next schedule; it never fails the queue.
*   **Tables** (a migration): `workshop_addons` (id, title, `updated` from the Workshop, `indexed_at`, status, bytes, file count, error) and `workshop_files` (addon id, lower-cased path, size, crc) indexed by path. Paths of **models, materials, textures** (`models/`, `materials/`) are kept in full; other files (Lua, sounds, maps) are counted per directory only, because nothing reads them (they are never executed or served). An addon is **re-indexed when its `updated` time is newer** than `indexed_at` (checked by the schedule with one batched details call).
*   **Size, measured not guessed:** the first full run on the maintainer's collection reports the downloaded bytes, the time, the rows and the database growth on the coverage page (section 5) before anyone decides anything about them.

### 3.3 The content source: build a model when it is needed
*   A new **source** next to the map pack and the game's content: `WorkshopContent`. Asked for `models/weapons/foo.mdl`, it finds the addon in the index, **fetches that addon again** (the same helper and limits), extracts **only the files the model needs** (`.mdl`, `.vvd`, `.dx90.vtx`, and the materials and textures its `$cdmaterials` and skins name, found by path in this or another addon of the index: a model may use materials from a different addon, or from the game's stock content) into a **content cache** on the server's volume, and builds the GLB with the existing model pipeline; the finished GLB is stored like the other model files. Later requests are served from the cache.
*   **Triggers (gradually, in the background):** a recorded track's `wm` (RFC 39: weapon model paths) queues the model builds it needs; a map's built mesh queues the models its placed props name that are unavailable today; an admin can queue a model by path. A replay that opens before the build finishes draws the **placeholder** for that model and picks the real one up on the next load (the same "later" behaviour as the textures; no spinner).
*   **Which source wins:** the map's own pack, then the game's stock content, then the workshop index (an addon cannot replace a stock model for a map that ships its own).

### 3.4 Safety (untrusted archives)
Addon archives are untrusted files from the Workshop: the same limits as for map addons (member size, total bytes, a time limit; extraction only of the named model and material files; paths normalised and checked against `..` and absolute names; the helper in its own environment with no secrets); **no Lua from an addon is ever read for execution** and no file is served to a browser except the built GLB and the converted textures. A malformed model fails its own build and nothing else.

## 4. What it gives
*   **RFC 39:** weapon world models from addons (the placeholder remains only for a model that is not yet built or an addon that cannot be fetched).
*   **Props:** the models that maps place from addons ("37 models unavailable" on `b7_summer` and the same on other maps) become drawable; the census of RFC 18 reports the drop.
*   **Player models** of the server's addons for the replay's figures (a later consumer; RFC 22 draws the stock model today).
*   **Materials:** the "not found" textures of RFC 36 that live in addons (the 24 fallbacks on the maintainer's maps are a list to check against the index).

## 5. The page
A card **"Workshop content"** on the admin side of the coverage page: the collection ID, addons in the collection, indexed, failed (with the reason) and pending; bytes downloaded and rows in total; the models built and in the queue; the last run. A button to run the queue now and to retry the failed. Styles as the other cards (RFC 30), no layout jump.

## 6. Tests (what must fail on a broken build)
*   **The list:** a constructed collection response with nested sub-collections, a loop, a duplicate and a hostile (huge) response: expanded, deduplicated, bounded; an empty `WORKSHOP_COLLECTION` is off; the setting's digits check; the bridge's `addons` list (digits only, 2 000 at most) and the cross-check.
*   **The index:** the queue on a fake fetcher: order, one at a time, resumable after a stop, a failure recorded and retried, an update re-indexes, the download is deleted, the rows are right for a constructed archive (models, materials and textures in full, the rest counted), duplicates across addons; the migration (fresh and upgrade).
*   **The source:** a model found in an addon is extracted with its materials (from the same or another addon or the stock content), built and cached; a missing material falls back as in RFC 36; path traversal and oversize members are refused; the priority between the sources; a build failure is local; the placeholder until built.
*   **Triggers:** a track's `wm` queues builds, deduplicated; a map's unavailable props queue builds; nothing queues when the feature is off.
*   **Page:** the card's numbers, no layout jump, contrast.
*   **Mutation checks** on the key rules (the recursion guard, the update check, the delete of the download, the path checks, the source priority, one at a time).

## 7. Verification (required before it is called done)
Run the index on the maintainer's real collection (with `WORKSHOP_COLLECTION` set in the panel) and report **time, downloaded bytes, rows and database size, failures and why**; then build the models of a real recorded round's `wm` and of a map with unavailable props and **look at them** in the replay (a weapon in a hand, a prop that was missing). Unverified until then: how many of the addons can be fetched anonymously, how long the first index takes against Steam's rate limits, how large the rows get, and whether the helper copes with the biggest items.

## 8. Open
*   **Where the collection ID comes from:** the backend setting proposed above (explicit, one place), or read from the game server (`host_workshop_collection`) by the bridge: proposed the setting, the bridge's list as a cross-check.
*   **Disk:** the content cache holds only what was built (a model's files, not whole addons); if the volume gets tight the cache can be pruned and rebuilt on demand; no count or quality cap is part of this RFC.
*   **Sounds and other content** (sprites, particles): not read in this RFC; the index counts them per directory, so a later RFC can add them.

## 9. As built (2026-11-20)
**What is in the code.** All of it is off unless `WORKSHOP_COLLECTION` is set to digits (an egg variable, in the README's table, and in the Pelican README); with it empty or not digits no table is read, no card shown, nothing queued, and the model pipeline is wired as before.

*   **The list** (`services/workshopCollection.ts`). `resolveCollection` calls `ISteamRemoteStorage/GetCollectionDetails` for the collection and then, level by level, for each sub-collection (POST form, no key), and `GetPublishedFileDetails` (100 ids to a request) for titles and `time_updated`. Guards: depth 6, 100 collections, 20 000 addons, 16 MiB per answer (the real POST also stops reading at that size); a loop or a duplicate is read once; what a guard cut is a note on the card. The HTTP call is injected (`HttpPost`), so the tests give constructed answers. Ids that are not digits are dropped.
*   **The bridge's list.** `maps.lua` collects every mounted addon id (`addons.allIds`); `bridge.lua` sends them as `addons` (digits, at most 2 000) and still sends `mapAddons` (the map-tagged ones, at most 300). The backend keeps `map_addons` as it was (the map fetch is unchanged) and stores `addons` in the new column `server_map_state.addons`. A bridge from before this RFC sends only `mapAddons`: the map fetch keeps working from it and the list of all addons is *unknown* (null), not guessed; the card then says the bridge has not reported. The cross-check (mounted, not in the collection) is on the card and in `workshopStore.notInCollection`.
*   **The tables** (migration 32): `workshop_addons` (id, title, `updated`, `indexed_at`, status, bytes, file_count, error, source, order), `workshop_files` (addon id, lower-cased path, size, crc; index on path; `models/` and `materials/` in full), `workshop_dirs` (every other file counted per top directory; names that are not safe paths counted as "(unsafe names)"), `workshop_models` (the model builds), `workshop_meta` (last run, notes); plus `server_map_state.addons`. Times are seconds, as Steam's are. `readGmaIndex` now also returns each entry's crc.
*   **The queue** (`services/workshopQueue.ts`, pattern of `runGeometryQueue`). One run at a time (a second call returns at once); inside it one job at a time, in this order: a queued model build, else the next pending addon in the collection's order. State is in the database, so a stop or a crash resumes (an addon left "indexing" is pending again; indexed ones are not downloaded again). Start: 30 s after boot and every night at 04:00 server-local time, both with "retry the failed"; a plain "Run now" does not retry the failed (the "Retry failed" button does). Pause between downloads: 3 s; before each download the queue also waits while a round report was received in the last 3 s. A failure (private, removed, too large for the limits, timeout, unreadable archive, a fetcher that throws) is recorded on the addon and never stops the run. The download is deleted as soon as the file table is read, also when it cannot be read. An addon is indexed again when Steam's `time_updated` is newer than `indexed_at` (checked at each run by the list refresh, which is one batched details call per 100 addons). Addons the servers mount that the collection lacks are indexed too (source "server"). It uses `addonFetcher` in `workshop.ts`, which shares the helper call, the limits, the scratch directory and the archive handling (including the old LZMA items) with the map fetch.
*   **The source** (`services/workshopContent.ts`). `buildModel(path)`: finds the addons that hold the model's `.mdl` in the index (newest first), takes the first that also holds the `.vvd` and a `.dx90.vtx` (or `.dx80.vtx`), fetches it again, copies those three files into the content cache (`WORKSHOP_CONTENT_DIR`, default `.workshop-content`; files named by a hash of the path), reads which materials the model names, and takes each `.vmt` (then the texture it names, and the material a patch includes) from that addon, else from another addon of the index (fetched once, together with the texture of the same material), else from the game's own content through the pipeline's stock source (kept in memory for the GLB only). A material found nowhere gets a plain colour (RFC 36's fallback). The GLB (`staticModelGlb` in `maps/modelGlb.ts`: a primitive per material run, PNG textures embedded, Z-up root like the other models) is written to the cache. Outcome per model: `built`, `failed` (with the reason), or `unknown` (no indexed addon holds it yet; looked at again at the next run, and once more at the end of a run that indexed something).
*   **Into the pipeline.** `workshopContent()` is a `StockModels`/`StockTextures` over the cache; `chainModels` and `chainTextures` put the game's content before it, so the priority is the map's pack (read by `buildPropSet` itself), the game's content, then the workshop. The chain is installed in `index.tsx` with the game's content (when `GAME_CONTENT=1`) and the workshop's (when the collection is set), still only when `MAP_GEOMETRY=1`.
*   **Triggers.** `queueModelBuild(path)` (normalises the path, refuses anything that is not `models/....mdl`, deduplicates, starts a models-only run). The **map-mesh trigger**: when the workshop source is asked for a model it does not have it queues a build if the index holds the model or the index is not complete yet. An **admin route** queues a model by path. `queueTrackModels(paths)` is the function **RFC 39 is to call** with a track's `wm`; nothing calls it yet (RFC 39 is not built). Nothing queues when the feature is off.
*   **Safety.** Names are checked by `cleanPath` before they are stored or looked up (lower case, forward slashes; absolute names, `..`, empty parts, NUL, a colon and names over 300 characters are never stored or extracted); material names a model carries must also pass `texturePathName`; members over 64 MiB are refused; one build fetches at most 24 addons and looks for at most 1 200 material files (safety ceilings, reported in the build's note when they bite, not quality settings); cache file names are hashes, so no name becomes a path; no Lua from an addon is read; the GLB route serves only a built GLB (`nosniff`, a content security policy of `default-src 'none'`).
*   **The page.** The card "Workshop content" at the top of the coverage page (admin only, only when the collection is set): collection id, addons in the collection (and when it was read), indexed, pending, failed (with the reasons in a table), bytes downloaded, rows in the database (with an estimate of their size), models built and queued, the last run (time, duration, counts, bytes), the queue's state, the mounted-but-not-in-collection count with the first ids, the buttons "Run now" and "Retry failed", and a field to queue a model by path. The same rows are always there (the numbers change, the rows do not); only existing card, table and button styles are used (RFC 30's spacing variables through them). Routes (all admin, in `routes/tiers.ts`, CSRF by the app's origin check): `POST /servers/:serverId/workshop-content/{run,retry,model}` and `GET .../model.glb?path=`.
*   **Files.** New: `services/workshopCollection.ts`, `workshopStore.ts`, `workshopQueue.ts`, `workshopContent.ts`, `workshopRuntime.ts`; tests `test/rfc40_collection.test.ts`, `rfc40_index.test.ts`, `rfc40_content.test.ts`, `rfc40_page.test.ts`, `test/helpers/workshop_fake.ts`. Changed: `migrations.ts`, `Store.ts`, `routes/api.tsx`, `routes/tiers.ts`, `index.tsx`, `workshop.ts`, `maps/gma.ts`, `maps/modelGlb.ts`, `components/MapCoveragePage.tsx`, `addon/lua/traitordash/maps.lua` and `bridge.lua`, `pelican/egg-traitordash.json`, the READMEs, and two tests (`maps_bridge.test.ts` for the new payload key; `rfc26c4_talk.test.ts` no longer pins the number of migrations).
*   **Mutation checks** (a rule broken, a test failed, the rule restored): the recursion guard (a loop is read once), the update check, the delete of the download, the path checks, the source priority, one at a time, the member size limit, the off switch of the triggers, the response size guard.

**Differences from the text above.** (1) The GLB of a model is written to the cache, served only to admins (`model.glb`) and ready for RFC 39; no replay page asks for it yet. (2) A map's mesh does not pick up a model built later by itself: it draws it the next time the mesh is built (the stored meshes are not marked stale by a workshop build). (3) The index reads only `models/` and `materials/` in full; textures are under `materials/`, so they are in. (4) The nightly time (04:00) and the 3 s pause are constants, not settings.

**Not verified (section 7 is still open).** Nothing was run against Steam or the helper: how many of the addons of the maintainer's collection can be fetched anonymously, how long the first index takes against Steam's rate limits, how large the rows get, whether the helper copes with the biggest items, the real shapes of `GetCollectionDetails` and `GetPublishedFileDetails` answers (the code follows Steam's documented fields; the tests use answers built from them), and that the models built from real addons look right in the replay (a weapon in a hand, a prop that was missing) and have their textures. The page was checked by tests of its markup, not in a browser. The "pause while a round report is being processed" is a 3 s quiet window after a report, not a measured need.

## 10. The model search (2026-11-20)
The "Build a model" box needed an exact path, which nobody knows. The card now has **Find a model**: a GET form (`?q=usp`, at least 2 characters, `%` and `_` literal) that searches the index for `models/...mdl` paths containing the term and lists up to 40, one row per path with the addon that holds it (the most recently updated) and a **Queue** button, or "built" / "queued" if it already is. Only indexed addons are searched. Tests: `backend/test/rfc40_search.test.tsx` (the query, the cap, the escaping, an injection attempt, the card); mutation checks: dropping the indexed filter and the escape each failed a test. Not looked at on the real server yet.
