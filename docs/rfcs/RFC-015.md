# RFC 15: Public Role Pages and a Role Tab in the In-Game F1 Menu

> **Status: steps 1 to 3 built (2026-10-20): the public pages, the embed, the headers, the limiter, the switches, `GET /api/v1/whoami`, the server part and the client files of the F1 tab, and the case-file look with the roles' own colours, put-away roles by player count and bundled fonts. Not done: the real-client test (step 4), which is also the first time the tab runs inside TTT2's own menu code.** It extends the role pages of [RFC 4](./RFC-004.md) (the dashboard) and the access model of [RFC 13](./RFC-013.md) (anonymous, signed-in, admin), and adds a client part to the bridge of [RFC 2](./RFC-002.md).

## 1. Abstract
The page of a role (what it is, how often it appears, what its settings are) is today an **admin page**: an anonymous visitor is sent to the front page. Players are the people who most want to know what a role does and how likely it is. This RFC makes the role pages **public and read-only** (the settings form stays admin-only, on its own address), adds a **compact embedded layout** (`?embed=1`) for small windows, and adds a **tab in TTT2's F1 menu** that shows that page inside the game, with `!role` and `!role <name>` as shortcuts. Nothing is sent from the player's machine except the page request they asked for.

## 2. Motivation
*   **Players ask the same questions again and again** ("what does the Haunter do?", "how many players does it take to get a Sheriff?"). The answers exist on the dashboard (the addon's description, the minimum players, the spawn chance, the role's settings) but only admins can read them.
*   **The data is already collected.** The bridge reports each role's settings and live values, and the language files (RFC 4); the dashboard computes the numbers for its role overview (`roleMetrics`). Nothing new has to be gathered from the game server.
*   **TTT2's own role description is not enough.** It is a sentence from the addon author. The server's rules (is the role enabled, min players, maximum, chance, credits) are what decides whether a player will ever meet it, and only the server operator's values are right for this server.
*   **A read-only view is safe to make public.** The form is the dangerous part (it can change the server); the view is not.

## 3. Current State (summary, not a change)
*   `GET /servers/:serverId/roles/:roleName` returns the **configuration form** for admins (`RoleConfigForm`, with the live values from the game server) and redirects everybody else to `/`. The role list (`Sidebar`, `GET /sidebar/:serverId`) is admin-only too. In `routes/tiers.ts` both are `admin`. Saving is `POST /api/save/:serverId/:role`, admin-only with CSRF protection (RFC 7).
*   The stored data per server: the roles (name, team, base role, policing flag), each role's settings schema (labels already resolved through the language files), live ConVar values with defaults and limits, and the **language files** (RFC 4). `roleMetrics(live, roleName)` turns the ConVars into the six numbers of the overview (distribution, max, min players, min karma, spawn chance, credits).
*   TTT2 describes a role in its language files (`ttt2_desc_<role>` is the key its own role menu uses; the popup text at the round start is `info_popup_<role>`); role addons add their own keys.
*   The bridge (RFC 2, 8) knows the dashboard URL and its token. That URL is whatever the operator configured and may be **a private address** that a player's computer cannot reach. The bridge does **not** know its server's id on the dashboard, which the page addresses contain.
*   **TTT2's F1 menu is built from files** (read in the public TTT2 sources, `master`, 2026-10-20; the installed core on the real server is from April 2026 and was not compared line by line): every file in `lua/terrortown/menus/gamemode/` is one menu entry (a `CLGAMEMODEMENU` class with icon, title, description and priority), and the files in a folder of the same name are its pages (`CLGAMEMODESUBMENU`, with a `Populate(parent)` function that builds the panel). The scan covers every mounted Lua path, and the server sends the files it finds to clients at start. TTT2's own **Roles overview** page already puts a `DHTML` panel into such a page. An entry is shown to everyone unless it declares itself an admin menu: the built-in **Roles** tab does, so a player never sees it (`ShouldShow()` hides admin menus from non-admins).
*   TTT2 has no MOTD or other window that shows a web page by itself. The bridge has no client-side code today (the addon is server-only).

## 4. Design

### 4.1 Public role pages
*   `GET /servers/:serverId/roles` (new): the list of the server's roles, with team, enabled or not and the key numbers, and a search box (plain form, no script needed). Public.
*   `GET /servers/:serverId/roles/:roleName`: becomes **the read-only page**, public. A role or server that does not exist is a `404` with a short page (not a redirect to the login).
*   **The configuration form moves** to `GET /servers/:serverId/roles/:roleName/config` (admin). An admin who opens the role page sees an "Edit settings" link to it; nobody else sees it. Old bookmarks of the role address keep working (they land on the read-only page, one click from the form). `POST /api/save/...` is unchanged.
*   The admin sidebar and dashboard link to the form as before.

### 4.2 What the page shows
Shown, all read-only text:
1.  **Name, team** (with the team's colour) and whether the role is **enabled** on this server.
2.  **Description** from the language files, in this order: `ttt2_desc_<role>`, `info_popup_<role>`, then the first `desc`/`description`-like key of the role's addon if there is one; English first, then any language that has the key. If nothing is found the page says "The addon does not describe this role" and shows the team's generic line. The text is **untrusted** (any addon author wrote it): it is rendered as text, never as HTML; the formatting marks of the language files are removed.
3.  **How it appears on this server:** the six numbers of the overview (distribution, maximum, minimum players, minimum karma, spawn chance, starting credits), with "unlimited" and "not reported yet" where that is the truth.
4.  **The role's settings**, read-only: label, current value, the default, in the order of the role's own menu. A setting the server has not reported shows no value.

Not shown, ever: tokens, admin lists, audit data, other servers, raw Lua, the server's address, anything that only an admin sees today. The page is built from a fixed selection of fields, not from the stored objects, so a field added to them later does not leak by default (a test pins this).

*   **Two operator switches** (egg variables and environment): `PUBLIC_ROLES` (default `1`; `0` keeps the role pages admin-only, as today) and `PUBLIC_ROLE_SETTINGS` (default `1`; `0` hides item 4 and keeps the rest). A server owner who regards the exact numbers as a secret can switch them off without losing the descriptions.

### 4.3 The embedded layout
*   `?embed=1` (or `embed=true`) renders the same content **without the site header, the sign-in link, the admin marks and the sidebar**; the links on the page stay inside the roles section (list, other role, back). It is for a browser panel of about 800 by 500 pixels and up; the normal layout stays for browsers.
*   **No script.** The page is server-rendered HTML with the inline stylesheet. The game's browser is an old Chromium and nothing in the page needs script, so it works the same everywhere and a script cannot be injected by a description.
*   Headers on every role page: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src 'self' data:; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` (the embed has no form; the list's search form is `GET`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: public, max-age=60` and an `ETag`. No cookie is set or read for anonymous visitors. The embed also sends `X-Robots-Tag: noindex`.

### 4.4 Access and abuse
*   Tier **public** in `routes/tiers.ts` for `GET /servers/:serverId/roles` and `GET /servers/:serverId/roles/:roleName`; **admin** for `.../config`. The sweep test of RFC 13 fails if either is missing.
*   A public page costs a database read and a render, so it is **rate limited per address** (default 120 a minute, `429` over it, using the existing limiter and `clientAddress` of RFC 13), and answered from a short cache keyed by server, role and `updated_at` so a flood of identical requests is cheap.
*   Role names are validated against the server's own list before anything is read; an unknown name is a `404`, whatever characters it has.

### 4.5 The role tab in the F1 menu (bridge)
**Configuration.** Two things the bridge does not have today:
*   the **public address of the dashboard** (`public_url` in `data/traitordash/config.json`, or the ConVar `traitordash_public_url`): the address a *player* can reach. It must be `https` (a plain `http` address is not sent to clients, and a private address is useless to them). It is separate from the URL the server itself uses.
*   the **server's id** on the dashboard: the bridge asks once at start, `GET /api/v1/whoami` (bridge token, returns `{ server_id }`).

With either missing the feature is off (the tab is not shown) and one console line says which and why.

**The tab.** Two client files, sent to players like the other menu files:
*   `lua/terrortown/menus/gamemode/traitordash_roles.lua`: the menu entry. Base `base_gamemodemenu`, a title such as "Server roles", a description, a priority after the built-in tabs, not an admin menu (so everybody sees it), and `ShouldShow()` additionally returns false when the feature is off. **Its icon is borrowed from TTT2** (`vgui/ttt/vskin/helpscreen/roles`, the image the admin Roles tab uses): nothing is downloaded, and the only people who see two tabs with that icon are admins, whose admin tabs are shown in a separate group. A custom icon can replace it later.
*   `lua/terrortown/menus/gamemode/traitordash_roles/guide.lua`: its one page. `Populate(parent)` creates a `DHTML` panel (docked to fill) and opens the address; it does nothing else.

**Which address.** The client builds it itself from the base and the server id that the server sent once at join (`TraitorDash_RolesInit`): `<public_url>/servers/<server_id>/roles?embed=1`, or `.../roles/<name>?embed=1` when a role was asked for (below). **The client never opens an address it was sent.** The page is fetched when the tab is opened, not at join: a player who never opens the tab never contacts the dashboard.

**Shortcuts.** A player types `!role` (their own role), `!role <name>` or `!roles` (the list), or runs `traitordash_role [name]`. The server validates the name against the roles it knows (case-insensitive), rate limits to one per player every 2 seconds, answers in chat when the name is unknown ("No role called X"), and sends a **net message with the role name only**. The client then opens the F1 menu on the tab with that role. TTT2's menu code has a call for showing a given submenu (`HELPSCRN:ShowSubmenu(menuClass)`); how to find our class from outside is checked when it is built, and if it cannot be done the shortcut opens the F1 menu and says in chat "open the Server roles tab".

**What TTT2 provides, so that the bridge does not build it:** the window, the close button, `Esc`, and the placement. Navigation inside the page is limited by the page itself (the embed has no outbound links; the CSP forbids loading anything else). The first time in a session the player sees one chat line: "Opening the role guide from <host>."

**Privacy.** The page request comes from the player's own machine, so the dashboard sees their address like any web visit, and only when they open the tab or ask for a role. Nothing about the player, their role or the game is sent in the request: the role is in the path because they asked for it.

### 4.6 What it does not do
*   No change to the admin form, saving, CSRF, or who may change settings.
*   No sign-in in the tab (the pages are public; the game's browser has no session).
*   No role icons (the addons' materials are not available to the dashboard).
*   TTT2's own role descriptions, its Guide tab and its popup stay as they are; this adds the server's rules next to them. The admin-only Roles tab is untouched.

**As built (step 1):** `services/roleview.ts` builds the page from a fixed selection of fields; `components/RolePublic.tsx` renders it (one shell for both layouts, inline stylesheet, no script); the routes and their cache and limiter are in `index.tsx`; tests are `test/role_public.test.tsx`. Decisions the RFC left open:
*   **The description is read once, at extraction** (in the extractor's worker, which already loads the language files) and stored in `roles.description` (migration v16, which also clears the role hashes so the bridge sends every role again and existing roles get one). Only the **English** files are stored, so it is English only for now. Keys tried in order: `ttt2_desc_<role>`, `info_popup_<role>`, `desc_<role>`, `description_<role>`, `<role>_desc`, `<role>_description`. It is cleaned (markup and control characters removed, whitespace collapsed, 2,000 characters at most) and rendered as text.
*   **Both layouts have the strict Content-Security-Policy** (the normal one is script-free too, with its own small header instead of the site's); the normal layout is therefore plainer than the dashboard.
*   **The limit is per client address and only applies behind `TRUST_PROXY=1`** (as in RFC 13), 120 a minute (`ROLE_PAGE_LIMIT` changes it). The cache is in memory (500 pages), keyed by server, page, embed, the switches and a version made of the row counts and last update times of the roles, live values and language files, so a change shows at once, except two changes within one millisecond.
*   An admin's page has an edit link and is `private`; the embed is the same for everybody and never has the link.
*   The list shows team, distribution and minimum players per role; the page shows all six numbers.
*   The form's links in the sidebar and the server page point at `/config`; the form page has a link to the public page.

**As built (steps 2 and 3):** `addon/lua/traitordash/rolemenu.lua` (server), `addon/lua/autorun/client/traitordash_roles_cl.lua` (client: the address, the net receivers, opening the menu), and the two TTT2 menu files `terrortown/menus/gamemode/traitordash_roles.lua` and `.../traitordash_roles/guide.lua`; tests in `test/rolemenu_bridge.test.ts` (the real files against a fake of net, hook, timer, HTTP and the menu classes). What differs from the text above:
*   **`public_url`** is read like the other two settings (file first, then the ConVar `traitordash_public_url`) by `TraitorDash.GetPublicUrlRaw()` and checked by the role guide: `https://host[:port][/path]` only. The feature starts 8 s after load (after the first sync has begun), asks `whoami` once, and a failure leaves it off with one console line. A `traitordash_role` in the server console prints its state.
*   **Names are plain:** letters, digits, `_ . -`, starting with a letter or digit, 64 at most, checked against the game's role list on the server and again on the client. All of those are safe in an address as they are, so **nothing is encoded** (the RFC said the name is encoded); `.` and `..` are not names.
*   `!role`, `!role <name>` and `!roles` hide the chat line (`PlayerSay` returns an empty string); a request that is too soon is dropped without a message.
*   **Opening the tab by a command** finds the menu class in `menusIndexed`, a global that TTT2's `cl_help.lua` fills in, then calls `HELPSCRN:ShowMainMenu()` and `HELPSCRN:ShowSubmenu(class)`. That is read from the public sources and not tried in the game; if the class is not found, the player gets the chat line "Open the Server roles tab in the F1 menu." The tab's page takes the wanted role once when it is built, so clicking the tab later shows the list.
*   The tab's `ShouldShow` is false until the server has sent the base and id; the title and description are plain English strings.
*   The first-time chat line is "Opening the role guide from <host>." once per session.

### As built (descriptions from more places, added after the look)

A role whose addon ships no language text used to say only "The addon does not describe this role." Three sources were added, in this order of preference:

1. **The language files, searched wider.** By the role's name and its abbreviation, with more key prefixes and endings, then any English key that names the role and is about it (a real sentence, at least 30 characters), then the same keys in another language. Migration v18 clears the role hashes so the roles are sent again.
2. **The Workshop page of the addon the role comes from.** `traitordash_roleaddons` (`roleaddons.lua`) reads the file list at the start of each mounted addon's `.gma` (never the contents) and finds the role folders, so the link from role to addon is read, not guessed from names. `engine.GetAddons()` gives the file as an operating-system path that `file.Open` rejects, so the path is tried with its leading folders dropped against `BASE_PATH`, `GAME` and `MOD`. Checked on a real server: 172 addons, all opened (69 directly, 103 through `BASE_PATH`), 28 roles found, 70 ms. After a sync the bridge sends the list to `POST /api/v1/roleaddons` (migration v19: `role_addons`, `workshop_text`); the backend then reads the pages from Steam's public `GetPublishedFileDetails` (no key), in batches of 20, once a week (an hour after a failure), in the background. The page is stored as Steam sent it and cleaned when shown (BBCode and HTML removed; links and images dropped; sections about the addon's upkeep such as convars, changelog and links dropped; lines that only pointed at a link dropped; at most 1,500 characters), so a better cleaning needs no new fetch (migration v20 re-reads the pages stored before that) and shown as plain text with where it came from and, outside the game, a link. An addon that holds more than three roles is a collection (the TTT2 base, a pack): its page is not about one role and is not shown. A page that covers two or three roles says which others.
3. **What the server itself knows**: the team, and whether the role polices.

The role's own language text always wins over the Workshop page. The page text is untrusted: it is cleaned on the way in and rendered as text only.

## 5. Data Model
None. No migration. The pages read what is stored today.

## 6. Compatibility and Rollout
*   **Backend first:** the public pages and the embed work without any bridge change, so a server owner can already paste the address into a MOTD addon or a chat message.
*   **Bridge later:** an older bridge has no tab; a newer bridge on an older backend finds no `whoami` (`404`), turns the feature off and says so once.
*   **Admins:** the role address still works; the form is one click away (4.1). The tier change is visible in `tiers.ts` and in the README.
*   **Off switch:** `PUBLIC_ROLES=0` restores today's behaviour for the pages; unsetting `public_url` switches the tab off.
**As built (the look, added after step 3):** the pages are drawn as case files (paper folders on a dark desk, a tab and a stamp in the role's colour) instead of a table. Decided with the owner from rendered mockups; what it adds to the text above:
*   **Colours:** the role's own colour (`ROLE.color`, as TTT2 shows it) is read in the extractor worker (a colour the role sets itself in `PreInitialize` or `Initialize`; the mock's default white does not count; channels must be whole numbers 0 to 255) and stored as `#rrggbb` in `roles.color` (migration v17, which clears the hashes again so every role is sent once more). Without one the page uses its team's colour. Only a value matching `#rrggbb` is ever stored, because it ends up in a `style` attribute.
*   **Players:** `?players=N` (a whole number 1 to 128; anything else is ignored) puts away the roles whose minimum-players setting is higher than N: a dark dashed folder, a grey tab, the stamp "needs M+" and the line "K more players needed". A disabled role is shown separately (struck-through name, red stamp) and stays that way whatever N is; a role with no reported minimum is never put away. Order: roles that can appear, then the put-away ones, then the disabled ones, each in the old order. The count is part of the cache key and the ETag. The page offers 6, 8, 10, 12 and "all" as plain links; the F1 tab adds the number of players in the game (`player.GetCount()`) when it builds the address, so the page matches who is there when the tab is opened (not live: reopening the tab refreshes it). The page says "needs M+ players" and not "can appear": TTT2's role selection has more rules than this one setting.
*   **Fonts:** identical on every client, because the app serves them itself: Courier Prime (400, 700) and Barlow Condensed (600, 800), Latin subsets in `src/fonts/` with their SIL OFL texts, at `/fonts/<file>` with a one-week `immutable` cache. The policy gained `font-src 'self'`, nothing else. Text outside the Latin range (a translated description) falls back to the client's own font. The page CSS is inserted unescaped (it is a constant of the source file): escaping turned its quotes into `&quot;` and broke it.
*   Tests: `test/role_look.test.tsx` (colours, the stored-colour rule, every player-count case and its limits, the order, the fonts and the policy, the extractor), migration v17 and the address with the count in `test/role_public.test.tsx` and `test/rolemenu_bridge.test.ts`; mutation checks on each rule.
*   Delivery in order: (1) backend: the pages, the embed layout, headers, limiter, switches, tests; (2) `whoami`; (3) the bridge part with the Fengari harness and the client file; (4) a real client opening the tab on the real server, as the acceptance test.

## 7. Testing
*   **Backend, access:** an anonymous visitor gets `200` for the list and for a role of a known server; an unknown server or role is `404` (no redirect); an unusual name (slashes, dots, very long, encoded) is `404` and reads nothing; `/config` is `401` or redirected for anonymous and non-admin sessions and `200` for an admin; the admin sees the edit link, others do not; `PUBLIC_ROLES=0` makes the pages admin-only again; the sweep test knows every new route.
*   **Backend, content:** the description is chosen in the stated order and falls back to the generic line; a description containing `<script>`, `<img onerror>` and the language files' formatting marks is shown as plain text; the six numbers match `roleMetrics`; "unlimited" and "not reported" read as such; settings show label, value and default and nothing for an unreported value; `PUBLIC_ROLE_SETTINGS=0` removes the settings and keeps the rest.
*   **Nothing else leaks:** a test seeds the server with a token, admin ids, an audit row, a second server and a role with an extra field, and asserts none of them appears in the page, the embed or the headers.
*   **Embed and headers:** `embed=1` has no header, sign-in link, sidebar or script; its links stay in the roles section; every response has the CSP, `nosniff`, `Referrer-Policy`, `Cache-Control` and `ETag`; `If-None-Match` answers `304`; no `Set-Cookie` for an anonymous request; `noindex` on the embed.
*   **Limits:** the 121st request in a minute from one address is a `429` and another address is not affected; a cached answer is not re-rendered; changing the role's data changes the `ETag`.
*   **`whoami`:** returns the id for the token and `401` without; never another server's.
*   **Bridge (Fengari):** `!role` with no argument names the player's role; `!role Haunter`, `!role haunter` and `!role  haunter ` resolve to the same role; an unknown name answers in chat and sends no net message; a name with `/`, `?`, `..` or a very long string is refused; two requests within 2 s send one message; with `public_url` missing, `http://`, or `whoami` failing, the feature is off, the tab's `ShouldShow()` is false and the console says why once; the client builds `<base>/servers/<id>/roles[/<name>]?embed=1` with the name encoded, and a net message carrying an address instead of a name opens nothing; nothing contacts the dashboard at join. The two menu files are loaded in a fake of the menu classes (`CLGAMEMODEMENU`, `CLGAMEMODESUBMENU`, `vgui.Create`) to check that the tab is not an admin menu, has a page, and that `Populate` opens exactly the built address.
*   **Mutation checks:** remove the name validation, the encoding, the `https` check or the rate limit, and a test fails for each.
*   **Real client (acceptance):** on the real server, as a **non-admin** player: F1 shows the Server roles tab, with the borrowed icon; the page opens at a usable size, the text is readable, nothing scrolls sideways at 1280 by 720; `!role`, `!role <a role with a long description>`, `!roles` and a wrong name behave as above; as an **admin** both tabs are there. The page is also opened in a normal browser at phone width. The menu files are checked against the installed TTT2 core first (that the folder is scanned from the bridge's Lua path and that the files reach the client).

## 8. Alternatives Considered
*   **`gui.OpenURL` (the Steam overlay browser).** Needs the overlay to be enabled, leaves the game, and cannot be sized or closed by the game. The in-game panel is predictable.
*   **Our own window (a `DFrame` with a `DHTML`) opened only by command.** Independent of TTT2's menu code, but it needs its own frame, close handling and sizing, and players would have to know the command. The F1 tab is where they already look. The commands remain as shortcuts into the tab.
*   **Patching or replacing TTT2's Roles tab.** It is an admin menu by design; making it public would change what TTT2 shows to players and would break on updates.
*   **Sending the description as text to a native panel.** Works offline and needs no web address, but cannot show the live numbers of the server's own settings without sending them too, and duplicates the layout in Lua. The page already exists and is also useful outside the game.
*   **Pointing the tab at the existing admin page.** It needs a login that the game's browser cannot hold, and it would put a form in the player's hands.
*   **Opening the tab by itself at the round start.** Convenient, but it covers the screen at the moment the player needs it least and contacts the dashboard without being asked. A one-line hint is listed in section 9 instead.
*   **Letting the server send the address.** Simpler, but then a net message decides what the player's browser opens; the client builds the address from a base it was given once and a name.
*   **Keeping the pages admin-only and giving players a separate summary.** Two views of the same data to maintain.

## 9. Open Questions
*   **A custom icon** instead of the borrowed one? It needs a small file sent to players (and a fallback if it fails); only admins see the duplicate today.
*   **A hint at the round start** ("You are the Haunter. Type !role to read what it does"), off by default? It helps new players and costs one chat line.
*   **The tab's name and description** are plain English strings; TTT2 translates its own keys. Add language entries for the bridge's languages later, or keep English?
*   **Language:** the client's language could be sent as `?lang=` so the description comes in the player's language when the server has that file. Worth it now, or English first?
*   **Show the numbers of roles that are switched off?** The page says "disabled on this server" and keeps the numbers; hiding them is a different choice.
*   **Is the settings table fine to publish?** It lists the role's own menu items with their values. Most are replicated to every client by TTT2 already; the switch `PUBLIC_ROLE_SETTINGS` covers the operator who disagrees. Should the default be off?
