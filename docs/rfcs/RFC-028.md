# RFC 28: Player Names from the Steam Web API

> **Status: proposal (2026-11-12), not built.** Asked for by the maintainer when the voice page's list of people showed a SteamID64 for players the server had never seen. The small step (the game server sends the nicks of everyone connected) is built, see [RFC 27](./RFC-027.md), section 7. This RFC is the larger one: names for players the game server does not have at that moment. The facts about Steam's API below are from the author's own knowledge and have **not been checked against Steam's documentation**; section 8 lists what to verify first.

## 1. Abstract
The voice page shows who is on the voice chat. A player is known there by the SteamID64 they signed in with (RFC 13). Their name has to come from somewhere else. Today it comes from the game server (the nick of a player who is connected to it now) or from a finished round (the latest nick the dashboard stored). A person who is on the voice page but not in the game, and who has never finished a round on that server, shows as seventeen digits. Steam's Web API can give the profile name of any public account in one call for up to a hundred accounts. This RFC uses it as the last resort before the number.

## 2. Where a name comes from, in this order
1. **The game server, now** (RFC 27, 7): the nick of someone connected to it at this moment. Free, current, covers the players.
2. **The last round** the dashboard stored for that server (`round_players`): consistent with every other page of the dashboard, which shows these nicks.
3. **Steam** (this RFC): the profile name, for anybody else, with a cache.
4. **The SteamID64**, when nothing above knows the player (no key set, a private or missing profile, Steam not answering).

Why Steam is third and not first: the first two cost nothing and are what the other pages already show, and the in-game nick is what the other players know the person as (it can differ from the profile name on servers that rename players). Steam is for the people the other two do not know.

## 3. Design
*   **The key.** The backend reads `STEAM_API_KEY` from its environment. Unset means this RFC does nothing (step 3 is skipped), exactly as voice chat is off without a media server. The key is never sent to a browser or written to a page. It is a variable of the backend's Pelican egg, admin-only (`user_viewable` and `user_editable` false), empty by default, with a test that the egg declares it (like the `LIVEKIT_` ones).
*   **The call.** `ISteamUser/GetPlayerSummaries` for up to 100 SteamID64s at once (the page lists about ten people). Only `personaname` is used; nothing else of the answer is stored or shown.
*   **The cache.** A table `steam_names (steam_id PRIMARY KEY, name, fetched_at)` (a migration). A name is kept for 24 hours; a miss (no such profile, or no name) is kept for one hour so a missing player is not asked for again at every poll. The answer for a voice page is made from the cache, and a refresh is started in the background for the names that are missing or old, so a page never waits for Steam. Only the SteamIDs of people who are on the voice chat or who ask for a token are looked up: no crawling.
*   **Where it is used.** Two places: the join token's `name` (RFC 27, 7), when steps 1 and 2 know nothing, and the list the voice page shows before a player has joined (`/servers/:id/voice/people`, same rule). A person's name in the token is fixed when they join; to show a name that arrives later, the backend may set it on the participant in the media server (`UpdateParticipant`), which is the same call family as the routing; that is the one optional part and is left to the first version's result.
*   **If Steam fails.** A timeout of 3 seconds, no retry in the same request, the old cache entry (however old) is used, then the SteamID64. One log line per minute at most, never the key.
*   **Names are text from outside.** They are cleaned as every nick is (RFC 27: control characters out, at most 32 characters, shown with `textContent`, never as markup).

## 4. What it does not do
*   It does not ask Steam for anything else (friends, games, avatars). An avatar would be a separate decision.
*   It does not make the dashboard's other pages use Steam names; they keep showing the nick of the round.
*   It does not store a name for anybody who is not on the voice chat.
*   It does not use Steam's public profile pages (`steamcommunity.com/profiles/<id>?xml=1`): they work without a key, but they are not the API, they are rate-limited per address, and Steam may change them.

## 5. Tests
*   The lookup with a fake `fetch`: one call for several ids, a hundred at most, only `personaname` read, a bad answer and a timeout handled, the key never in a log line or an error.
*   The cache: a fresh entry is not asked for again; an old one is refreshed in the background while the old one is still shown; a miss is kept for an hour.
*   The order of section 2 for the token and for the people list.
*   The egg declares `STEAM_API_KEY`, admin-only, empty (`egg.test.ts`).

## 6. Deploy
Make a key (Steam asks for a domain name when it is made), put it in the backend's egg variable, restart. Without it nothing changes.

## 7. Privacy
A profile name is public on Steam for a public profile. It is shown only to signed-in users of this dashboard, and only for people who are on its voice chat. Nothing is sent to Steam but the SteamID64s, which are public.

## 8. Open (to verify before building)
*   Steam's current terms for the Web API key, its rate limit, and that a key is free.
*   Whether a **private** profile still returns its `personaname` (the maintainer believes it does; unverified).
*   Whether to set a late name on the participant in the media server (section 3), or to leave it until the player joins again.
*   Whether other pages should use the same cache for players the dashboard has never seen.
