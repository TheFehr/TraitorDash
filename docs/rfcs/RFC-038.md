# RFC 38: Proximity Voice, as a Choice of the Listener

> **Status: proposed (2026-11-20), not built.** Asked for by the maintainer as a "wild spin": with the 3D maps and the voice chat under our control, could proximity voice be done? Decided in the conversation: yes, **as an option each listener chooses**, because (1) the game's own locational voice is poor (audio quality; vertical distance is ignored, so a player a floor away comes through while one a door away is silent) and (2) proximity audio makes the best part of the game, talking with friends, harder (feedback from a player). Builds on RFC 27 (the voice chat and its rules), RFC 23 (the shared settings page) and, for stage B, RFC 10 (the floor-plan scan).

## 1. Abstract
Today every living player hears every other living player at full volume in the dashboard's voice chat (RFC 27, 2): the rules are global and deliberately know nothing but the phase and the list of the living (`voice.lua`: "No role, team or position is sent, so the voice side cannot leak one"). This RFC adds **proximity**: the volume, the muffling and the left-right position of each voice follow where the speaker is relative to the listener, with distance, floors and walls counted. It is **off for everyone by default**; a server turns it on as *available*, and **each listener chooses** Off, Soft or Full on their own device, and can **pin** friends who are then always heard in full.

## 2. Rules
1.  **Available by a server setting, never forced.** `traitordash_voice_proximity` (bool, default 0, group "Voice chat", applied at once, RFC 23). With it off nothing in the voice chat changes and the bridge sends nothing new.
2.  **The listener chooses, per device:** **Off** (today's behaviour, the default for everyone), **Soft** or **Full**; remembered on the device like the volumes. A listener who switches proximity on gets Soft first.
    *   **Soft:** voices get quieter and muffled with distance and walls but **never below a floor** (35 % of their volume; the muffling capped at one step). Friends across the map stay audible, and there is still a sense of who is near.
    *   **Full:** the distance and walls apply properly, down to silence.
3.  **Pinned players are always heard in full.** Next to each player's volume and mute on the voice page (kept on the device by SteamID64, as those are): "Always audible". A pinned player skips proximity (gain 1, no muffling, centred) in every mode. A friend group plays on Full and still hears itself.
4.  **The existing rules stay:** only the living in a round are affected. The dead hear everyone (at full volume: proximity is for the living), and outside a round everyone hears everyone, as RFC 27 says. Proximity only scales voices that the rules already allow.
5.  **Positions never leave the game server.** The bridge computes, for each living listener and each living speaker, three small numbers (gain, pan, muffling) and sends **only those**. The voice side and the browsers never see a position, a floor or a map coordinate; they learn how loud, how muffled and from which side a voice should sound, which is what the listener hears anyway. The sentence of `voice.lua` quoted above stays true for positions.

## 3. Design, stage A: distance, floors and walls (built first)
*   **The model (in the bridge, per pair, at about 5 times a second while a round is active and proximity is available):**
    *   **Distance:** `d = sqrt(dx^2 + dy^2 + (v * dz)^2)` between the two players' eye positions, with `v` the **vertical factor** (default 2: a floor above counts as far, which fixes "above and below are heard, one door away is not").
    *   **Gain:** a smooth curve, 1 up to `d0`, falling to 0 at `d1` (for example a squared ease: `g = (1 - (d - d0) / (d1 - d0))^2` clamped), so there is no hard cutoff. Defaults to tune by ear: `d0` 300, `d1` 1 500 units.
    *   **Walls and floors:** one line trace between the two players against the world (solid, as the engine's own trace sees it: a closed door is solid, an open door is not); the number of solid hits (capped at 3) is the **muffling step** `m` (0 clear, 1, 2, 3), and each step also lowers the gain a little (`wall` factor, default 0.7 per step).
    *   **Pan:** the horizontal angle of the speaker relative to the **listener's view yaw**, from -1 (left) to 1 (right), 0 straight ahead or behind (no front/back cue: this is a stereo pan, not head-related audio).
*   **The message:** the bridge adds a `prox` object to its existing round message (`POST /api/v1/voice`, RFC 27): for each living listener, a list of `[speaker, gain 0..100, pan -100..100, muffle 0..3]`, only for pairs the rules allow, only when the setting is on, sent when a row changed beyond a small threshold or on a slow refresh. An old backend ignores the field; an old bridge sends none (the page then falls back to Off).
*   **The backend** (`VoiceHub`, `voice.ts`) validates and forwards each listener's own row **only to that listener**, as a LiveKit data message to their identity (`SendData`, lossy, a few hundred bytes at 5 Hz for ten players: the Twirp client the hub already uses; verify the call exists in the server version in use: if not, the voice page polls a route instead). The row is dropped when the listener's rules say they hear nobody, when the state is stale (the 20 s rule of RFC 27) or when the round is over.
*   **The browser** (`src/voice.ts`): each remote voice goes through a Web Audio chain: source from the track, a gain (proximity gain, then the player's volume, mute and the Soft floor), a low-pass filter whose cut-off follows the muffling step (clear 20 kHz, then about 3 kHz, 1.2 kHz and 600 Hz), a stereo panner, the output; every change is **smoothed** (about 80 ms) so a 5 Hz update never clicks. Pinned players bypass the proximity values; Off bypasses everything for that listener and the page behaves as today (the per-player audio element volume of RFC 27). Chrome needs the remote stream to be attached to an audio element as well for Web Audio to run on it (a known browser behaviour; the voice library has a mode for it): the implementer reads the library and verifies.
*   **The page:** a control "Proximity" with Off / Soft / Full (shown only when the server has proximity available, i.e. the page was told by the join answer), and the "Always audible" toggle for each player in the list; the voice page's layout rules apply (fixed sizes, no layout jump, `--space-N` variables, contrast); a short muted line says what the modes do.
*   **Settings** (shared settings page, group "Voice chat", declared in `settings.lua` and `bridgeSettings.ts`, each with its test of the two lists in sync): `traitordash_voice_proximity` (bool, default 0), `traitordash_voice_prox_near` (units, `d0`), `traitordash_voice_prox_far` (units, `d1`), `traitordash_voice_prox_vertical` (the factor `v`, 1 to 5), `traitordash_voice_prox_wall` (the gain factor per solid hit, 0.3 to 1). Applied at once.

## 4. Stage B: a precomputed fade map (only after stage A has been heard)
A straight line between two players says nothing about how sound **travels**: around a corner through an open door, up a stairwell. A **fade map** is a table, built once per map, of the **sound-path distance** between coarse places of the map, measured through open space (the walkable plan of RFC 10), so a room above is far by the stairs and a room round a corner through a doorway is near.
*   **Built by the backend** when the plan of a map is stored (RFC 10, 4.5: the plan is uploaded after a scan): coarse cells (128 to 256 units: the plan's 64-unit cells merged, storeys kept apart), a **range-bounded Dijkstra** from each coarse cell over the walkable graph (a step between neighbouring floors of at most 48 units connects, as in the scan), stopping at the far distance `d1`; the result is **sparse**: for each cell the list of cells within range and their path length in 32-unit steps (one byte). Pairs beyond the range are simply absent (inaudible). Size and build time are measured on the maintainer's maps before stage B is accepted (the plan itself is about 55 KB for a typical map).
*   **Used by the bridge:** it downloads the table of the current map (`GET /api/v1/fademap?map=...&fingerprint=...`, bridge tier, cached on disk for the map) and, per pair, looks up the two cells and reads the path length. The distance used for the gain becomes `min(path distance, straight 3D distance * through-wall factor)`: sound goes the shorter of "around" and "through". The live trace of stage A stays for what a table cannot know (a closed door, a prop in the way).
*   **Fallback:** a map without a plan, or a bridge that cannot fetch the table, keeps stage A's model: nothing breaks.
*   Stage B is its own build and is **not** started before stage A has been tuned by ear on the real server: the table's value is only proved by listening.

## 5. What this does not do
*   No head-related (HRTF) or height cues, no reverb or room acoustics, no front/back distinction: stereo pan, volume and a low-pass only.
*   No change to who may hear whom (RFC 27 stays the authority), no team or role channels (the voice side knows no teams, by design), and no change to the game's own voice (it stays off while this chat is used).
*   No positions to browsers (rule 5), and nothing is stored: the numbers live for the next update only.

## 6. Tests (what must fail on a broken build)
*   **Bridge model** (Fengari harness, `voice.lua`'s tests): the gain is 1 up to `d0`, falls monotonically and smoothly to 0 at `d1`, never negative or above 1; the vertical factor (a speaker one floor up at the same horizontal distance is quieter than one on the same floor); the muffling step counts solid hits and is capped; the pan sign follows the listener's yaw (a speaker at the listener's right is positive, left negative, behind or ahead zero); only living pairs the rules allow appear; the dead and the preparation phase send no `prox`; the setting off sends nothing and costs nothing; the rate and the change threshold; positions appear nowhere in the message (a test that scans the sent JSON for the coordinates used).
*   **Backend:** validation of every field (gain, pan and muffle ranges, speakers are players of the room, the row belongs to its listener); the row goes only to its listener; stale or round-over rows are dropped; an old bridge without `prox` and a new backend work; the settings are declared in both lists.
*   **Browser** (the page code tests with stubs): a gain row sets the gain, filter and pan values as the tables say, smoothed; the Soft floor (35 %) and the muffling cap; Full reaches silence; pinned players ignore the row; Off ignores rows; the mode and the pins are remembered per device; proximity unavailable hides the control; the audio-element fallback for Web Audio is in place.
*   **Layout:** the new control and the pin toggles keep the page's layout rules (no jump between modes, contrast, 390 px).
*   **Mutation checks** on the model's key rules (the vertical factor, the wall count, the pan sign, the soft floor, the pin bypass, rows to the wrong listener).

## 7. Verification on the real server (required before it is called done)
A listening session with friends, which no test can replace: stand a floor above each other (a voice should be faint and muffled, not clear), one door away (clear through an open door, muffled through a closed one), at the far end of the map (Soft: faint but there; Full: silent), and check the pan against where people stand. Tune `d0`, `d1`, the vertical factor and the wall factor by ear and write the final defaults into this RFC. Unverified until then: the cost of one line trace per pair on the server (about 90 per update with ten players), the availability of `SendData` in the media server's API version, and Web Audio on remote WebRTC streams in the browsers the players use.

## 8. Open
*   The defaults of the distances and factors (by ear, section 7).
*   Whether Soft should be the default for every listener once the server has it available (the maintainer's concern is that proximity makes talking with friends harder, so the proposal is Off for everyone until they choose).
*   Whether to show a small "near you" indicator in the player list (who is audible right now): not planned.
