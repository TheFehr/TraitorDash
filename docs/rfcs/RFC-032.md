# RFC 32: A Coverage List for the Map Format (What the 3D Pipeline Draws, Ignores on Purpose, and Misses)

> **Status: built (2026-11-15), stage A; see 11, "As built". Not deployed.** Asked for by the maintainer after the pool of `ttt_67thway_rework_b1` turned out to be missing from the 3D view ("any other materials we just ignored? is there like a catalogue/list of materials this map format supports so we can map our progress?"). This RFC is the list and the measurement; [RFC 33](./RFC-033.md) is the implementation of what the list shows as missing. Builds on RFC 11 (map geometry), RFC 18 (fuller 3D maps).

## 1. Abstract
The map pipeline (`backend/src/maps/bsp.ts`, `meshGlb.ts`, `mapgeometry.ts`) reads a Source map and draws what it knows: the world's floors and walls, displacements, liquid faces, some brush entities, props, textures. Everything else is dropped, and **nothing records what was dropped**. The pool was found by a screenshot; the next missing thing would be found the same way.

This RFC adds (1) a **registry**: one table in code that names every kind of thing a map can hold that the pipeline has a view on (surface flags, brush-entity classes, special materials, features of the file we do not read) with its status; (2) a **coverage record** that the extractor writes for each map it builds, counting what the map contains per registry entry; (3) a **page** for admins that adds the records of all the maps of a server and ranks the gaps; and (4) a **document**, `docs/MAP_COVERAGE.md`, the same table in prose, with the measurement on a real map. Deploying it and rebuilding the stored maps gives the numbers on the maintainer's real maps; those numbers decide what RFC 33 builds.

## 2. Statuses
Every registry entry has exactly one of:

| Status | Meaning | Example |
|---|---|---|
| `drawn` | The pipeline draws it. | world floors and walls, displacements, props, `func_door` at its starting place |
| `invisible` | Not drawn, and nothing is lost: a player never sees it. | `trigger_*`, `func_clip_vphysics`, `func_areaportal`, sky and `tools/` materials, `SURF_SKY`, `SURF_NODRAW`, `SURF_HINT`, `SURF_SKIP` |
| `gap` | A player sees it and the pipeline does not draw it. These are what RFC 33 builds, ranked by the survey. | `func_water_analog`, `func_button`, `func_breakable_surf` (breakable glass), `func_illusionary` |
| `not read` | A feature of the file the pipeline does not read, with a note on what drawing it would take. | lightmaps (`LUMP_LIGHTING`), overlays (decals), cubemaps, detail props, visibility |
| `unknown` | Seen in a map and not in the registry: new things show up here by themselves and are a task. | any brush-entity class that nobody has classified |

Which entries are `gap` is a judgement; the registry carries a short note for it, and the maintainer can change a status by changing one line (the test checks that every entry has a note).

## 3. The registry
`backend/src/maps/coverage.ts` exports `COVERAGE`, a list of `{ kind, key, status, note }`:

*   **`flag`** (surface flags of a face's texinfo, from the BSP format): `LIGHT, SKY2D, SKY, WARP, TRANS, NOPORTAL, TRIGGER, NODRAW, HINT, SKIP, NOLIGHT, BUMPLIGHT, NOSHADOWS, NODECALS, NOCHOP, HITBOX`. (`SKY2D`, `SKY`, `TRIGGER`, `NODRAW`, `HINT`, `SKIP` are the extractor's `SKIP_FLAGS`; `WARP` is water, RFC 18, 4.1; `TRANS` and the lighting flags are drawn as ordinary faces and their effect is not modelled.)
*   **`material`** (name rules): sky pictures (`skybox`, `*sky`), `tools/*` (RFC 18, 4.1a).
*   **`class`** (brush entities, classes that own a model `*N`): every class the pipeline lists today (`FIXTURE_CLASSES`: `func_brush, func_wall, func_breakable, func_lod, func_wall_toggle` as `drawn`; `MOVABLE_CLASSES`: doors, lifts, trains and the rest, as `drawn` at their starting place) and the ones it does not: `trigger_*`, `func_clip_vphysics`, `func_areaportal*`, `func_occluder`, `func_precipitation` (`invisible`); `func_button`, `func_breakable_surf`, `func_water_analog`, `func_illusionary`, `func_door` variants not listed (`gap` or per note); everything unlisted is `unknown`.
*   **`feature`** (parts of the file): lumps and what lives in them: displacements (`drawn`), props (static props, game lump: `drawn`; detail props: `not read`), the pak file's textures (`drawn`, RFC 18, 5), lightmaps, overlays, cubemaps, visibility, the 3D skybox (`invisible`: removed on purpose, RFC 11), fog and light entities (`not read`).

The registry is **the** catalogue: the document of section 6 is made from the same facts, and a test fails if an entry has no note or a status outside the five.

## 4. The coverage record
The extractor already counts a few things (`stats`: faces, skipped, `skippedByMaterial`, `otherModelFaces`, `waterFaces`, `fixtureModels`, `movableFaces`, displacements). The record extends that, per map:

*   faces of the world model by surface-flag set (`BUMPLIGHT: 1381`, `SKY|NOLIGHT: 219`, ...), and by status of the face (drawn as floor / wall / water, skipped by flag, skipped by material);
*   brush entities by class: `{ entities, faces, status }`, with a class that is not in the registry marked `unknown`;
*   the sizes of the lumps the pipeline does not read (lighting, overlays, cubemaps, the game lump, the visibility data) and the counts of the point entities that matter for the registry (overlays, `light*`, `env_*`, `info_particle_system`: counts only, top 30 classes);
*   the number of materials the map names and how many the pipeline could texture (already in `GeometryInfo.surface`).

It is a small JSON object (a few kilobytes), stored with the mesh's `GeometryInfo` (`mapgeometry.ts`, the `info` that `map_geometry` already keeps as JSON): **no new table and no migration.** `MESH_VERSION` and `MESH_VERSION_GAME` go up by one so that every stored mesh is rebuilt in the background and gets a record; no new download happens that the rebuild would not have done anyway. A map that cannot be rebuilt (its file is gone) shows "no record" in the list and is not an error.

The record only counts: it does not change what is drawn, so the mesh bytes of an existing map do not change.

## 5. The page
`GET /servers/:serverId/map-coverage` (tier **admin**, RFC 13; the path is outside `/maps/:map`, which is a map's name): one table for the server.

*   **Totals by status:** faces and entities, over all maps with a record, and how many maps have none yet.
*   **The gaps, ranked:** each `gap` and `unknown` entry with the number of maps it appears in, the total faces (entities for classes), and the map with the most. This is the list RFC 33 works from.
*   **Per map:** a row for each map with its counts of gap faces and `unknown`, linking to the map's page; a click opens that map's record (the counts above).
*   **The not-read features:** the lumps and their sizes, summed.
*   A link to this page from the maps page's admin controls (where "Build geometry" is) and from the admin overview if there is one; the page uses `PageHead`, the case-file card and the spacing scale (RFC 30), and does not jump.

It is an admin page because it is a maintenance tool, not a statistic for visitors.

## 6. The document
`docs/MAP_COVERAGE.md`: the registry as tables by kind and status, a sentence for each entry, and the **measurement of 2026-11-15 on `ttt_67thway_rework_b1`**, made by the record itself (corrected from the first survey, which mixed drawn and undrawn classes): 11 571 world faces: 9 895 with no flag, 1 381 `BUMPLIGHT`, 219 `SKY|NOLIGHT` (all `tools/toolsskybox`), 50 `TRANS`, 18 `WARP|NOLIGHT|NOSHADOWS|NODECALS` (the coast water), 8 `NOPORTAL`; by outcome 2 759 floor, 7 989 wall, 484 ceiling (left out on purpose), 18 water, 94 displacement, 219 left out by a flag, 8 by material (`tools/toolsblack`). Brush entities: 72 of the drawn classes (44 fixtures, 28 of the kinds that move), of which 71 are drawn: one `func_brush` (6 faces) has a parent entity and is not; not drawn, by class: `func_breakable_surf` 29 entities and faces, `trigger_teleport` 11 entities 66 faces, `trigger_multiple` 8/47, `func_button` 6/36, `func_clip_vphysics` 4/24, `trigger_hurt` 2/12, `env_embers` 1/6, `trigger_soundscape` 1/6, `func_water_analog` 1/2, `ttt_traitor_check` 1/0 (unknown to the registry); the 234 faces of models that are not drawn are these 228 plus the parented `func_brush`. Not read: lighting 6.6 MB, overlays 28 KB, cubemaps 4 KB, game lump 2.2 MB, visibility 188 KB (decimal units; the lighting lump of high dynamic range is empty). The record is 3 KB of JSON. After the deployment, the document gets a second table, the totals over the maintainer's server's maps, copied from the page; it is the snapshot that RFC 33 starts from.

## 7. Limits, safety and cost
*   The record is built from the counters of the existing face loop and the entity read; no extra pass over the faces (the flag tally is one more increment per face). The extractor's limits (`SurfaceLimits`, entity caps) are unchanged. Cost: negligible.
*   Class names, material names and counts come from the map file, which is untrusted: names are cut to 64 characters and limited to the characters of a class name (`[a-z0-9_*]`), the number of classes in a record to 200 and the sum to 30 point-entity classes; anything over is counted in an `other` bucket. They are shown escaped by the page (the project's normal rendering).
*   The page is admin-only and read-only.

## 8. Stages
*   **A (this RFC):** the registry, the record, the version bump, the page, the document with the measurement, the tests; deployed.
*   **B:** after deployment and the rebuild of the stored maps, the totals are copied into the document and the gaps are ranked; RFC 33 (the pool and the next ones in the ranking) starts from them. Not built by this RFC.

## 9. Tests (what must fail on a broken build)
*   Registry: every entry has a kind, a key, a status from the five and a non-empty note; no duplicate (kind, key); every class in `FIXTURE_CLASSES` and `MOVABLE_CLASSES` is `drawn` (so changing the code's lists without the registry fails); every surface flag of the BSP format is present.
*   Record, on a small constructed BSP (the tests of RFC 18 build one): counts of faces by flag set and by outcome match a hand count; a brush entity of a listed class is counted `drawn`, a `func_button` as `gap`, a class that is not in the registry as `unknown`; the sizes of unread lumps are reported; names are cut and escaped; the class cap and the `other` bucket work; a map with no brush entities gives an empty but valid record.
*   `GeometryInfo` with and without a record both load (an old stored mesh has none); the stored mesh bytes of the same input are identical to before the change (the record does not change the drawing).
*   The mesh version numbers are bumped and a stored mesh of the old version is rebuilt (the existing version tests).
*   The page: tier admin (the tiers test), anonymous and user get the answers the tiers say; the totals add up; gaps are ordered by faces; a map with no record is listed as such; no layout jump; contrast; page head.
*   The document: a test compares the registry's keys with the document's tables, so a new entry cannot be left out of the document.

## 10. What cannot be verified here
*   The numbers over the maintainer's other maps: only `ttt_67thway_rework_b1` was measured (the file is a public Workshop item, downloaded with the pinned helper of RFC 11). The survey of all maps is what this RFC delivers once deployed.
*   Whether `gap` is the right status for each class: it is a judgement of what a player sees (a button is pressed by players; breakable glass is a window), to be corrected from what the replay looks like.
*   Whether a very large map's record stays small: bounded by the caps in 7, not measured on a huge map.

## 11. As built (2026-11-15)
Built as designed (registry `backend/src/maps/coverage.ts`, record in `GeometryInfo.coverage`, page `GET /servers/:serverId/map-coverage`, `docs/MAP_COVERAGE.md`, mesh versions 13 and 14). Differences and details:
*   **Drawn classes come from the code's own lists:** the registry reads the alternatives of `FIXTURE_CLASSES` and `MOVABLE_CLASSES`, so they cannot drift; the document test then asks for a row for any new one. The extractor's lists must stay of the form `^prefix(a|b)$`, or the module refuses to load.
*   **Flag sets are written in the order of the bits** (`NOLIGHT|BUMPLIGHT`, not `BUMPLIGHT|NOLIGHT`); a bit the format does not name is `OTHER`, which the registry does not know, so it shows as unknown. Lighting is lump 8 plus the HDR lump 53.
*   **Outcomes** also count `ceiling` (left out on purpose); the record also keeps faces left out by material per rule (`sky`, `tools/*`) and, per drawn class, `parentedFaces`: an entity with a parent entity is not drawn whatever its class (six faces here).
*   **Point entities that belong to a not-read feature** (lights, fog, `info_overlay`, `env_cubemap`) are counted over all classes in `pointFeatures`, apart from the top 30 list. The census of classes is also bounded while the entity lump is read (5 000 classes). Brush classes are ranked unknown, gap, then the rest before the cap of 200.
*   **Totals by status** count a world face once, by its flags (unknown over gap over invisible over drawn; a face left out by material is invisible); ceilings count with the drawn. Statuses are looked up in the registry when the page is made, not read from the record, so a changed line shows without a rebuild.
*   **The page** is in `MapCoveragePage.tsx` with its sums in `services/coveragereport.ts`; a map's record is in a `<details>` below the table of maps. It redirects non-admins to the front page like the other admin pages. Linked from the maps page for an admin when the 3D feature is on (not from the map page, and there is no admin overview page with a place for it).
*   **After RFC 33 (2026-11-15):** the registry has no `gap` entry any more: the classes of the survey are `drawn` (they come from the code's lists, now four: `FIXTURE_CLASSES`, `MOVABLE_CLASSES`, `WATER_CLASSES`, `DECORATION_CLASSES`) or `invisible` (the six zones of RFC 33, 4.6). The status `gap` stays defined for what a later map brings; the sums of the page take an optional status function so that a gap can be tested. The constructed map of the tests spells its button and water brush with one letter changed (same length), so that its mesh bytes stay as they were.
*   **Mesh unchanged:** a test pins the hash of the surfaces and of the GLB of a constructed map, taken before the record code; the surfaces of the real map hash the same before and after.
*   **Checked in Chromium** (v1.64, 1100 and 390 px): no layout shift, no sideways overflow of the page, contrast 4.8 : 1 or better. Not verified: the page on the real deployment with the real fonts, and with a hundred maps; the nominal "unknown" `ttt_traitor_check` is a real finding to classify.
