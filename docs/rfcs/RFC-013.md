# RFC 13: Sign-in for Everyone: Anonymous, Signed-in and Admin

> **Status: built (2026-10-19), including the replay page and `track.json`, which use the same gate. Not built: `SIGNIN_PLAYERS_ONLY` and a page for the view log.** It extends [RFC 7](./RFC-007.md) (signed sessions, the admin allow-list, CSRF) and is the access model that [RFC 11](./RFC-011.md) (the map's 3D geometry) and [RFC 12](./RFC-012.md) (the round replay) use for their heavier content.

## 1. Abstract
Today there are two kinds of visitor: **anonymous**, who read the public pages, and **admins**, who sign in with Steam and are listed in `ADMIN_STEAM_IDS`. Steam itself lets any account prove who it is; TraitorDash refuses everyone who is not an admin. This RFC adds a middle tier. **Any Steam account can sign in** and becomes a **signed-in user**; admin rights still come only from the allow-list, checked on every request, exactly as in RFC 7. Content that is heavier to serve or more detailed than the public pages (the 3D map and **the round replay**, its track included) needs a signed-in user, so it can be rate limited per account and not only per address. The feature is **off until the operator turns it on**, and an instance that does not behaves exactly as it does today.

## 2. Motivation
*   **Heavier content needs a gate that is not "admin".** A 3D mesh of a map is hundreds of KB to a few MB, and a replay's track a few MB more. Anonymous addresses are easy to rotate and impossible to attribute; a Steam account is neither free to churn nor anonymous. A login wall is not a lock (any Steam account will do, see 6.2), but it makes limits per person possible and keeps casual scraping out.
*   **A place for per-player features.** "Highlight me in this replay", "my rounds" and similar need to know who is looking, without making them admins.
*   **No new infrastructure.** Steam sign-in already works and is hardened (RFC 7); this reuses it and the existing audit log, and creates no user table.

## 3. Current State (summary, not a change)
*   The login flow (`/auth/steam`, `/auth/steam/callback`) is hardened: a one-time state cookie, checks of the OpenID response, verification with Steam. The callback then does `if (!isAdmin(steamId)) return 403` and sets **no cookie** for anyone else.
*   The session is a signed cookie (`steam_id`, or `__Host-steam_id` over https) that carries only the SteamID64. `getAdminId` verifies the signature **and** looks the ID up in `ADMIN_STEAM_IDS` on every request, so removing an admin takes effect at once and the cookie alone grants nothing.
*   The page header offers "Login with Steam" to everyone who is not an admin and a logout form to admins.
*   Public pages (round stats, the maps list) call `getAdminId` only to decide whether to show admin extras.

## 4. Design

### 4.1 The three tiers
| Tier | Who | Gets |
|---|---|---|
| **Anonymous** | no session | the public pages: round stats, player pages, the maps list, round results (with a link to each round's replay, marked as needing sign-in); **no replay**, 2D or 3D |
| **Signed in** | any Steam account with a valid session | everything anonymous gets, plus the **round replay** (its page, its `track.json`, top-down and 3D) and the **3D map** (`mesh.glb`), RFC 11 and 12, and personal features |
| **Admin** | a SteamID64 in `ADMIN_STEAM_IDS` | everything: the role settings, servers, tokens, pairing, scans, pinning, retention, geometry switches |

Each tier includes the one below it. An admin is just a signed-in user who is also on the list.

### 4.2 Signing in
*   **The callback stops refusing non-admins** when open sign-in is on (4.7). It sets the same signed session cookie for any valid Steam login, with the same lifetime (one week), flags and `__Host-` prefix. Nothing about the Steam verification changes.
*   **No server-side user record.** The session is the cookie; no user table is created. The only thing stored about a signed-in user is the view log of gated content (6.3).
*   **Admin is still decided live.** The session helper returns the SteamID64 and, separately, whether it is on the allow-list *now*. A signed-in user is never promoted by anything in the cookie; an admin removed from the list is a plain user from the next request.
*   **Where to go afterwards.** Today the callback always redirects to `/`. A visitor who clicks "Sign in to see this map in 3D" should come back to that page. `GET /auth/steam?next=<path>` accepts a **same-site relative path only** (it must start with a single `/`, contain no `\`, no scheme and no `//`, and be at most 200 characters); the path is stored with the one-time login state and used after the callback. Anything else is ignored and the visitor lands on `/`. This is the one place a redirect target comes from the request, so it is tested against the usual open-redirect tricks.

### 4.3 One place that decides
A single helper, used by every route, replaces ad-hoc checks:
```
getSession(c)  ->  null                              (anonymous: no cookie, a forged or expired one)
               ->  { steamId, admin: boolean }       (signed in; admin is the allow-list, checked now)
requireUser   (signed in, else 401 for data and a redirect to sign-in for pages)
requireAdmin  (admin, else 401/403; today's requireSession)
```
`getAdminId` stays, with its meaning unchanged (the ID if admin, else null), so no existing admin route changes behaviour. **Fail closed:** a cookie that does not verify, or a SteamID64 that does not look like one, is anonymous.

### 4.4 What needs which tier
*   **Anonymous:** as today.
*   **Signed in:** the replay (`/servers/<id>/rounds/<round_id>/replay` and its `track.json`), the 3D viewer, and `GET /servers/<id>/maps/<map>/mesh.glb` (RFC 11, 12). For a page, an anonymous visitor is sent to sign-in with `next` set to the page and comes back to it; for data (`track.json`, `mesh.glb`) the answer is `401` with a short JSON body saying that sign-in is needed.
*   **Admin:** unchanged.
*   **A replay cannot be public.** Because the track needs a signed-in user, there is no anonymous replay, not even a top-down one on the floor plan. A link to a replay works for anyone who has a Steam account and signs in. This is accepted (section 9 lists the alternative).
*   **The rule for new routes:** a route is anonymous only if it is listed as public; a route that does not name its tier is admin-only. A test enumerates the application's routes and fails on a route whose tier is not declared.

### 4.5 The interface
*   The page header shows **Sign in with Steam** to anonymous visitors, and for a signed-in visitor their SteamID64 (the only identity the cookie holds; persona names would need a Steam Web API key and are out of scope), a small "admin" mark for admins, and the logout form for both. The "Servers" link stays admin-only.
*   A locked feature says so where it would be: a replay page offers "Sign in with Steam to see this round in 3D" next to the top-down view that anonymous visitors do get, instead of hiding the option.
*   Sign-in is not forced anywhere that is public today.

### 4.6 Limits per account
Heavy endpoints are rate limited **per SteamID64** for signed-in users and **per client address** for anonymous requests (the address only behind `TRUST_PROXY=1`, as for pairing), with `429` and `Retry-After`:
*   `mesh.glb`: 30 a minute per account.
*   `track.json`: 30 a minute per account (RFC 12).
*   An anonymous request to a gated endpoint is answered `401` at once and costs almost nothing; those are limited per address (30 a minute) only to keep a loop from filling the log.
A limit hit is logged at a limited rate and never writes to the audit table.

### 4.7 Switch and compatibility
*   **`OPEN_SIGNIN=1`** (an environment variable, in the egg as a variable) turns on sign-in for non-admins. **Default off**: the callback refuses non-admins exactly as it does today and no tier above anonymous exists besides admin. The 3D features of RFC 11 and 12 are then available to admins only (they need a signed-in user, and the only signed-in users are admins).
*   **`BLOCKED_STEAM_IDS`** (comma-separated, default empty): accounts that may not sign in or keep a session, for the one abusive user an operator will eventually have. It is checked with the allow-list, on every request. An admin cannot be blocked by it (the allow-list wins), so an operator cannot lock themselves out by a typo.
*   An old session cookie of an admin keeps working. Turning the switch off ends every non-admin session at the next request, because the session helper refuses non-admins while it is off.

### 4.8 As built
*   `middleware/session.ts`: `getSession` (null, or `{ steamId, admin }`; the allow-list is read on every call, the shape check and the switch and block list apply to non-admins only), `getAdminId` on top of it with the meaning unchanged, `safeNext`, `signinUrl`. `OPEN_SIGNIN`, `BLOCKED_STEAM_IDS` and `VIEW_LOG_DAYS` are read **at each request**, so turning one off takes effect at once.
*   `routes/tiers.ts` names the tier of every route; `test/signin.test.ts` fails on a route that is missing or does not behave as declared (a signed-in user is refused by every admin route, an anonymous visitor by every admin and user route, a session cookie is not a bridge credential).
*   `services/gates.ts`: the gate for signed-in content with its own per-endpoint counters (30 a minute per account; per client address for anonymous requests, only behind `TRUST_PROXY=1`).
*   **Pages:** the maps list offers a map that has a 3D view (a link to a signed-in visitor, a "sign in" link when sign-in is open, nothing otherwise); the map page is for signed-in users (an anonymous visitor goes to sign-in when it is open, back to the list when not) and shows a plain user only the 3D view; the floor plan and the geometry switch stay admin-only. The 3D feature still needs the operator's `MAP_GEOMETRY=1`.
*   The `td_next` cookie holding `next` is client-controlled, so it is validated again at the callback.
*   Not built here: the replay page and `track.json` (RFC 12, step 3), the SteamID64 not being in the access log (the server writes none), `SIGNIN_PLAYERS_ONLY`.

## 5. Data Model
No new table. Sessions are cookies; limits are in memory, as the other limiters are. The view log uses the existing `audit_log` (new action names `VIEW_REPLAY`, `VIEW_MESH`); an index on `(steam_id, action, details, timestamp)` (migration v14; the column is called `timestamp`) makes the once-an-hour check cheap, and a cleanup removes rows older than `VIEW_LOG_DAYS`.

## 6. Security and Privacy

### 6.1 What changes in the threat model
*   **The cookie used to imply admin; it will not.** RFC 7's code treats a valid cookie as proof of an admin only because every non-admin was refused at login. After this RFC a valid cookie is any Steam account, so **nothing may treat "has a valid cookie" as "is an admin"**. The protection is that every admin route goes through the allow-list check (3). It is made a test, not a hope: with a non-admin session, every route of the application is requested and each admin route must refuse (`401`/`403`/redirect). A route that is added without a declared tier fails the build (4.4).
*   **Forging, replay and CSRF are unchanged:** the signature, the `__Host-` prefix, `HttpOnly`, `SameSite=Lax` and the same-site `Origin` check on every `POST`/`DELETE` apply to every tier.
*   **Login CSRF and open redirect:** the one-time state still binds a login to the browser that started it; `next` is validated as in 4.2.

### 6.2 What a login wall does and does not do
It does not keep determined people out: a Steam account is cheap, and anyone with one can sign in. It does give **accountability** (limits and, if ever needed, a block by SteamID64 rather than by an address that changes), and it filters unattended scraping. It must not be described, in the UI or the docs, as a secret.

### 6.3 Privacy, and the view log
*   The server learns a visitor's SteamID64 only from the cookie it has just verified. **Nothing is stored about a visitor who only browses the public pages**, and no user record is ever created.
*   **Views of gated content are logged** (decided). Opening a replay, a map's mesh or the 3D viewer writes one row to the existing audit log: the SteamID64, the server, what was opened (`VIEW_REPLAY` with the round, `VIEW_MESH` with the map) and the time. A user's repeated opens of the same thing within an hour are one row, so a replay that is reloaded or a scrubber that refetches does not flood the log. The purpose is abuse handling (one account pulling everything), not statistics about people.
*   **Retention:** view rows older than **90 days** (`VIEW_LOG_DAYS`, `0` switches the logging off) are deleted at start-up and once a day. They are **not** shown to the people they are about in this RFC; an admin reads them in the audit log (a page for it is a later feature).
*   **Telling users:** the sign-in prompt and the install guide say that views of replays and 3D maps are logged with the account's SteamID64 for 90 days. Steam shows its own consent page at login; TraitorDash asks for nothing more than the public identifier.
*   The SteamID64 of a visitor is not written to the access log; admin and denied-admin events are logged as today.

### 6.4 Operator control
Open sign-in is the operator's decision, off by default, and reversible at once (4.7). The install guide must say that turning it on lets any Steam account sign in.

## 7. Rollout
*   Additive and off by default. Delivered in order: (1) the session helper with the route-tier declarations and the sweep test, behaviour unchanged; (2) the callback change, the switch, `next` and the header; (3) the gated endpoints as RFC 11 and 12 add them.
*   RFC 11's open question about a public mesh and RFC 12's "public by default" are **already updated** to this model: the mesh, the replay page and the track all need a signed-in user.

## 8. Testing
*   **Callback:** with the switch on, a non-admin gets a session and an admin still does; with it off, a non-admin gets `403` and no cookie, as today; a blocked ID gets neither; a bad Steam response, a wrong state or a replayed login still fail for everyone.
*   **Session helper:** no cookie, a forged signature, a tampered ID, an expired cookie and a cookie whose ID is not a SteamID64 are anonymous; a valid one is a user; `admin` is true only for IDs on the list *now* (an ID removed from the list is a user on the next request; one added is an admin on the next request); the blocked list removes a user but never an admin.
*   **The sweep:** with a non-admin session every route of the application is requested; every route that is not declared public or user-level refuses; a route without a declared tier fails.
*   **`next`:** accepted for `/servers/x/maps/y`; refused (landing on `/`) for `//evil.example`, `/\evil.example`, `https://evil.example`, `javascript:`, a path over 200 characters, a path with a newline or control character, and an encoded variant of each.
*   **Gated endpoints:** `mesh.glb`, `track.json` and the replay page answer `401` (or a redirect to sign-in with `next` set, for pages) to anonymous visitors, and work for a user and for an admin; the page brings the visitor back after sign-in; the per-account and per-address limits answer `429` with `Retry-After`.
*   **View log:** opening a replay or a mesh writes one `VIEW_REPLAY` or `VIEW_MESH` row with the SteamID64; the same user opening the same thing again within an hour writes none; another user, another round or an hour later writes one; anonymous requests write none; rows older than `VIEW_LOG_DAYS` are removed by the cleanup, and `0` logs nothing.
*   **Header:** anonymous sees the sign-in button; a user sees the ID, no "Servers" link and a logout; an admin also sees the admin mark and the link; the logout form is a `POST`.
*   **Switch:** turning it off ends non-admin sessions at the next request.

## 9. Alternatives Considered
*   **Another identity provider** (Discord, Google, GitHub). The visitors are TTT players, who all have Steam accounts, and the admin allow-list is already SteamID64s; a second provider would need account linking for nothing.
*   **Only accounts that have played on the server** (a SteamID64 that appears in the server's rounds). A stronger gate that also fits per-player features, but it excludes a curious newcomer and anyone who wants to look at a server they have not played on. Kept as a possible stricter mode (`SIGNIN_PLAYERS_ONLY`), not the default.
*   **Per-server invitations or passwords.** More to manage for an owner and no better against scraping than an account limit.
*   **A bot-check on anonymous requests** (a CAPTCHA service). Adds a third party to every visit and still identifies nobody.
*   **Everything public, rate limited by address only.** The current model for the public pages. Adequate for small pages; for multi-MB downloads, addresses rotate too easily and nothing can be done about one abusive person.
*   **A public replay with only the 3D mesh gated.** Keeps replays shareable by link, but the track (where every named player was) would be open to anyone and unattributable; rejected in favour of gating the whole replay.
*   **Everything behind sign-in.** Would break the public stats pages that exist because a server's players want to share them.

## 10. Decided, and Open Questions
**Decided (2026-10-19):**
*   The replay's **track is gated** with the rest: a replay is not public, and there is no anonymous top-down replay either (4.4).
*   **Views of gated content are logged** (6.3).
*   A signed-in player who took part in a round gets **their own player selected by default** in its replay (RFC 12 3.5); someone who did not take part gets the victim of the first death.

**Still open:**
*   **Should anonymous visitors see the 2D floor-plan pictures** (RFC 10, admin-only today)? They are small and derived from the same trace; with replays gated, a plan is the less sensitive of the two.
*   **A viewer for the view log:** an admin page listing who opened what, or is the audit log enough for now?
*   **Players only** (section 9): a per-instance switch for a stricter tier, or never?
*   **Persona names and avatars** would make the header friendlier but need a Steam Web API key and an outbound request per login; worth it?
*   **Session length:** a week for admins is established; should a non-admin session be shorter?
*   **Extra things for a signed-in player about themselves:** a list of their rounds, their own statistics page linked from the header; each needs only the SteamID64 in the cookie.
