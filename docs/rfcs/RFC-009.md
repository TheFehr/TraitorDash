# RFC 9: Pairing a Game Server

> **Status: backend and dashboard implemented; the bridge command (`traitordash_connect`, section 3.4) is not yet.** It depends on [RFC 8](./RFC-008.md) (the bridge configuration file), which is implemented. Until the bridge command exists, a code can be redeemed with a plain `POST /api/v1/pair`, but no released bridge does it for you.

## 1. Abstract
Today an owner adds a server in the dashboard, copies a 64-character API token that is shown once, and pastes it into the game server's configuration together with the dashboard's URL. This RFC replaces the copy-and-paste with **pairing**: the dashboard shows a short, single-use code; the owner runs one console command on the game server; the bridge exchanges the code for its token over HTTPS and stores it itself. The token is never displayed, typed, pasted into chat or written into a file anyone shares.

## 2. Motivation
*   **The token is the weakest step of onboarding.** It is long, shown once (a missed copy means regenerating it), and ends up wherever the owner pastes it: a terminal history, a chat message asking for help, `server.cfg`.
*   **Public adoption.** A new owner should be able to get from "I installed the addon" to "the dashboard shows my server" with one console command and no knowledge of ConVars, file locations or the https rule.
*   **Provisioning stays possible.** Provisioning tools (configuration management, container images, hosting panels) need a token they can write themselves; pairing must be an addition, not a replacement.

## 3. Flow

```
 Dashboard (admin, logged in)                 Game server console                 Backend
 ───────────────────────────                  ───────────────────                 ───────
 "Connect a server" on server X ───────────────────────────────────────────▶ create code
 ◀── shows:  traitordash_connect https://dash.example.com  ABCDE-FGHJK  (10 min, once)

                                              traitordash_connect <url> <code>
                                              ── POST /api/v1/pair {code} ──▶ validate, mark used,
                                              ◀── { token, server_id, name }   rotate X's token
                                              write data/traitordash/config.json (RFC 8)
                                              reload, start the sync
                                              "Connected as «X». Syncing roles…"
```

### 3.1 Creating a code (dashboard)
*   `POST /api/servers/:id/pairing-code`, admin session required, same-site `Origin` required (RFC 7).
*   The backend generates a code, stores only its SHA-256 hash, and returns an HTML fragment (HTMX) with the full command, ready to copy, and a countdown.
*   The command carries the dashboard's own address from `BASE_URL`, so the owner types neither a URL nor a token. Without `BASE_URL` (development) the request's host is used.
*   Creating a new code for a server invalidates its previous unused one: at most one outstanding code per server.
*   The audit log records `PAIR_CODE_CREATED` with the admin's SteamID.

### 3.2 The code
*   10 characters from the Crockford base32 alphabet (digits and letters without `I`, `L`, `O`, `U`), displayed as `XXXXX-XXXXX`: 50 bits from the system's CSPRNG.
*   Case-insensitive; the bridge uppercases it, removes dashes and spaces, and maps the usual confusions (`O`→`0`, `I`/`L`→`1`) before sending.
*   Valid for **10 minutes** and for **one** successful redemption.

### 3.3 Redeeming (backend)
`POST /api/v1/pair` with `{ "code": "ABCDEFGHJK" }`. No bearer token, no session: the code is the credential, so the endpoint is unauthenticated by design (and, having no `Origin`, passes the CSRF check as every bridge request does).

*   One generic failure for *unknown*, *expired* and *already used*: `400 {"error":"invalid or expired code"}`. The three cases are not distinguishable from outside.
*   On success, in **one database transaction**: mark the code used, replace the server's token (`Store.regenerateToken`, the same operation as the dashboard's "Regen token"), and return `{ "token", "server_id", "name" }`. The token appears in this one response and nowhere else; only its hash is stored, as today.
*   The audit log records `PAIR_REDEEMED` (with the client address when known).
*   Expired and used codes are deleted by a periodic cleanup (on startup and hourly).

### 3.4 `traitordash_connect` (bridge)
Console command, superadmin or server console only, `traitordash_connect <url> <code>`:
1.  **Transport first.** The URL goes through `TrustedBaseUrl` (https, or a private/loopback address). A code is a credential too, and the answer carries a token, so a public `http://` URL is refused before anything is sent.
2.  **Can the result be stored?** Write and delete a probe file in `data/traitordash/`. If that fails, stop *before* redeeming, because redeeming rotates the server's token and a lost token would lock the server out.
3.  Normalize the code (3.2) and `POST` it, with a 15 s timeout.
4.  Validate the answer's shape: `token` is a string of the expected form (64 hex characters), `name` a string. Anything else is treated as failure.
5.  Write `config.json` (RFC 8), run `traitordash_reload`, and start the startup sync. Print `Connected as «<name>». Syncing roles…`. The token is never printed.
6.  Failures print one clear line and nothing sensitive: invalid/expired code, rate limited (with the wait), network error, could not write the file.

## 4. Security Considerations

### 4.1 Guessing a code
A successful guess hands the attacker a working token for that server, so the endpoint is rate limited and the space is large.
*   **Space:** 2⁵⁰ ≈ 1.1 × 10¹⁵ codes, at most one outstanding per server, alive for 10 minutes.
*   **Rate limit:** per client address 5 attempts per minute, and **globally** 30 per minute (the existing in-memory `RateLimiter`), answered `429` with `Retry-After`. At the global limit an attacker gets 300 guesses in a code's lifetime: a success probability of about 3 × 10⁻¹³ per code.
*   **Client address:** behind a reverse proxy the socket address is the proxy. The per-address limit therefore uses `X-Forwarded-For` only when the operator opts in (`TRUST_PROXY=1`); without it, only the global limit applies. The global limit alone already makes guessing infeasible; the per-address one limits how much one client can use up of it.
*   **Trade-off:** an attacker who keeps the global limit exhausted blocks legitimate pairing until the window passes. The owner sees `429` and retries, and nothing else is affected (running bridges do not use this endpoint). Considered acceptable; see open questions.

### 4.2 Token rotation
Pairing **replaces** the server's token (the backend stores only hashes and cannot reveal the old one). Consequences, all deliberate:
*   a server that is already running with the old token stops working until its configuration is updated. The dashboard therefore marks a server that reported in the last few minutes and asks for confirmation before creating a code ("This server is online. Pairing replaces its token."); and
*   Servers provisioned by a tool keep using the token that tool wrote. Pairing one of them is a mistake the confirmation above is meant to catch; writing the token into the configuration file (RFC 8, section 5) remains the way to provision.

### 4.3 The code in transit
*   The code and the answer travel only over a trusted transport (3.4 step 1). Over a private-network `http://` address both are readable on that network, exactly as the token is today; the install guide recommends https.
*   A pasted or leaked code is useless after one use or ten minutes, whichever comes first. The dashboard shows it only to the admin who created it, and the database holds only its hash.

### 4.4 What an attacker with a code can and cannot do
They can obtain one server's token, nothing else: no session, no other server, no dashboard access. That is what the token already allows, so pairing adds no new capability, only a new way to reach it, which 4.1 is built to protect.

### 4.5 Unauthenticated endpoint hygiene
*   No state is created by a failed attempt (no rows, no counters in the database); failures are logged to the console at a limited rate, never to the audit table, so the endpoint cannot be used to fill it.
*   The body is limited to a few hundred bytes; anything but a JSON object with a string `code` is a `400`.
*   Responses to failures are identical in body and status for every cause, and a failed attempt takes no longer than a successful lookup of a wrong code (hash, then lookup).

## 5. Data Model
Migration v8:

```sql
CREATE TABLE pairing_codes (
  code_hash  TEXT PRIMARY KEY,                 -- sha256 of the normalized code
  server_id  TEXT NOT NULL REFERENCES servers(id) ON DELETE CASCADE,
  created_by TEXT NOT NULL,                    -- the admin's SteamID64
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  used_at    INTEGER                           -- NULL until redeemed
);
CREATE UNIQUE INDEX pairing_codes_open ON pairing_codes(server_id) WHERE used_at IS NULL;
```
The partial unique index enforces "one outstanding code per server" in the database; creating a new code deletes the old open one in the same transaction.

## 6. Dashboard Changes
*   The server list gets a **Connect** action per server, producing the banner from 3.1.
*   **Add server** ends with the same banner instead of the raw token. The raw token stays available under an *Advanced / provisioning* disclosure for tools that write it themselves (scripts, provisioning tools).
*   Servers that have never reported are labelled "Waiting for the first connection", which is also where the install guide's troubleshooting starts.

## 7. Compatibility and Rollout
*   Additive: a new endpoint, a new table, a new console command. Existing tokens, bridges and the provisioning role are unaffected.
*   **Bridge and backend are independent.** A new bridge against an old backend gets a `404` from `/api/v1/pair` and says "this dashboard does not support pairing; use the token". An old bridge simply has no `traitordash_connect`.
*   Delivered in order: RFC 8 (config file, accessor, reload) first; then this RFC's backend (table, endpoints, tests); then the bridge command and the dashboard UI; the install guide describes pairing as the default path.

## 8. Testing
*   **Backend:** the code is 10 characters from the alphabet; only its hash is stored; a new code replaces the open one; expiry (injectable clock); a code redeems once, the second use fails identically to an unknown one; the three failure causes are indistinguishable; the token is rotated and the old one stops working in the same transaction; a failing step leaves the code unused; the per-address and global limits answer `429` with `Retry-After`; the endpoint needs no session and ignores `Origin`; creating a code needs an admin session and a same-site `Origin`; cleanup removes expired rows; deleting a server removes its codes.
*   **Bridge (Fengari):** a public `http://` URL is refused before any request; the write probe failing stops before redeeming; code normalization (`o`→`0`, dashes, case); a valid answer writes `config.json` and reloads; a malformed answer writes nothing; no printed line contains the token.
*   **End to end:** create a code via the API, redeem it through the real endpoint with the real bridge code in the harness, and check that the next poll with the new token succeeds.

## 9. Alternatives Considered
*   **Device-code flow** (as in the OAuth Device Authorization Grant, IETF RFC 8628): the *server* asks the backend for a code, prints it, and the admin approves it in the dashboard. The secret never has to be typed into a console, and the console command needs only the URL. It needs an *unauthenticated endpoint that creates state* (pending requests), plus the bridge polling for approval, which makes it a larger abuse surface than redeeming a code. The chosen direction keeps every state-creating action behind an admin session.
*   **A longer, self-describing connection string** (`traitordash://host/TOKEN`), to paste once. It is still a long-lived credential in a clipboard and a command history; pairing makes the pasted value worthless within minutes.
*   **Keep the token flow and only improve its documentation.** Cheapest, but leaves the token in chat and shell histories, and is the step most likely to lose a new owner.
*   **Multiple tokens per server**, so pairing does not invalidate the existing one. Removes the rotation hazard in 4.2 but adds token management (naming, listing, revoking) that nothing else needs yet.

## 10. Open Questions
*   Should the global limit be lower, or should a burst of failures *pause* pairing for everyone for a minute? (The trade-off in 4.1.)
*   Is a 10-minute lifetime right? Long enough to start a server and type a command, short enough to be useless when leaked.
*   Should pairing be disabled unless the admin opts in per instance (an environment variable), for operators who want only provisioned tokens?
*   Should redemption record the game server's reported name or address, to show in the dashboard who paired?
