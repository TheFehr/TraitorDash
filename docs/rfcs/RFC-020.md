# RFC 20: Doors, Lifts and Traps in the Replay: Recording Parts That Move

> **Status: proposal (2026-10-24), nothing built.** Follows RFC 12 (the track), RFC 14 (events in the track) and RFC 18 (the parts that can move, drawn in orange). Stage 0 is a probe on a real server; the rest waits for what it finds.

## 1. Abstract
RFC 18 draws the parts of a map that can move (doors, lifts, a building a traitor can bring down) at the place the map file stores them, in orange. In a replay they never move: the building a traitor dropped at minute 4 stands for the whole round, and a door someone opened is shut. This RFC records **where each such part is during the round, and what was done to it, and by whom**, and lets the replay move the orange parts with the match and list the events ("Alice opened `cabin12_securitydoor_1`", "Bob set off `building_collapse`").

It changes three things: the mesh gets one addressable node per movable part (so the viewer can move it), the bridge records poses and inputs with the track, and the replay animates them. Each is a stage that can be built and left on its own.

## 2. Motivation
*   A replay answers "what happened". Many TTT rounds turn on a trap (a falling building, a lift, a flooded room) or a door. Today the replay shows the players walking through walls that were open in the match, and the trap going off shows as nothing.
*   RFC 18 already tells the viewer *which* parts can move. It cannot tell it *when*.
*   An event list that names the part and the player ("who opened what, when") is useful to an admin judging a round, next to the revivals and role changes of RFC 14.
*   The data is small: a handful of parts move in a round, and each pose change is a few numbers.

## 3. What is there
*   **The track (RFC 12).** One timer samples the living players at a shared tick; times are in whole milliseconds since the round began, stored as differences in one list `t`; positions are stored as the first value and then differences. The timer is judged against a time budget, can skip ticks and degrade, and the buffers have caps. The upload is `POST /api/v1/track`, validated strictly and stored whole as JSON in `round_tracks.data`.
*   **Events (RFC 14, 4.3).** An optional `events` array in the upload with its own cap (1,024) and strict checks.
*   **The mesh (RFC 18).** The parts that can move are one `movable` node holding one mesh of all of them, with the triangles already moved to where the entity stands. The viewer cannot tell one part from another, and cannot move one.
*   **The viewer (RFC 12, 3.5).** `replay.ts` loads the mesh, paints the levels, and draws the players from the track by time.
*   **The bridge** has no hook on doors or entity inputs.

## 4. Design

### 4.1 Which part is which: the model number
A brush entity in the game has the model `*N`, the number of its model in the map file (`Entity:GetModel()`; to be confirmed in the probe, 6). The mesh already uses that number: RFC 18 stage 1 reads each brush entity by it. So **the model number is the identity** that joins a part in the mesh to an entity in the game, with no names and no guessing. A `targetname` is only for display: it may be empty or shared by several entities (Airbus has pairs of doors with one name).

If two entities share one model number, they share the pose in the mesh too (the mesh holds the model once). The probe counts how often that happens on the 27 maps; the expectation is never.

### 4.2 The mesh: one node per movable part (stage 1)
The `movable` node becomes a group with **one child node per movable entity**:
*   the child's triangles are **local to the entity's origin** (the form the map file stores them in, before RFC 18's move and turn), and the child's own translation and rotation are the entity's origin and angles (the same matrix `angleMatrix` builds), so the drawn result at rest is what it is today;
*   its extras are `{ model, class, name?, origin, angles }`, and the node is named `movable-<model>`;
*   nothing else about the group changes: orange, no storeys, cut by the level buttons, one switch.

The viewer then moves a part by setting its node's position and rotation. The map page does not, and looks as before. The mesh generation goes up (it has not been deployed yet when this RFC is written, so it may share the bump of RFC 18's last stage).

### 4.3 What the bridge records (stage 2)
A new ConVar, `traitordash_track_parts` (default `0`), switches it on; it only does anything while `traitordash_track` is on. The same hard rule as the rest: **it must never hurt the game**.

**Which entities.** At the start of the round the bridge lists the entities whose class is one of the movable classes of RFC 18 (`func_door`, `func_door_rotating`, `func_movelinear`, `func_rotating`, `func_tracktrain`, `func_physbox`, `func_physbox_multiplayer`) and whose `GetModel()` is `*N`, up to **256**. Entities are looked up once; a table keyed by entity index makes the hook below a single lookup.

**Poses.** The pose of a part is its position (`GetPos`, whole units) and angles (`GetAngles`, in quarter degrees). A pose is stored as a **keyframe** on the track's own tick list, as differences like the players' segments:

```jsonc
"parts": [
  { "m": 98, "c": "func_movelinear", "n": "building_collapse",
    "k": [0, 410, 5, 5, 5],          // tick index of each keyframe, as differences (the first is absolute)
    "x": [160, 0, 0, 0, 0],          // first value absolute, then differences; whole units
    "y": [2240, 0, 0, 0, 0],
    "z": [-602, 0, -208, -208, -208],
    "p": [0, 0, 0, 0, 0], "w": [0, 0, 0, 0, 0], "r": [0, 0, 0, 0, 0] }   // pitch, yaw, roll, quarter degrees
]
```
*   Every tracked part has a **first keyframe** at the first tick (a door that starts open is then right). After that a keyframe is written **only when the pose changed**, so a door that is never touched costs one keyframe.
*   **Cost is kept low by an active set.** Sampling 256 parts at every tick would eat into the track's own budget. Instead the bridge samples the **active** parts at every tick: a part becomes active when an input reaches it (4.4) or when a full scan finds that its pose changed, and stops being active after two ticks without change. A **full scan** of all tracked parts runs at every fifth tick, which finds what no input announced (a pushed crate, a train). A part that moves for the whole round (a fan) is active for the whole round and is bounded by the caps.
*   The viewer **interpolates linearly** between two keyframes. A door that takes a second to open and is sampled every 0.2 s shows a smooth swing; at the slowest interval (1 s) it shows a jump. That is the same limit the players have.
*   **Caps:** 256 parts, 4,000 keyframes per part, 50,000 in all; beyond a cap the recording of that part stops and the track is flagged `truncated` (as for the other caps). The size estimate for the track's byte cap counts parts too.
*   **Budget.** The time spent on parts is part of the tick's time, so the existing budget, backing off and degrading apply to it unchanged. If the track degrades, parts stop with the rest.

### 4.4 What happened to a part: inputs (stage 2)
`GM:AcceptInput(ent, input, activator, caller, value)` is called whenever something fires an input at an entity. The bridge hooks it and records, for a tracked part and an input on a short list, an entry in a new array **`inputs`**:

```jsonc
"inputs": [ { "t": 94210, "m": 98, "i": "open", "by": "7656119..." } ]
```
*   `t` is milliseconds since the round began (as in `deaths` and `events`); `m` is the model number; `i` the input name in lower case, one of a fixed list (`open`, `close`, `toggle`, `lock`, `unlock`, `use`, `setposition`, `startforward`, `startbackward`, `stop`, `reverse`, `start`); `by` the player who caused it: the `activator` when it is a player, else the `caller` when it is, else absent (a map timer, a trigger fired by a prop).
*   Up to **1,024** inputs per track. A part that is toggled every tick would hit the cap by design, not grow the upload. An input also marks the part active (4.3).
*   **The hook returns nothing.** In Garry's Mod, returning `true` from `AcceptInput` **blocks the input**. The hook must end without a return value on every path, including the error path (`pcall`), and a test checks that. It does one table lookup before anything else, so that the many inputs a busy map fires (logic timers, triggers) cost almost nothing; all other work is only for tracked parts.
*   `GM:PlayerUse(ply, ent)` could say who pressed use on a door that opens by itself. It is left out until the probe shows `AcceptInput` misses it.
*   Inputs say what was *asked*. The pose says what *happened*; a locked door asked to open stays shut and the replay shows it shut.

### 4.5 Upload and storage (stage 2)
Two optional arrays, `parts` and `inputs`, are added to the body of `POST /api/v1/track`, and stored in the same JSON `data`. No migration is needed. The checks follow the rest:
*   every array of a part is the same length; every value is an integer in the range of the map (positions) or of a quarter-degree angle (−1,440 to 1,440 after differences are added up); the tick indexes are inside `t` and rise;
*   `m` is 1 to 65,535 and appears once among the parts; `c` is one of the classes of 4.3; `n` is at most 64 characters of the usual filter;
*   `inputs` are sorted by time, `i` is on the list, `by` is a player in the round or absent;
*   counts are inside the caps, and an upload over **8 MB** is still refused. The retention limits (RFC 12, 3.4) apply to the larger track; the extra size is small (an estimate: a typical round, 40 keyframes per moving part and a dozen moving parts, is under 20 KB).

An old bridge sends neither field and an old backend would refuse unknown fields: **deploy the backend first**, as for RFC 14.

### 4.6 The replay (stage 3)
*   `replay.ts` finds the `movable-<model>` nodes; for each `parts` entry with a matching `m` it sets the node's position and rotation from the keyframes at the current replay time (linear between two keyframes, the first before the first and the last after the last). A part in the track with no node in the mesh (an older mesh, a different map version) is ignored; a node with no entry stays at rest.
*   The angles go through the same rotation matrix as the mesh (`Rz(yaw)·Ry(pitch)·Rx(roll)`), turned into a quaternion, in the Source space of the mesh's root node.
*   The **event list** (RFC 14, 4.6) gets the inputs: "Alice opened `cabin12_securitydoor_1`" at its time, with the part's name when it has one, else its class. Clicking an entry jumps to its time.
*   The level cut and the "Movable parts" switch work as on the map page. The orange stays, so a part in motion cannot be taken for the fixed map.
*   A replay of a round without parts looks as it does now.

### 4.7 What it does not do
*   It does not record **doors that are props** (`prop_door_rotating`, `prop_dynamic` doors). They are props in the mesh (RFC 18, stage 2), not brush entities, and have no model number to join on (9).
*   It does not record **breakable glass and walls** being broken (9); the mesh draws them as fixed.
*   It does not show a live view, and it does nothing to change what happens in the game: the hooks only watch.
*   It does not add statistics ("trap triggers by player"). The data would allow it later.

## 5. Data model
No migration. The track JSON gets `parts` and `inputs` as above. The mesh extras get one `movable-<model>` node per part. `GeometryInfo` and the page are unchanged.

## 6. Compatibility and rollout
*   Stage 1 (the mesh) changes only how the mesh is written; the map page looks the same, and the replay still draws the parts at rest. It is safe to deploy alone.
*   Stage 2 is off until `traitordash_track_parts` is set. Deploy the backend before the bridge.
*   Stage 3 changes nothing for a track without parts.
*   Each stage is a separate commit with this RFC updated to say what was built and measured, as for RFC 18.

## 7. Testing
*   **Mesh:** a map with two movable entities gives two nodes with the right extras and local triangles; moving a node by its extras' origin and angles gives the triangles the previous version drew; survey the 27 real maps for duplicate model numbers and for the node counts.
*   **Bridge (the headless Lua harness, as for the track):** poses are written only when they change; the first keyframe is always written; the active set stops after two quiet ticks; the full scan catches a part nobody announced; the caps truncate and flag; `AcceptInput` records a listed input on a tracked part and ignores the rest; **the hook returns no value** for tracked, untracked, listed and unlisted inputs, and when the recording code fails; with `traitordash_track` off nothing is hooked.
*   **Backend:** a valid upload is stored and returned; every check of 4.5 has a test that it is refused with `400`; an upload without the new fields is as before.
*   **Viewer:** a fixture track and mesh: at times before, between and after two keyframes the node has the expected position and rotation; an unknown model is ignored; the event list shows the inputs.
*   **Acceptance on a real server** (not reproducible here, as for RFC 12 and 14): see stage 0.

## 8. Alternatives considered
*   **Record every part at every tick.** The simplest, and wasteful: a map has up to a few hundred parts and almost all of them never move. Rejected for the active set plus a slow full scan.
*   **Record only inputs, and replay by guessing the motion** (a door opens over `speed` units per second). It needs each entity's keyvalues (speed, distance, lip, open direction), which the bridge would have to send as well and the viewer would have to simulate; a door blocked by a prop, or a lift stopped half way, would be wrong. Poses are what happened.
*   **Record only poses, without inputs.** The poses show *that* a door opened and not *who* opened it, which is the part an admin asks about.
*   **Join by `targetname`.** Not unique and often empty. The model number is exact.
*   **Join by `MapCreationID` or `hammerid`.** Both work for a map-made entity, and would let the mesh also address entities without their own model (props). They need the mesh to carry them, which stage 1 can add later; the model number needs nothing the mesh lacks today.
*   **Send the poses on a timer of their own.** A second timer is a second cost to budget. The shared tick list is already there.

## 9. Open questions
*   **Does `GetModel()` give `*N` for a brush entity on a real server, and does `N` match the map file's model?** Everything in 4.1 rests on it. Stage 0 answers it.
*   **Does `AcceptInput` fire for what the maps do?** Maps open doors with `logic_relay`, `func_button` and `trigger_*` outputs, which arrive as inputs; a Lua addon that moves a door with `SetPos` does not. The probe compares the inputs seen with the poses that changed and lists the poses with no input.
*   **How big is the cost of the hook on a busy map?** The probe counts inputs per second (maps with many `logic_timer`s may fire thousands) and times the hook.
*   **How fast should a moving part be sampled?** At the track's own tick (0.2 to 1 s) a fast door is a jump. A separate faster sample for the active set only is possible, at the cost of a second list of tick times.
*   **Prop doors.** `prop_door_rotating` is common in building maps. The mesh would have to place it as a node of its own (RFC 18, props) and the join would be by `MapCreationID`. Worth doing if the probe shows many of them in the TTT maps in use.
*   **Breakables.** A window or wall that breaks is a brush entity of a stand-still class today; a `func_breakable` that is broken is removed from the game. It would be a `gone` pose of a part, and the mesh would have to move these out of the fixed geometry as well. A good second use of the same mechanism.
*   **A part with a parent** (a train carrying a door) is left out of the mesh (RFC 18), and so is not tracked.
*   **Does a part that starts part way along its track or starts open** need the first keyframe only (as designed), or also a note in the mesh so the page's rest pose could be right? The first keyframe covers the replay; the page keeps showing the stored pose.

## 10. Stages
0.  **Probe (the bridge, no backend). Built; not yet run on a real server.** A console command, `traitordash_parts_probe`, for a superadmin or the console: prints the tracked entities by class, whether `GetModel()` is `*N`, and for a window of minutes the inputs seen on them, the poses that changed with and without an input, the inputs per second map-wide and the time the hook cost. Run on a real server on Rooftops, Airbus and one more map; the results are written into this RFC (as RFC 12 did for the track). Nothing else is built before that.
1.  **The mesh:** one node per movable part, with extras (4.2).
2.  **Record and store:** the bridge (4.3, 4.4) and the backend (4.5).
3.  **The replay:** move the parts, list the inputs (4.6).
4.  Later, each its own RFC or addendum: breakables and prop doors (9), the same data in the canvas replay of RFC 19, statistics on traps.

### As built (stage 0)
`addon/lua/traitordash/partsprobe.lua`, loaded by `traitordash_init.lua` like the frame-time tool; tests in `backend/test/partsprobe_bridge.test.ts` (21, against a fake of the game with entities, hooks and timers the test controls).
*   **Commands** (console or superadmin): `traitordash_parts_probe scan | start [seconds] | round | auto on [people] | auto off | stop | status`. `start` takes 5 to 1,800 seconds (default 120); `round` watches from the next round's start to its end (at most 30 minutes). Nothing is hooked and no timer runs before a watch starts, and both are removed at its end.
*   **`scan`** lists the movable entities of RFC 18's classes by class (at most 512), how many have a model of the form `*N`, those that do not, models used by two entities, entities without a name, those with a parent (left out of the mesh), and counts `prop_door_rotating`, `func_breakable`, `func_breakable_surf`, `func_button` and `func_wall_toggle` (what RFC 20 leaves out).
*   **A watch** hooks `AcceptInput` and `PlayerUse` and looks at every part's position and angles every 0.2 s. It counts inputs on any entity (a rate) and on parts (by class and input, and whether the activator or only the caller was a player), `PlayerUse` on parts, **movements** (a part's position changed by more than half a unit, or its angles by more than a quarter degree, after standing still), whether an input reached the part in the 5 seconds before each movement (**announced**) or not (**unannounced**, listed with the time and the part), and parts removed from the game. It times the hook (average and worst, in microseconds) and each look at all parts.
*   **Never hurts the game:** every body runs inside `pcall`; the hooks end without returning a value on every path, including when the bookkeeping fails (tests check the number of return values for tracked, untracked and invalid entities and for an error), so an input is never blocked; the lists keep at most 40 lines.
*   **Result:** one block on the console and appended to `data/traitordash_parts_probe.txt` (not beyond 512 KB), to be pasted below. A block starts with the people at the start, at most and at the end (bots counted apart), the number of entities, and one `SUMMARY` line (humans, inputs a second, hook cost, cost of looking at the parts, unannounced movements, the server's frame time average and worst, and the tick). Frame time is looked at five times a second, so it shows a trend.
*   **For an event that comes rarely (a full server every two or three months):** `auto on [people]` watches every round that starts with at least that many humans, with no one at the console, and is kept in `data/traitordash_parts_probe_auto.txt`, so it holds across restarts and map changes until `auto off`. Every way a watch can end writes its block: the round ending, a restarted round, a map change or shutdown, the time running out. Rehearse on a small server with bots first (`auto on 1`), then set `auto on 20` (or the server's usual full number) and leave it.
*   **To run:** on a real server with a few players or bots, `traitordash_parts_probe scan` on each of Rooftops, Airbus and one more map; then `traitordash_parts_probe round` for a whole round in which someone opens doors and sets off a trap. Paste the blocks here and answer the questions of section 9 from them.
