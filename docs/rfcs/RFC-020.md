# RFC 20: Doors, Lifts and Traps in the Replay: Recording Parts That Move

> **Status: stages 0, 1 and 2 built (2026-11-05): the probe has run on a real server, the mesh has a node for each part, and the bridge records the parts and the inputs that reach them and the backend stores them. Stage 2 has run on a real server (2026-11-06, a round with a player and five bots: 28 parts, 4,959 keyframes, 1 input; see "First round with a player"). Stage 3, the replay that moves the parts, is not built. Most doors of 67th Way are `prop_door_rotating`, which this RFC does not record.** Follows RFC 12 (the track), RFC 14 (events in the track) and RFC 18 (the parts that can move, drawn in orange).

## 1. Abstract
RFC 18 draws the parts of a map that can move (doors, lifts, a building a traitor can bring down) at the place the map file stores them, in orange. In a replay they never move: the building a traitor dropped at minute 4 stands for the whole round, and a door someone opened is shut. This RFC records **where each such part is during the round, and what was done to it, and by whom**, and lets the replay move the orange parts with the match and list the events ("Alice opened `cabin12_securitydoor_1`", "Bob set off `building_collapse`").

It changes three things: the mesh gets one addressable node per movable part (so the viewer can move it), the bridge records poses and inputs with the track, and the replay animates them. Each is a stage that can be built and left on its own.

## 2. Motivation
*   A replay answers "what happened". Many TTT rounds turn on a trap (a falling building, a lift, a flooded room) or a door. Today the replay shows the players walking through walls that were open in the match, and the trap going off shows as nothing.
*   RFC 18 already tells the viewer *which* parts can move. It cannot tell it *when*.
*   An event list that names the part and the player ("who opened what, when") is useful to an admin judging a round, next to the revivals and role changes of RFC 14.
*   The data is small: a handful of parts move in a round, and each pose change is a few numbers.

## 3. What is there
*   **The track (RFC 12).** One timer samples the living players at a shared tick; times are in whole milliseconds since the round began, stored as differences in one list `t`; positions are stored as the first value and then differences. The timer is judged against a time budget, can skip ticks and degrade, and the buffers have caps. The upload is `POST /api/v1/track`, validated strictly and stored whole as JSON in `round_tracks.data`.
*   **Events (RFC 14, 4.3).** An optional `events` array in the upload with its own cap (1,024) and strict checks.
*   **The mesh (RFC 18).** The parts that can move are one `movable` node holding one mesh of all of them, with the triangles already moved to where the entity stands. The viewer cannot tell one part from another, and cannot move one.
*   **The viewer (RFC 12, 3.5).** `replay.ts` loads the mesh, paints the levels, and draws the players from the track by time.
*   **The bridge** has no hook on doors or entity inputs.

## 4. Design

### 4.1 Which part is which: the model number
A brush entity in the game has the model `*N`, the number of its model in the map file (`Entity:GetModel()`; to be confirmed in the probe, 6). The mesh already uses that number: RFC 18 stage 1 reads each brush entity by it. So **the model number is the identity** that joins a part in the mesh to an entity in the game, with no names and no guessing. A `targetname` is only for display: it may be empty or shared by several entities (Airbus has pairs of doors with one name).

If two entities share one model number, they share the pose in the mesh too (the mesh holds the model once). The probe counts how often that happens on the 27 maps; the expectation is never.

### 4.2 The mesh: one node per movable part (stage 1)
The `movable` node becomes a group with **one child node per movable entity**:
*   the child's triangles are **local to the entity's origin** (the form the map file stores them in, before RFC 18's move and turn), and the child's own translation and rotation are the entity's origin and angles (the same matrix `angleMatrix` builds), so the drawn result at rest is what it is today;
*   its extras are `{ model, class, name?, origin, angles }`, and the node is named `movable-<model>`;
*   nothing else about the group changes: orange, no storeys, cut by the level buttons, one switch.

The viewer then moves a part by setting its node's position and rotation. The map page does not, and looks as before. The mesh generation is not raised in stage 1: generations 6 and 7 are already deployed, and nothing reads the nodes before stage 3. It is raised in stage 3, when the replay needs them; until then a map built now has the nodes, a stored one has the single `movable` node of world-space triangles, and every reader copes with both (a replay of a stored mesh simply moves nothing).

### 4.3 What the bridge records (stage 2)
A new ConVar, `traitordash_track_parts` (default `0`), switches it on; it only does anything while `traitordash_track` is on. The same hard rule as the rest: **it must never hurt the game**.

**Which entities.** At the start of the round the bridge lists the entities whose class is one of the movable classes of RFC 18 (`func_door`, `func_door_rotating`, `func_movelinear`, `func_rotating`, `func_tracktrain`, `func_physbox`, `func_physbox_multiplayer`) and whose `GetModel()` is `*N`, up to **256**. Entities are looked up once; a table keyed by entity index makes the hook below a single lookup.

**Poses.** The pose of a part is its position (`GetPos`, whole units) and angles (`GetAngles`, in quarter degrees). A pose is stored as a **keyframe** on the track's own tick list, as differences like the players' segments:

```jsonc
"parts": [
  { "m": 98, "c": "func_movelinear", "n": "building_collapse",
    "k": [0, 410, 5, 5, 5],          // tick index of each keyframe, as differences (the first is absolute)
    "x": [160, 0, 0, 0, 0],          // first value absolute, then differences; whole units
    "y": [2240, 0, 0, 0, 0],
    "z": [-602, 0, -208, -208, -208],
    "p": [0, 0, 0, 0, 0], "w": [0, 0, 0, 0, 0], "r": [0, 0, 0, 0, 0] }   // pitch, yaw, roll, quarter degrees
]
```
*   Every tracked part has a **first keyframe** at the first tick (a door that starts open is then right). After that a keyframe is written **only when the pose changed**, so a door that is never touched costs one keyframe.
*   **Cost is kept low by an active set.** Sampling 256 parts at every tick would eat into the track's own budget. Instead the bridge samples the **active** parts at every tick: a part becomes active when an input reaches it (4.4) or when a full scan finds that its pose changed, and stops being active after two ticks without change. A **full scan** of all tracked parts runs at every fifth tick, which finds what no input announced (a pushed crate, a train). A part that moves for the whole round (a fan) is active for the whole round and is bounded by the caps.
*   The viewer **interpolates linearly** between two keyframes. A door that takes a second to open and is sampled every 0.2 s shows a smooth swing; at the slowest interval (1 s) it shows a jump. That is the same limit the players have.
*   **Caps:** 256 parts, 4,000 keyframes per part, 50,000 in all; beyond a cap the recording of that part stops and the track is flagged `truncated` (as for the other caps). The size estimate for the track's byte cap counts parts too.
*   **Budget.** The time spent on parts is part of the tick's time, so the existing budget, backing off and degrading apply to it unchanged. If the track degrades, parts stop with the rest.

### 4.4 What happened to a part: inputs (stage 2)
`GM:AcceptInput(ent, input, activator, caller, value)` is called whenever something fires an input at an entity. The bridge hooks it and records, for a tracked part and an input on a short list, an entry in a new array **`inputs`**:

```jsonc
"inputs": [ { "t": 94210, "m": 98, "i": "open", "by": "7656119..." } ]
```
*   `t` is milliseconds since the round began (as in `deaths` and `events`); `m` is the model number; `i` the input name in lower case, one of a fixed list (`open`, `close`, `toggle`, `lock`, `unlock`, `use`, `setposition`, `startforward`, `startbackward`, `stop`, `reverse`, `start`); `by` the player who caused it: the `activator` when it is a player, else the `caller` when it is, else absent (a map timer, a trigger fired by a prop).
*   Up to **1,024** inputs per track. A part that is toggled every tick would hit the cap by design, not grow the upload. An input also marks the part active (4.3).
*   **The hook returns nothing.** In Garry's Mod, returning `true` from `AcceptInput` **blocks the input**. The hook must end without a return value on every path, including the error path (`pcall`), and a test checks that. It does one table lookup before anything else, so that the many inputs a busy map fires (logic timers, triggers) cost almost nothing; all other work is only for tracked parts.
*   `GM:PlayerUse(ply, ent)` could say who pressed use on a door that opens by itself. It is left out until the probe shows `AcceptInput` misses it.
*   Inputs say what was *asked*. The pose says what *happened*; a locked door asked to open stays shut and the replay shows it shut.

### 4.5 Upload and storage (stage 2)
Two optional arrays, `parts` and `inputs`, are added to the body of `POST /api/v1/track`, and stored in the same JSON `data`. No migration is needed. The checks follow the rest:
*   every array of a part is the same length; every value is an integer in the range of the map (positions) or of a quarter-degree angle (−1,440 to 1,440 after differences are added up); the tick indexes are inside `t` and rise;
*   `m` is 1 to 65,535 and appears once among the parts; `c` is one of the classes of 4.3; `n` is at most 64 characters of the usual filter;
*   `inputs` are sorted by time, `i` is on the list, `by` is a player in the round or absent;
*   counts are inside the caps, and an upload over **8 MB** is still refused. The retention limits (RFC 12, 3.4) apply to the larger track; the extra size is small (an estimate: a typical round, 40 keyframes per moving part and a dozen moving parts, is under 20 KB).

An old bridge sends neither field and an old backend would refuse unknown fields: **deploy the backend first**, as for RFC 14.

### 4.6 The replay (stage 3)
*   `replay.ts` finds the `movable-<model>` nodes; for each `parts` entry with a matching `m` it sets the node's position and rotation from the keyframes at the current replay time (linear between two keyframes, the first before the first and the last after the last). A part in the track with no node in the mesh (an older mesh, a different map version) is ignored; a node with no entry stays at rest.
*   The angles go through the same rotation matrix as the mesh (`Rz(yaw)·Ry(pitch)·Rx(roll)`), turned into a quaternion, in the Source space of the mesh's root node.
*   The **event list** (RFC 14, 4.6) gets the inputs: "Alice opened `cabin12_securitydoor_1`" at its time, with the part's name when it has one, else its class. Clicking an entry jumps to its time.
*   The level cut and the "Movable parts" switch work as on the map page. The orange stays, so a part in motion cannot be taken for the fixed map.
*   A replay of a round without parts looks as it does now.

### 4.7 What it does not do
*   It does not record **doors that are props** (`prop_door_rotating`, `prop_dynamic` doors). They are props in the mesh (RFC 18, stage 2), not brush entities, and have no model number to join on (9).
*   It does not record **breakable glass and walls** being broken (9); the mesh draws them as fixed.
*   It does not record **physics props** (`prop_physics` crates and barrels): a carried or pushed one is not a part (first round with a player, at the end).
*   It does not show a live view, and it does nothing to change what happens in the game: the hooks only watch.
*   It does not add statistics ("trap triggers by player"). The data would allow it later.

## 5. Data model
No migration. The track JSON gets `parts` and `inputs` as above. The mesh extras get one `movable-<model>` node per part. `GeometryInfo` and the page are unchanged.

## 6. Compatibility and rollout
*   Stage 1 (the mesh) changes only how the mesh is written; the map page looks the same, and the replay still draws the parts at rest. It is safe to deploy alone.
*   Stage 2 is off until `traitordash_track_parts` is set. Deploy the backend before the bridge.
*   Stage 3 changes nothing for a track without parts.
*   Each stage is a separate commit with this RFC updated to say what was built and measured, as for RFC 18.

## 7. Testing
*   **Mesh:** a map with two movable entities gives two nodes with the right extras and local triangles; moving a node by its extras' origin and angles gives the triangles the previous version drew; survey the 27 real maps for duplicate model numbers and for the node counts.
*   **Bridge (the headless Lua harness, as for the track):** poses are written only when they change; the first keyframe is always written; the active set stops after two quiet ticks; the full scan catches a part nobody announced; the caps truncate and flag; `AcceptInput` records a listed input on a tracked part and ignores the rest; **the hook returns no value** for tracked, untracked, listed and unlisted inputs, and when the recording code fails; with `traitordash_track` off nothing is hooked.
*   **Backend:** a valid upload is stored and returned; every check of 4.5 has a test that it is refused with `400`; an upload without the new fields is as before.
*   **Viewer:** a fixture track and mesh: at times before, between and after two keyframes the node has the expected position and rotation; an unknown model is ignored; the event list shows the inputs.
*   **Acceptance on a real server** (not reproducible here, as for RFC 12 and 14): see stage 0.

## 8. Alternatives considered
*   **Record every part at every tick.** The simplest, and wasteful: a map has up to a few hundred parts and almost all of them never move. Rejected for the active set plus a slow full scan.
*   **Record only inputs, and replay by guessing the motion** (a door opens over `speed` units per second). It needs each entity's keyvalues (speed, distance, lip, open direction), which the bridge would have to send as well and the viewer would have to simulate; a door blocked by a prop, or a lift stopped half way, would be wrong. Poses are what happened.
*   **Record only poses, without inputs.** The poses show *that* a door opened and not *who* opened it, which is the part an admin asks about.
*   **Join by `targetname`.** Not unique and often empty. The model number is exact.
*   **Join by `MapCreationID` or `hammerid`.** Both work for a map-made entity, and would let the mesh also address entities without their own model (props). They need the mesh to carry them, which stage 1 can add later; the model number needs nothing the mesh lacks today.
*   **Send the poses on a timer of their own.** A second timer is a second cost to budget. The shared tick list is already there.

## 9. Open questions
*   **Does `GetModel()` give `*N` for a brush entity on a real server, and does `N` match the map file's model?** Everything in 4.1 rests on it. **Answered yes** (see Findings).
*   **Does `AcceptInput` fire for what the maps do?** Maps open doors with `logic_relay`, `func_button` and `trigger_*` outputs, which arrive as inputs; a Lua addon that moves a door with `SetPos` does not. **Answered: partly.** `AcceptInput` sees what maps do to doors, but a door opened with the use key often arrives only as `PlayerUse`, and physics, trains and spinning parts move with no input at all (see Findings).
*   **How big is the cost of the hook on a busy map?** **Answered: small** at 6 to 7 people, which is a full server for this group (see Findings).
*   **How fast should a moving part be sampled?** At the track's own tick (0.2 to 1 s) a fast door is a jump. A separate faster sample for the active set only is possible, at the cost of a second list of tick times.
*   **Prop doors.** `prop_door_rotating` is common in building maps. The mesh would have to place it as a node of its own (RFC 18, props) and the join would be by `MapCreationID`. **The probe shows many:** 30 on one map and 21 on another (see Findings), so they are worth doing, as a stage of their own after the brush parts.
*   **Breakables.** A window or wall that breaks is a brush entity of a stand-still class today; a `func_breakable` that is broken is removed from the game. It would be a `gone` pose of a part, and the mesh would have to move these out of the fixed geometry as well. A good second use of the same mechanism.
*   **A part with a parent** (a train carrying a door) is left out of the mesh (RFC 18), and so is not tracked.
*   **Does a part that starts part way along its track or starts open** need the first keyframe only (as designed), or also a note in the mesh so the page's rest pose could be right? The first keyframe covers the replay; the page keeps showing the stored pose.

## 10. Stages
0.  **Probe (the bridge, no backend). Built and run (28 rounds, 6 maps, 6 to 7 people, a full server for this group; see Findings).** A console command, `traitordash_parts_probe`, for a superadmin or the console: prints the tracked entities by class, whether `GetModel()` is `*N`, and for a window of minutes the inputs seen on them, the poses that changed with and without an input, the inputs per second map-wide and the time the hook cost. Run on a real server on Rooftops, Airbus and one more map; the results are written into this RFC (as RFC 12 did for the track). Nothing else is built before that.
1.  **The mesh: built.** One node per movable part, with extras (4.2); see As built (stage 1).
2.  **Record and store: built.** The bridge (4.3, 4.4) and the backend (4.5); see As built (stage 2).
3.  **The replay:** move the parts, list the inputs (4.6).
4.  Later, each its own RFC or addendum: breakables and prop doors (9), the same data in the canvas replay of RFC 19, statistics on traps.

### As built (stage 0)
`addon/lua/traitordash/partsprobe.lua`, loaded by `traitordash_init.lua` like the frame-time tool; tests in `backend/test/partsprobe_bridge.test.ts` (21, against a fake of the game with entities, hooks and timers the test controls).
*   **Commands** (console or superadmin): `traitordash_parts_probe scan | start [seconds] | round | auto on [people] | auto off | stop | status`. `start` takes 5 to 1,800 seconds (default 120); `round` watches from the next round's start to its end (at most 30 minutes). Nothing is hooked and no timer runs before a watch starts, and both are removed at its end.
*   **`scan`** lists the movable entities of RFC 18's classes by class (at most 512), how many have a model of the form `*N`, those that do not, models used by two entities, entities without a name, those with a parent (left out of the mesh), and counts `prop_door_rotating`, `func_breakable`, `func_breakable_surf`, `func_button` and `func_wall_toggle` (what RFC 20 leaves out).
*   **A watch** hooks `AcceptInput` and `PlayerUse` and looks at every part's position and angles every 0.2 s. It counts inputs on any entity (a rate) and on parts (by class and input, and whether the activator or only the caller was a player), `PlayerUse` on parts, **movements** (a part's position changed by more than half a unit, or its angles by more than a quarter degree, after standing still), whether an input reached the part in the 5 seconds before each movement (**announced**) or not (**unannounced**, listed with the time and the part), and parts removed from the game. It times the hook (average and worst, in microseconds) and each look at all parts.
*   **Never hurts the game:** every body runs inside `pcall`; the hooks end without returning a value on every path, including when the bookkeeping fails (tests check the number of return values for tracked, untracked and invalid entities and for an error), so an input is never blocked; the lists keep at most 40 lines.
*   **Result:** one block on the console and appended to `data/traitordash_parts_probe.txt` (not beyond 512 KB), to be pasted below. A block starts with the people at the start, at most and at the end (bots counted apart), the number of entities, and one `SUMMARY` line (humans, inputs a second, hook cost, cost of looking at the parts, unannounced movements, the server's frame time average and worst, and the tick). Frame time is looked at five times a second, so it shows a trend.
*   **For an event that comes rarely (a full server every two or three months):** `auto on [people]` watches every round that starts with at least that many humans, with no one at the console, and is kept in `data/traitordash_parts_probe_auto.txt`, so it holds across restarts and map changes until `auto off`. Every way a watch can end writes its block: the round ending, a restarted round, a map change or shutdown, the time running out. Rehearse on a small server with bots first (`auto on 1`), then set `auto on 20` (or the server's usual full number) and leave it.
*   **To run:** on a real server with a few players or bots, `traitordash_parts_probe scan` on each of Rooftops, Airbus and one more map; then `traitordash_parts_probe round` for a whole round in which someone opens doors and sets off a trap. Paste the blocks here and answer the questions of section 9 from them.

### Findings of stage 0 (run on a real server, 28 rounds)
The probe ran with `auto on`, unattended, on one server with 6 or 7 humans (no bots) over 28 rounds of 6 maps (`ttt_67thway_rework_b1`, `ttt_community_bowling_re_v1b`, `ttt_minecraft_b7_summer`, `ttt_yucatan`, `ttt_cape_town_revamped`, `ttt_forest_final`). **This is the server's real load:** the group never has more than 10 players, and 7 is a full night, so the cost below is the cost that matters. A larger server would need a new measurement, since inputs and movements grow with the people.

*   **The model number joins the game to the mesh.** Every movable entity of every scan has a model of the form `*N` (28 of 28, 28 of 28, 8 of 8, 1 of 1, 34 to 38 of the same on the minecraft map; `ttt_yucatan` has none); no `N` was used by two entities; none had a parent. Checked against the map files with the reader of RFC 18: on `ttt_67thway_rework_b1` the game's `roofdoor`, `baldoor`, `do1`, `do2`, `car1` and `whitetrain` are `*41`, `*8`, `*18`, `*19`, `*23` and `*28`, and the file says the same, with the same classes. The number of movable entities in the file equals the game's on three maps (28, 28, 8). Section 4.1 stands as designed.
*   **Parts are created and removed during a map.** `ttt_minecraft_b7_summer` has 40 movable entities in its file but the game had 34, 35, 37 and 38 at the start of different rounds (physics blocks that a map creates and removes), and a part was removed while watching in 6 of 28 rounds (a `kill` input on an ore block). A part that does not exist yet still carries its `*N` from the file, so the join holds, but the bridge must look for new parts now and then, not only once at the start of a round.
*   **Cost at 6 to 7 people is small.** The hook took 0.5 to 3.4 microseconds per input on average and 34 at worst; inputs came at 0.1 to 4 a second on most maps and 48 a second on `ttt_forest_final` (hook 0.5 us on average there, 0.025 ms of time a second). Looking at all parts (28 to 38 of them) every 0.2 s took 70 to 115 us on average, about 0.05% of the server's time. **But the worst single look took 1.7 to 5.7 ms in 6 of the 28 rounds** (out of a tick of 45 ms), against 17 to 44 us on the map with no parts. Those spikes are probably garbage collection triggered by the probe's own tables (two per part per look); the probe has been changed to make none, and stage 2 must keep numbers in the part's own fields and write keyframes to a preallocated array. This is a guess until measured again.
*   **The frame-time figure of the first version was useless:** the game's `FrameTime()` on a server is always the tick length (45.45 ms here, 22 ticks a second). The probe now reports how late its own 0.2 s timer ran (average, worst, and the number of looks more than 50 ms late), which does move when a server hitches.
*   **What moves with no input** (0 to 29 such movements a round; 87 of them were `minecart` alone): physics blocks that players or explosions push (`minecart`, `DiaOre_*`, `GoldBlock` on the minecraft map, unnamed `func_physbox`es on `ttt_67thway_rework_b1`), a spinning `func_rotating` (`Clock` on `ttt_cape_town_revamped`, 24 starts), trains that run from the start of the round (`car1`, `whitetrain`), and `func_door`s (`baldoor`, `do1`, `do2` on `ttt_67thway_rework_b1`, `Chest` on `ttt_cape_town_revamped`). So **pose sampling is needed for every kind of part; an event hook alone is not enough**, and stage 2 as designed (keyframes plus inputs) is the right shape.
*   **`AcceptInput` does not see every use.** On the first round of `ttt_67thway_rework_b1`, `PlayerUse` fired 12 times on movable parts while only 3 of the inputs were `use`. A door pushed open with the use key often reaches the game without an input to the door, so **`GM:PlayerUse` is a second event source**, and it is the better one for "who opened it" because it carries the player. The bridge should record both, as `inputs` with a `via` of `input` or `use`.
*   **Who:** for the inputs that reached parts, the activator was a player in 17 of 17 on `ttt_67thway_rework_b1`, and 64 of 76 on the minecraft map; the rest were the map's own (`enablemotion` and `kill` on ore blocks, by nobody). The caller alone was never the player. So the activator is the field to record.
*   **Prop doors are a main kind of door.** `prop_door_rotating` count: 30 on `ttt_67thway_rework_b1`, 21 on `ttt_community_bowling_re_v1b` (against 8 brush parts, all doors; its brush doors never moved in three rounds), 1 on `ttt_forest_final`, none on the other three. Brush breakables: `func_breakable` 38 to 58 on two maps and `func_breakable_surf` (glass) 29 on one. Buttons: up to 12. So parts that are props (RFC 18's props and the game's models) and breakables are the second and third stage, after the brush parts; this RFC's first release shows doors made of brushes only, and says so.

What this changes in the design: (1) `GM:PlayerUse` becomes a second event source (4.4); (2) the bridge's list of parts is refreshed during the round, at the full scan; (3) sampling must not allocate; (4) the sampling cost per part is small enough that no cap below 256 parts is needed at this size, but the spikes must be measured again with the changed probe (leave `auto on` running) before stage 2 is called done; (5) a stage for prop doors and breakables is added after stage 3.

### Findings of the second run (36 rounds, 7 maps, 2026-11-03)
The same unattended probe ran again on a night with 6 or 7 humans: `ttt_67thway_rework_b1` (4 rounds), `ttt_airbus_b3` (6), `ttt_community_pool` (6), `ttt_pwp_v4` (6), `ttt_minecraft_b7_summer` (6), `ttt_lego` (6) and `ttt_lttp_kakariko_a5_fixed` (2, a few people fewer).

*   **A model number can be shared.** On `ttt_airbus_b3` (149 movable entities) the probe counted 6 cases of one `*N` on two entities; on `ttt_pwp_v4` one of 30 has no `*N`. So section 4.1's "never" is wrong for some maps. Stage 1's reader keeps one part for each model number (the first entity wins), so the second entity's origin is lost. What this changes: the bridge records poses for each **entity** (with its model number), the mesh holds the geometry once for each model, and the replay places one copy of a model's node for each entity that uses it. An entity without `*N` is not drawn and is left out of the records.
*   **Cost, the same as the first run.** Hook: 1.1 to 3.2 us on average for an input, 44 us at worst; inputs 0.2 to 3.8 a second on average for a map. Looking at the parts: 2 to 293 us on average (Airbus, with 149 parts, is the largest; Lego with 9 parts and Kakariko about 30 us), but 8 of the 36 rounds have a single look of 3.6 to 5.2 ms (Airbus, community pool, pwp, minecraft), as before. The sampling timer ran 10.9 ms late on average, 39 ms at worst, and never more than 50 ms late: nothing visible to a player. The stage 2 design does not change.
*   **Moves with no input:** 101 on `ttt_community_pool` over 6 rounds, 67 on the minecraft map, 51 on Airbus, 32 on `ttt_67thway_rework_b1`, 29 on `ttt_pwp_v4`, none on `ttt_lego` and Kakariko (all doors there are moved by input).
*   **Prop doors and breakables** (left out): `ttt_67thway_rework_b1` 30 prop doors and 40 breakables, Airbus 5 and 48, `ttt_minecraft_b7_summer` 0 and 58, Lego none, pwp 0 and 13.

### As built (stage 1)
`extractSurfaces` returns `movableParts` next to the world-space `movable` list; `surfacesToGlb` takes `movableParts` and writes the group; `buildGeometry` passes it. Tests: `bsp_stage1.test.ts` (3 new) and `mesh_glb.test.ts` (2 new, one with the Khronos validator).
*   **The reader** collects, for each model that is a movable part (one entry for each model number, the first entity wins, so two entities with one model are one part), the faces' corners as the map file stores them, rounded to sixty-fourths of a unit (exact in a float32, and whole units where the map has them), with the entity's origin, angles, class and `targetname` (cut to 80 characters, display only). The world-space list is kept, so the stored `info.movable` count and the fallback do not change.
*   **The writer** makes the `movable` node a group with no mesh of its own (extras `{ group: 'movable', triangles, parts }`) and one child for each part, named `movable-<model>`, with the translation from the origin, the rotation from `angleQuaternion` of the angles, the orange material, and extras `{ model, class, name?, origin, angles, triangles }`. Triangles with no area are dropped, and a crop keeps a triangle whose centre, once placed, is inside the area. Without parts given it writes the single node of before.
*   **Checked on real maps** (the six the probe ran on, and Airbus): placing each part's local triangles by its origin and angles gives the world list again, vertex for vertex after rounding, on all but Airbus, where 105 of 17,910 vertices differ by a rounding step. Parts with a drawable face: 17 of 31 movable entities on `ttt_rooftops_2016_v1`, 26 of 28 on `ttt_67thway_rework_b1`, 40 of 40, 28 of 28, 8 of 8, and 143 of 143 on Airbus; the others have only faces that are not drawn (tool materials), so there is nothing in the mesh to move for them (they are still recorded in stage 2). The Rooftops page looks as before: the building is orange and the switch hides it.

### As built (stage 2)
Bridge: `track.lua` (the section "Parts that move"), `traitordash_track_parts` (also in the settings list of RFC 23, group "Position tracking"). Backend: `validateTrack` in `services/tracks.ts` and the types `TrackPart`, `TrackInput`. Tests: `track_bridge.test.ts` (10 new, against a fake of the game with entities, hooks and the clock), `tracks.test.ts` (9 new), and the settings tests. No migration: `parts` and `inputs` are stored in the track's JSON.

What differs from the design above, because of what the probe found:
*   **One part for each entity, not for each model.** A part has `e`, a number the track gives it (1, 2, ...), next to `m`, its model number (the name of its node in the mesh): two entities with one model are two parts. Inputs name a part by `e`, not by the model. The viewer (stage 3) places a copy of the model's node for each part that uses it; the mesh already holds a model once. A part is an entity of the seven classes with a model `*N` (N from 1) and no parent; the others are not recorded.
*   **A hold keyframe.** A keyframe only when the pose changes would make the viewer, which draws a straight line between two keyframes, slide a door from its rest pose to the open pose over all the time it stood shut. When a part moves after standing still for more than a tick, the old pose is written once more at the tick before. Cost: one more keyframe for each start of a movement.
*   **The list of parts is made again** on every 25th sample (5 seconds at the default rate), with `ents.FindByClass` for each of the seven classes, so a part the map creates during a round is found (it gets its first keyframe then). A part that is removed is not looked at again; nothing is written for its removal (breakables are a later stage).
*   **Looking.** The first sample looks at every part; then an active part is looked at at every sample, and every part at every fifth. A part is active for two samples after a change and for three after an input. A movement that no input announced starts to show at the next full look, at most five samples late (one second at the default rate); the hold keyframe makes the line start where the part stood. The look writes numbers into the part's own fields and appends to its own arrays, and makes no table of its own (`GetPos` and `GetAngles` make their vectors, as in the probe).
*   **Inputs come from two hooks**, `AcceptInput` and `PlayerUse` (the findings: a door opened with the use key often arrives only there), with `v` = `input` or `use`. `by` is the activator when it is a tracked player, else the caller when it is, else absent. The same input by the same player on the same part within a second is one entry: `PlayerUse` is sent again for as long as the key is held, and a press can arrive as both. Both hooks end without a value on every path (the test counts the values returned for a tracked part, an unlisted input, an untracked entity, nil, and an entity that fails), and both are removed when the recording ends for any reason (end of round, switched off, next round prepared, a cap, degrading).
*   **Failure.** A look that fails ends the recording of the parts (a line says so) and the track is sent without them; players and the rest are not affected. The size estimate counts 36 bytes for a keyframe and 90 for an input.
*   **Angles** are written as quarter degrees from -720 to 719, so a part that turns for the whole round (a fan) jumps by 1,440 where it wraps. The viewer must unwrap them before it draws a line between two keyframes (stage 3). The backend accepts sums of up to 1,440 either way.
*   **Checks** (4.5), as built: `e` is 1 to 65,535 and appears once; `m` is 1 to 65,535; `c` is one of the seven classes; `n` is the usual name characters (the bridge cuts others out); keyframe ticks are inside the track, rise by at least one; the arrays are as long as the keyframes; the sums stay inside +-32,768 units and +-1,440 quarter degrees; at most 256 parts, 4,000 keyframes for a part, 50,000 in all, 1,024 inputs (an input names a part of the track, a listed input, `input` or `use`, a time in order, and a player of the round or nobody).
*   **Measured once (2026-11-06), with bots.** A 16-bot, 289-second round on 67th Way with parts on (28 parts, 5,832 keyframes, 0 inputs, since bots do not open doors): the average tick cost was 0.093 ms, no frame overran (RFC 12, 13), and the worst tick was 3.633 ms, once in 2,905 ticks (a shorter round had 0.474 ms). The spikes of the probe (3.6 to 5.2 ms) are therefore still there, once in a round; the cause (the refresh of the part list on every 25th sample, or the look at all parts) is not proven. Still to do: a round with players who open doors and push crates, to see the inputs.

### First round with a player (2026-11-06)
One round on `ttt_67thway_rework_b1` with a player and five bots (245 s, 6 players), `traitordash_track_parts` on. Read from the stored `track.json`.
*   **What was recorded:** 28 parts, 4,959 keyframes, 1 input. The `func_door` `baldoor` has 28 keyframes and one `use` by the player at 64.0 s, which is where it opens; the two `func_tracktrain` (`car1`, `whitetrain`) moved the whole round with no input at all; 15 other doors and lifts and ten `func_physbox` have one keyframe each, so they never moved. The tick cost was 0.065 ms on average and 0.365 ms at the worst, the track 195 KB encoded in 51.7 ms.
*   **The player opened about ten doors, and only `baldoor` is a recorded part.** The door looked at was a `prop_door_rotating` (entity 416). That is the known gap of 4.1 and 9 (30 prop doors on this map), now seen in a real round: **on this map most doors a player uses are not parts**, so a replay with stage 3 alone would show `baldoor` and the trains and nothing of the doors.
*   **Physics props are not in this RFC.** The crate the player carried with the magneto stick was a `prop_physics` (`models/props_junk/wood_crate001a.mdl`, move type VPHYSICS), not one of the ten `func_physbox`, which stood still all round. The bridge looks at the seven brush classes only, so a carried or pushed `prop_physics` (crates, barrels) is not recorded. It is added to what this RFC does not do (4.1), together with the prop doors.
*   **Consequence for the stages:** the bridge's look at a part is the same for a prop (position and angles, differences between keyframes), so prop doors and physics props are one more stage after 3: a part with a class of `prop_door_rotating` or `prop_physics`, joined to the mesh by its model and its place at the start instead of a model number. It needs a model in the replay (RFC 22 draws players from a model file; a prop would use the same way). Not built, and not designed further here.
