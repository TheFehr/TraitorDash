# RFC 16: Round Stats and Maps in the In-Game F1 Menu

> **Status: built (2026-10-22), not yet tried in the game. The pages described in section 3 are now the public pages of the website too (RFC 17); the file names and the "game pages" of this text are history.** The embedded pages, their routes, the two menu pages, the game's vouching for its players and the tests. What is left is the check on a real server (the panel height, the look in the game's browser, whether the game's browser keeps the cookie and runs the replay and the 3D view).

## 1. Abstract
RFC 15 put the role guide into TTT2's F1 menu. This RFC adds two more pages next to it: **Round stats** and **Maps**, in the same case-file look. The F1 tab is renamed **Server info** and holds three pages: Server roles, Round stats, Maps.

## 2. Motivation
Players ask "who is winning?", "what maps are on?" and "what happened in that round?" while they are in the game. The website answers all three, but it is a full site with a header, a login and admin controls, which does not fit a small window, and every link in it leaves the window.

## 3. Design

### 3.1 Embedded pages
The existing public addresses take `?embed=1` and then answer with a page of the role guide's kind: no site header, no script, no admin controls, the same strict Content-Security-Policy, noindex, rate limited by address with the same counter as the role guide, `Cache-Control: private, max-age=30` with an ETag. Every link on them keeps `embed=1`.

*   `GET /servers/:serverId/stats?embed=1` with `view=overview` (default), `leaders` or `rounds`. Overview: rounds, players, average round, last round, who wins (share by team) and the best roles (win rate, from 3 rounds on). Leaderboard: the top 10, sortable by rounds, wins, win rate, kills or K/D. Rounds: the latest 15 with the result as a tag.
*   `GET /servers/:serverId/rounds/:roundId?embed=1` (new, public): one round as a file: result, length, players, deaths, **first blood** (the earliest death by time into the round, else the first reported; "0:48 · killer → victim"), and the roles the players ended with, in the role's own colour. Without `embed` it goes to the stats page.
*   `GET /servers/:serverId/maps?embed=1`: a card per map the vote can offer (as on the website: votable first, then the running map), with the status, the rounds played, when the last was played and a bar of who won there. Maps outside the pool and file sizes are not shown.
*   `GET /servers/:serverId/maps/:map/rounds?embed=1` (new, public): one map: rounds played, average length, last round, who wins there. Without `embed` it goes to the list.

The website pages without `embed` do not change.

### 3.2 The F1 tab
`traitordash_roles.lua` is now titled **Server info** ("Roles, round stats and maps of this server") and, as before, is shown only while the server has said where the dashboard is. Its pages: `guide.lua` (Server roles), `stats.lua` (Round stats), `maps.lua` (Maps). The client builds each address from the base and the server id it was sent (`SectionUrl`, which knows only `stats` and `maps`) and never opens an address it was given. All three pages share one browser panel helper that gives the panel the height of the visible area (a panel docked to fill collapses to a thin strip inside TTT2's scrolling page).

## 4. The game vouches for the player
The replay and the 3D view are for signed-in visitors (RFC 13), and someone in the game has no session on the dashboard. The game server knows who is in front of it, so it vouches for them.

*   **A key per player.** The bridge sends the SteamID64s of the players in the game (bots left out, at most 128) to `POST /api/v1/ingame-keys` (bridge tier: the server's token, 6 requests a minute) and gets one key for each, as a list of `{ steam_id, key }` (not an object keyed by SteamID64: GMod's `util.JSONToTable` turns number-like keys into numbers, and a SteamID64 does not fit in one exactly): `<SteamID64>.<expiry>.<signature>`. The signature is an HMAC-SHA256 under a key derived from the session secret; a key lives 15 minutes. The bridge checks each key's shape and sends it with a net message only to the player it was made for. Keys are asked for when the guide comes on, for players who join (collected for 3 seconds, then one request) and every 10 minutes.
*   **The link.** With a key, the client opens the Round stats and Maps pages through `GET /auth/game?k=<key>&to=<page>`. The role guide does not use it (its pages are public). The client checks the key's shape before it uses it and never opens an address it was sent; it builds this one itself.
*   **The session.** `GET /auth/game` checks the key and sets a cookie of its own (`td_game`, `__Host-td_game` over https), signed with the session secret, HttpOnly, SameSite Lax, 6 hours, then redirects to `to`, which must be a path under `/servers/`. A bad or old key sets no cookie and the redirect still happens, so the player lands on the same public page. Rate limited by address (30 a minute).
*   **What the session is.** A plain signed-in user, **never an admin, not even for an admin's account**: it is read only when there is no real sign-in cookie, and it is returned with `admin: false`. It follows the same switches as a sign-in: without `OPEN_SIGNIN=1` only accounts on the admin list get one (as users), and a blocked account gets none. The log of 3D views (RFC 13) records it like any other user. A real sign-in wins over it, and the logout removes both cookies.
*   **Pages in the window.** The replay and the 3D map page take `?embed=1` too: no site header, no Steam login, the way back stays in the window. Without a session nobody is sent to the Steam login from inside the game: the replay and the 3D page go back to the round and map pages of section 3.
*   **Trust.** A key can only be made with the server's token, so a player cannot make one for somebody else. A game server (or whoever holds its token) can vouch for any SteamID64; it can already report anything about its own players, and the session it can get this way is a plain user's. A leaked key gives a user session for that one player for at most 15 minutes after it was made (6 hours after it is used).
*   **Floor plans** stay admin-only (RFC 13); the map file says so.

## 5. Tests
`test/game_pages.test.tsx`: the shell (no header, no script, no admin controls, policy, noindex), every link keeps `embed=1`, the website pages unchanged, the cache headers and 304, the shared limiter; the overview, leaderboard and rounds views; the round file with first blood by time, without a time, without a killer and without deaths; the replay offered or not; unknown or bad ids; bot-only rounds; the maps cards and file; escaping of nicks and map names. `test/rolemenu_bridge.test.ts`: the tab and its three pages, `SectionUrl`, the keys (what is asked for, to whom each is sent, bad shapes, renewal). `test/game_vouch.test.tsx`: the key (forged, altered, expired), `/api/v1/ingame-keys`, `/auth/game` (cookie, switches, targets, flood), what a game session may and may not do (never an admin), the pages inside the window.
